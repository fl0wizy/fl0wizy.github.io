## 1. 키를 넣는 순서가 쓰기 비용을 바꾼다

B+트리의 노드(페이지)는 크기가 고정돼 있다. 페이지가 가득 찬 상태에서 그 범위에 키가 하나 더 들어오면 **페이지 분할**이 일어난다. 페이지를 둘로 쪼개고 절반씩 나눠 담은 뒤, 부모 노드에 새 항목을 추가한다.

여기서 삽입 순서가 결정적인 차이를 만든다.

**순차 키** — 자동 증가 정수나 시간 순으로 정렬되는 식별자를 쓰면, 새 키는 항상 가장 오른쪽 페이지로 간다. 분할이 거의 일어나지 않고, 분할되더라도 왼쪽 페이지는 가득 찬 채로 남는다. 페이지가 촘촘히 차므로 같은 데이터를 담는 데 필요한 페이지 수가 적다.

**무작위 키** — 랜덤 UUID를 기본키로 쓰면 삽입 위치가 트리 전체에 흩어진다. 중간 페이지가 계속 분할되고, 분할된 페이지는 대략 절반만 찬 상태가 된다. 결과는 세 가지다.

- 인덱스 크기가 커진다. 같은 행 수에 더 많은 페이지를 쓴다.
- 캐시 적중률이 떨어진다. 페이지가 많으니 메모리에 다 올라가지 않는다.
- 쓰기 증폭이 생긴다. 한 행을 넣는데 여러 페이지가 수정된다.

시간 순으로 정렬되는 UUID 변종(UUIDv7 계열)이 등장한 이유가 이 성질이다. 무작위성은 유지하면서 **앞부분을 타임스탬프로 만들어 삽입 위치를 오른쪽 끝에 몰아넣는다.** 식별자 설계라는 애플리케이션 레벨 결정이 스토리지 엔진의 물리 구조에서 역산되는 사례다.

## 2. 기본키 크기가 모든 인덱스로 전파되는 구조

엔진마다 테이블 저장 방식이 다르고, 그 차이가 인덱스의 의미를 바꾼다.

**클러스터드 인덱스 방식**에서는 테이블 자체가 기본키 순서로 저장된다. 기본키 인덱스의 리프가 곧 행 전체다. 그리고 보조 인덱스의 리프는 행의 물리적 위치가 아니라 **기본키 값**을 담는다.

```
보조 인덱스:  [email] → [기본키]
클러스터드:   [기본키] → [행 전체]
```

여기서 두 가지가 따라온다.

- **기본키가 크면 모든 보조 인덱스가 함께 커진다.** 36자 문자열 UUID를 기본키로 쓰면 그 36바이트가 모든 보조 인덱스의 모든 항목에 복제된다.
- **보조 인덱스 조회는 두 번 일어난다.** 보조 인덱스에서 기본키를 찾고, 클러스터드 인덱스에서 행을 찾는다. 필요한 컬럼이 전부 보조 인덱스 안에 있으면(커버링 인덱스) 두 번째 조회를 건너뛴다.

**힙 저장 방식**에서는 테이블이 삽입 순서대로 쌓이고 인덱스 리프가 물리적 위치를 가리킨다. 대신 행이 갱신돼 위치가 바뀌면 인덱스를 따라 갱신해야 하는 문제가 생긴다. 어느 쪽이 낫다기보다, **자기가 쓰는 엔진이 어느 구조인지 알아야 인덱스 설계가 달라진다**는 점이 중요하다.

## 3. MVCC의 비용

현대 데이터베이스 대부분은 다중 버전 동시성 제어를 쓴다. 갱신이 기존 행을 덮어쓰지 않고 **새 버전을 만들고**, 각 트랜잭션은 자기 시점에 보이는 버전을 읽는다. 덕분에 읽기가 쓰기를 막지 않는다.

대가는 구버전의 수명이다. **누군가 오래된 시점을 보고 있으면 그 시점에 보이는 버전들을 정리할 수 없다.**

```
09:00  긴 분석 쿼리 시작 (트랜잭션 열림)
09:00~12:00  같은 테이블에 갱신 수백만 건 발생
             → 생성된 구버전들이 전부 살아 있어야 한다
12:00  분석 쿼리 종료 → 그제야 정리 가능
```

세 시간 동안 테이블이 붓고, 그사이 모든 조회가 불어난 데이터를 훑게 된다. "트랜잭션을 짧게 유지하라"는 조언의 실제 근거가 이것이다. 커넥션을 잡아 둔 채 외부 API를 호출하거나, 트랜잭션 안에서 사용자 입력을 기다리는 코드가 이 문제를 만든다.

정리 작업 자체도 비용이다. 주기적으로 도는 정리 프로세스가 부하를 만들고, 정리가 밀리면 조회 성능이 악화되는 되먹임이 생긴다.

## 4. 스냅샷 격리가 막지 못하는 것

13편에서 lost update를 다뤘는데, 더 미묘한 형태가 하나 더 있다. **write skew**다.

규칙이 하나 있다고 하자. "당직 의사는 최소 한 명 남아야 한다." 현재 두 명이 당직 중이고, 두 사람이 동시에 당직 해제를 요청한다.

```
T1: 당직 인원 조회 → 2명   "나 말고 한 명 더 있으니 빠져도 된다"
T2: 당직 인원 조회 → 2명   "나 말고 한 명 더 있으니 빠져도 된다"
T1: 자기 당직 해제
T2: 자기 당직 해제
결과: 당직 0명
```

각 트랜잭션은 규칙을 확인했고, 확인한 시점에는 규칙이 만족됐다. 두 트랜잭션은 **서로 다른 행을 수정**했으므로 갱신 충돌도 아니다. 스냅샷 격리는 자기가 읽은 행이 나중에 바뀌었는지를 보지, 자기 판단의 근거가 된 **조건 전체**가 여전히 참인지는 보지 않는다.

해법은 세 가지다.

1. **직렬화 가능 격리 수준**을 쓴다. 직렬화 스냅샷 격리를 구현한 엔진은 이런 읽기-쓰기 의존을 추적해 충돌 시 한쪽을 실패시킨다. 애플리케이션은 실패를 받아 재시도해야 한다.
2. **판단 근거를 명시적으로 잠근다.** 조회에 `FOR UPDATE`를 붙여 읽은 행을 잠그거나, 규칙 자체를 대표하는 행 하나를 잠근다.
3. **제약 조건으로 데이터베이스에 맡긴다.** 표현 가능한 규칙이라면 유니크 제약이나 체크 제약이 가장 확실하다.

여기서 일반화할 점은 격리 수준의 이름이 주는 인상보다 실제 보장이 좁다는 것이다. `REPEATABLE READ`라는 이름은 "반복해서 읽어도 같다"는 뜻이지 "내 판단이 계속 유효하다"는 뜻이 아니다. 팬텀 처리도 엔진에 따라 다르다. 어떤 엔진은 스냅샷으로 팬텀이 나타나지 않고, 어떤 엔진은 갭 잠금으로 막는다. **자기 엔진의 문서를 확인하지 않으면 표준 표만 보고 틀린 결론을 낸다.**

## 5. 같은 구조가 정보 채널이 되는 방식

13편의 마지막에서 짚은 내용을 여기서 구체화한다. 지금까지 본 성능 구조가 그대로 공격면이 된다.

blind SQL 인젝션은 응답 본문이 전혀 돌아오지 않는 상황에서 값을 복원한다. 조건이 참일 때만 응답이 느려지게 만들면, 요청 한 번이 1비트를 준다. 글자 하나가 몇 비트이므로, 값 전체를 복원하는 데 필요한 요청 수는 **길이에 선형**이다.

흔히 지연 함수(`sleep` 계열)를 쓴다고 알려져 있지만, 그것이 막혀 있어도 채널은 남는다. 조건이 참일 때만 **비싼 경로를 타게** 만들면 된다.

- 인덱스를 쓰는 조건과 풀스캔을 유발하는 조건의 실행 시간 차이
- 큰 테이블에 대한 카티션 곱
- 정규식 매칭의 파국적 백트래킹

전부 이 심화 글의 앞부분에서 본 구조다. 인덱스가 있고 없고의 차이, 페이지 접근 횟수의 차이가 곧 시간의 차이이고, 시간의 차이가 관측 가능하면 그것이 채널이다.

그래서 **오류 메시지를 숨기는 것은 방어가 아니다.** 에러 기반 추출을 막을 뿐 시간 기반 추출은 그대로 남는다. 실제 방어는 13편에서 정리한 그대로다. 준비된 구문으로 구문과 데이터를 분리하고, 파라미터화할 수 없는 식별자 자리는 허용 목록으로 고정한다.

15편의 분류로 보면 이 칸은 A(구문과 데이터의 미분리)와 D(부수 효과 관측)가 겹치는 자리다. 원인은 A이고 추출 경로는 D다. 그래서 D 쪽만 막으려는 시도(오류 숨기기, 응답 지연 추가)는 근본 대응이 되지 못한다.

## 6. 정리

```
인덱스의 물리 구조   → 식별자 설계와 스키마 결정으로 되돌아온다
MVCC 의 버전 관리    → 긴 트랜잭션 하나가 전체 성능을 끌어내린다
격리 수준의 이름     → 실제 보장은 더 좁다. 엔진 문서로 확인해야 한다
성능 특성의 차이     → 관측되면 곧 정보 채널이다
```

인덱스를 이해하는 것과 타이밍 채널을 이해하는 것은 같은 지식의 두 방향이다. 성능을 위해 알아야 하는 것과 보안을 위해 알아야 하는 것이 이 계층에서는 거의 일치한다.
