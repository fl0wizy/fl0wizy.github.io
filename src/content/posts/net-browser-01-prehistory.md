이 글에서는 웹이 왜 지금의 형태를 갖게 됐는지를 정리한다. HTTP·HTML·URL이라는 세 조각으로 쪼개진 이유, 1993년의 두 라이선스 결정이 승패를 가른 경위, 그리고 표준 기구가 둘로 갈라진 자리에서 현대 웹 취약점의 절반이 서 있는 지반이 만들어진 과정이다.

## 1. 1989년 제안서가 요구한 것

팀 버너스리가 1989년 3월 CERN에 제출한 [Information Management: A Proposal](https://www.w3.org/History/1989/proposal.html)은 하이퍼텍스트 발명 선언문이 아니라 **조직 운영 문제 보고서**에 가깝다. 제안서가 지목한 문제는 인력 이동이다. CERN에서 "2년이 전형적인 체류 기간"이고, 그 결과 정보가 계속 유실된다. 기록이 없어서가 아니라 있는데 찾을 수 없어서다.

당시의 두 가지 해법을 제안서는 각각 기각한다.

- **트리 구조** – 정보를 하나의 계층에 밀어 넣는다. 도움말 시스템에서 막다른 곳에 도달하면 "시스템을 나갔다가 다시 들어와야" 다른 가지의 관련 정보에 닿는다.
- **키워드 시스템** – "두 사람이 같은 키워드를 고르는 일은 없다." 그래서 키워드는 이미 그 분야를 아는 사람에게만 쓸모가 있다.

대신 제안서는 다섯 가지 속성을 요구한다. 이 다섯 개가 오늘날 웹의 설계 제약 그 자체다.

| 요구 속성 | 제안서의 표현 | 현재의 구현 |
|---|---|---|
| 비중앙집중 | "중앙 통제나 조율 없이 기존 시스템을 연결" | 누구나 서버를 띄우고 링크를 건다 |
| 링크 기반 | "링크로 연결된 노트의 '웹'" | 하이퍼링크, `<a href>` |
| 원격 접근 | "원격 머신에서의 접근이 필수" | HTTP over TCP |
| 이기종 수용 | "서로 다른 종류의 시스템에서 같은 데이터에 접근" | MIME 타입, 콘텐츠 협상 |
| 사적 링크 | "공개 정보에 자신의 사적 링크를 추가" | 북마크, 인용, 외부 링크 |

이 중 **비중앙집중**이 가장 비싸게 값을 치른 항목이다. 중앙 통제가 없다는 것은 곧 "입력을 검증해 줄 주체가 없다"는 뜻이고, 이 성질이 이후 모든 편에 그림자를 드리운다.

## 2. HTTP·HTML·URL로 쪼갠 이유

웹이 경쟁 프로토콜과 갈라지는 지점은 기능이 아니라 **분해 방식**이다. 버너스리의 설계는 하나의 시스템을 세 개의 독립 규격으로 쪼갠다.

```
URL   – 무엇을 가리키는가        (식별)
HTTP  – 어떻게 가져오는가        (전송)
HTML  – 가져온 것을 어떻게 읽는가 (표현)
```

세 규격이 서로를 모르기 때문에 각각 독립적으로 교체될 수 있다. 실제로 HTML은 5까지 갔고 HTTP는 와이어 포맷을 세 번 갈아치웠지만 URL은 거의 그대로다. 같은 URL이 HTTP/1.1로도 HTTP/3으로도 가져와지고, 가져온 것이 HTML이 아니라 JSON이어도 동작한다.

동시대의 Gopher는 반대로 갔다. 메뉴 구조·전송·표현이 하나의 프로토콜 안에 묶여 있었고, 그래서 계층적 메뉴라는 형태에서 벗어날 수 없었다. 1989년 제안서가 기각한 바로 그 트리 구조다.

분해의 대가는 **해석 주체가 셋으로 늘어난다**는 것이다. URL을 파싱하는 코드, HTTP 메시지를 파싱하는 코드, HTML을 파싱하는 코드가 각각 따로 존재하고, 각각 다른 사람이 다른 시기에 다른 언어로 구현한다. 이 셋이 같은 바이트열을 다르게 읽을 때 생기는 것이 파서 불일치(parser differential)다. 웹 취약점의 큰 갈래 하나가 여기서 나온다.

## 3. 1993년, 두 개의 라이선스 결정

기술적 우열이 아니라 라이선스가 승패를 갈랐다는 점이 이 역사에서 가장 덜 알려진 부분이다.

**1993년 2월**, 미네소타 대학은 Gopher의 상용 사용에 라이선스 비용을 부과한다고 발표한다. 예산이 삭감되는 상황에서 개발 자원을 계속 쓸 근거가 필요하다는 것이 이유였다. 반응은 즉각적이었다. IBM은 제한적 라이선스가 걸린 프로토콜은 지원하지 않겠다고 선언했고, 커뮤니티의 정서가 하룻밤에 뒤집혔다.

**1993년 4월 30일**, CERN은 반대 방향의 문서에 서명한다. 행정 담당 이사 H. Weber와 전산 담당 이사 W. Hoogland가 서명한 반 페이지짜리 [문서](https://cds.cern.ch/record/1164399)는 `libwww` 라이브러리, 라인 모드 브라우저, W3 서버(`httpd`)에 대한 CERN의 모든 지적재산권을 포기한다. 명시된 의도는 "네트워킹과 컴퓨터 지원 협업에서의 호환성, 공통 관행, 표준을 촉진"하는 것이었다.

결과는 1993년 한 해의 성장률 비교로 남는다.

| 프로토콜 | 1993년 트래픽 성장률 |
|---|---|
| Gopher | 997% |
| Web | 341,634% |

Gopher는 그해에도 웹보다 훨씬 많이 쓰였고 계속 성장하고 있었다. 그런데도 자원이 들어갈 곳을 고르는 기업과 출판사들은 공짜인 쪽을 택했다. 버너스리 자신도 CERN과 라이선싱을 논의 중이었지만, Gopher 발표를 보고 요청을 "아무 제약 없음"으로 바꿨다.

**남은 유산:** 웹의 모든 구현체가 서로 다른 조직이 각자 만든 물건이라는 사실이다. 표준을 강제할 중앙 권력이 없으므로, 각 구현체는 "일단 받아들이고 최선을 다해 해석한다"는 관대한 파싱(Postel의 원칙)으로 수렴했다. 이것이 6편에서 다룰 HTTP 요청 스머글링의 문화적 뿌리다.

## 4. 브라우저 전쟁과 16년의 정체

1차 브라우저 전쟁(1995-2001)은 넷스케이프와 인터넷 익스플로러가 기능을 먼저 내놓는 경쟁이었다. 표준이 없는 상태에서 먼저 구현한 쪽이 사실상의 표준이 되는 구조였기 때문에, 이 시기에 만들어진 상당수의 브라우저 동작이 **스펙에 없는 관행**으로 굳었다. HTML의 태그 자동 닫기, 잘못된 마크업 복구 규칙, 쿠키의 동작 방식 상당 부분이 여기서 나온다.

IE가 승리한 뒤 2001년부터 약 5년간 브라우저 기술은 사실상 멈춘다. 그런데 이 정체기에 웹 애플리케이션의 방향을 바꾼 기능 하나가 조용히 들어와 있었다.

**XMLHttpRequest**는 1999년 IE5에 ActiveX 컨트롤(`Msxml2.XMLHTTP`)로 처음 실렸고, 목적은 Exchange 2000의 Outlook Web Access였다. 메일 클라이언트를 브라우저에서 돌리려면 페이지를 통째로 새로 그리지 않고 데이터만 가져와야 했기 때문이다. 2002년 모질라가 이를 채택했고, 구글이 Gmail과 Google Maps에서 본격적으로 활용했다. 이 묶음에 이름이 붙은 것은 한참 뒤인 2005년 2월 18일, Jesse James Garrett의 글 "Ajax: A New Approach to Web Applications"에서였다.

순서가 중요하다. **기술이 먼저 있었고, 6년 뒤에 이름이 붙었으며, 이름이 붙고 나서야 프런트엔드라는 분야가 생겼다.** 11편에서 다룰 SPA·SSR의 계보는 전부 이 지점에서 출발한다.

## 5. 표준이 두 갈래로 갈라진 날

2004년 6월 2일, W3C의 Web Applications and Compound Documents 워크숍에서 모질라와 오페라가 공동 제출한 제안이 부결된다. 제안의 요지는 HTML의 진화를 다시 열자는 것이었다. 부결 사유는 그것이 이미 선택된 웹의 진화 방향과 충돌한다는 것이었고, W3C는 XML 기반 대체 규격(XHTML2)을 계속 개발하기로 표결했다.

이틀 뒤인 **2004년 6월 4일**, 애플·모질라·오페라가 WHATWG 메일링 리스트를 연다. [WHATWG FAQ](https://www.whatwg.org/faq)가 밝히는 동기는 세 가지다. W3C가 XHTML로 가는 방향, HTML에 대한 무관심, 그리고 실제 웹 개발자의 필요에 대한 무시.

갈라진 상태는 15년간 지속됐고 2019년 5월 양측이 단일 HTML·DOM 규격에 합의하며 봉합된다. 하지만 이 기간이 남긴 결과는 문서 하나가 아니다.

- **Living Standard 개념** – 버전 번호를 붙여 동결하는 대신 계속 갱신되는 규격. HTML5 이후로 "HTML6"이 없는 이유다.
- **파싱 알고리즘의 명문화** – WHATWG HTML 규격의 가장 큰 기여는 새 태그가 아니라, 잘못된 마크업을 만났을 때 브라우저가 **정확히 어떤 순서로 복구해야 하는지**를 바이트 단위로 규정한 것이다. 그전까지 이것은 각 브라우저의 영업 비밀에 가까웠다.
- **규격의 다중화** – HTML은 WHATWG, HTTP는 IETF, CSS와 접근성은 W3C가 관리한다. 한 요청이 브라우저에 도착해 화면이 되기까지 최소 세 기구의 규격을 통과한다.

## 6. 이 역사에서 취약점이 사는 자리

앞의 다섯 절은 전부 같은 구조적 사실로 수렴한다.

```
중앙 통제 없음 (1989 설계 요구)
   → 구현체가 조직마다 따로 존재
   → 스펙 해석 차이를 강제로 교정할 주체 없음
   → 관대한 파싱이 생존 전략이 됨
   → 같은 바이트열을 두 구현체가 다르게 읽음
   → parser differential
```

이 사슬의 마지막 항이 웹해킹 트리의 상당 부분을 차지한다. HTTP 요청 스머글링, 캐시 포이즈닝, 리버스 프록시 우회, 유니코드 정규화 우회, mXSS는 전부 "두 해석기의 불일치"라는 하나의 형태를 공유한다. 개별 기법을 외우는 대신 이 형태를 먼저 붙잡는 것이 이 시리즈 전체의 방침이다.

2022년 6월, IETF는 HTTP 규격을 재편하며 이 문제를 정면으로 다룬다. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)이 버전과 무관한 **의미**(메서드·상태코드·헤더가 무엇을 뜻하는가)를 한 곳에 모으고, RFC 9112/9113/9114가 각각 HTTP/1.1·2·3의 **와이어 문법**만 정의한다. "404가 무엇을 의미하는가"를 단 한 번만 적고 모든 버전이 그것을 빌려 쓰게 만든 것이다. 의미와 문법을 분리하면 구현체 간 해석 차이가 줄어든다는 판단이고, 이 분리는 7편에서 HTTP/2·3을 볼 때 실제로 유용한 좌표가 된다.
