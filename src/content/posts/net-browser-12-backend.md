## 1. 동시 요청을 나누는 세 가지 방식

### 프로세스 (prefork)

요청마다 별도 프로세스가 처리한다. 메모리 공간이 분리돼 있으므로 한 요청의 크래시나 메모리 오염이 다른 요청에 닿지 않는다. 대가는 프로세스 하나당 메모리 비용이고, 동시 처리 수의 상한이 낮다.

함정은 **상태를 프로세스 메모리에 두는 것**이다. 요청마다 다른 프로세스에 배정될 수 있으므로, 메모리 캐시에 넣은 값이 다음 요청에서 없을 수 있다. 로컬에서는 프로세스가 하나라 잘 되다가 배포 후 간헐적으로 실패하는 버그의 흔한 출처다.

### 스레드 풀

같은 프로세스 안의 스레드들이 요청을 나눠 처리한다. 메모리를 공유하므로 가볍고 더 많은 동시 요청을 감당한다. 공유하기 때문에 **경쟁 조건의 무대**가 된다.

전역 캐시, 카운터, 요청 컨텍스트를 잘못 두면 요청끼리 데이터가 섞인다. 실제 사고에서 반복되는 형태는 사용자 정보를 스레드 전역 변수나 싱글턴에 저장했다가, 다음 요청이 그 값을 그대로 읽어 **다른 사용자의 데이터를 응답하는** 경우다. 3편에서 본 single-packet attack이 정확히 이런 공유 상태를 노린다.

### 이벤트 루프 (단일 스레드 비동기)

웹 요청의 시간 대부분은 계산이 아니라 대기다. 데이터베이스 응답을 기다리고, 외부 API를 기다리고, 파일을 기다린다. 이벤트 루프 모델은 대기하는 동안 스레드를 붙잡지 않고 다른 요청을 처리한다. 연결 수가 아무리 늘어도 메모리가 비례해 늘지 않는다.

대가는 명확하다. **CPU를 오래 쓰는 코드 하나가 전체를 멈춘다.** 이미지 처리, 큰 JSON 직렬화, 암호 연산이 루프를 막으면 그동안 모든 요청이 대기한다. 실무에서 가장 흔한 실수는 비동기 프레임워크 안에서 동기 라이브러리를 호출하는 것이다. 코드는 동작하지만 모델의 이점이 통째로 사라진다.

파이썬 생태계에서 WSGI(동기 인터페이스)와 ASGI(비동기 + WebSocket 지원)가 갈라진 것이 이 차이 때문이다. 서버가 오래 유지되는 연결을 다루려면 요청-응답 하나로 끝나는 인터페이스로는 표현할 수 없다.

## 2. API 스타일이 풀려던 문제

### REST

자원을 URL로 식별하고, 행위를 HTTP 메서드로 표현하고, 결과를 상태 코드로 알린다. 요지는 **HTTP가 이미 가진 의미 체계를 다시 만들지 않고 그대로 쓰는 것**이다. 캐시, 조건부 요청, 멱등성 같은 것이 공짜로 따라온다.

한계는 응답 모양이 서버에 고정돼 있다는 점이다. 화면마다 필요한 필드가 다르면 필요 없는 데이터까지 받거나(오버페칭), 여러 번 호출해야 한다(언더페칭).

### GraphQL

클라이언트가 필요한 필드를 쿼리로 지정한다. 오버페칭과 언더페칭이 사라지고 화면 변경이 서버 배포 없이 가능해진다.

대가는 **서버가 응답 비용을 예측할 수 없게 되는 것**이다.

- 중첩 깊이를 키우거나 목록을 재귀적으로 펼치는 쿼리 하나가 데이터베이스에 막대한 부하를 만든다. 깊이 제한과 복잡도 예산이 기본 방어다.
- 별칭(alias)으로 같은 필드를 한 요청 안에 수백 번 넣을 수 있어, 요청 수 기준의 레이트 리밋이 무력화된다.
- 인가가 **필드 단위**로 필요해진다. 엔드포인트 단위 권한 검사에 익숙한 팀이 가장 자주 놓치는 지점이다.
- 인트로스펙션이 켜져 있으면 스키마 전체가 공개된다.

### gRPC

스키마를 먼저 정의하고 코드를 생성하며, 바이너리로 직렬화하고, HTTP/2 위에서 스트리밍을 지원한다. 서비스 간 통신에서 성능과 타입 안전성을 얻는다. 브라우저에서 직접 호출할 수 없다는 점이 제약이고(프록시 계층이 필요하다), 리플렉션을 열어 두면 내부 서비스 구조가 그대로 노출된다.

## 3. 로그인 상태를 어디에 두는가

| | 세션 | 토큰 (JWT) |
|---|---|---|
| 저장 위치 | 서버 저장소 | 토큰 자체 |
| 서버 상태 | 있음 | 없음 |
| 즉시 무효화 | 가능 | 어려움 |
| 내용 노출 | 안 됨 | 누구나 디코딩 가능 |
| 확장 | 공유 저장소 필요 | 서버 간 조율 불필요 |

JWT에서 반복되는 오해 하나를 먼저 정리해 둘 만하다. **서명은 내용을 가리지 않는다.** 페이로드는 Base64URL로 인코딩돼 있을 뿐이고 누구나 디코딩할 수 있다. 민감한 값을 넣으면 그대로 노출된다.

검증 쪽에서 반복되는 실패는 종류가 정해져 있다.

- `alg: none`을 수용하는 라이브러리 설정 — 서명 검증 자체를 건너뛴다.
- RS256과 HS256의 혼동 — 공개키를 HMAC 키로 써 버리면, 공개된 값으로 누구나 유효한 서명을 만든다.
- `kid`, `jku`, `x5u` 헤더를 신뢰해 검증 키를 **토큰이 지시하는 위치에서** 가져오는 구현. 토큰이 자기 검증 키를 고를 수 있으면 검증이 아니다.
- 만료(`exp`) 미확인, 발급자(`iss`)·대상(`aud`) 미확인.

공통점은 하나다. **토큰 안의 값이 검증 절차 자체를 결정하게 두는 것**이다. 검증 파라미터는 서버가 고정해야 한다.

무효화 문제의 실무적 해법은 대개 혼합형이다. 액세스 토큰의 수명을 짧게 두고, 갱신 토큰은 서버가 상태로 관리한다. "무상태"의 장점을 액세스 토큰 구간에서만 취하는 절충이다.

## 4. OAuth 2.0 · OIDC, 그리고 권고가 필수가 되는 과정

두 이름이 자주 섞이는데 역할이 다르다.

- **OAuth 2.0은 인가**다. "이 애플리케이션이 내 자원에 접근해도 좋다"는 위임을 표현한다. 사용자가 누구인지는 규정하지 않는다.
- **OIDC는 인증**이다. OAuth 위에 ID 토큰을 얹어 "이 사용자가 누구인가"를 표준화한다.

OAuth를 로그인 용도로 쓰면서 액세스 토큰만으로 사용자를 식별하려 하면 문제가 생긴다. 액세스 토큰은 "이 토큰이 어떤 권한을 갖는가"만 말하고 "누구에게 발급됐는가"를 검증 가능한 형태로 주지 않기 때문이다.

개정 작업의 방향이 이 영역의 성격을 잘 보여 준다. **OAuth 2.1**은 2026년 기준 아직 IETF 드래프트 단계인데, 합의된 변경 사항은 전부 "선택이던 것을 필수로 올리는" 형태다.

| 변경 | 배경 |
|---|---|
| PKCE 필수 | 인가 코드 탈취 공격 |
| 리다이렉트 URI 정확 일치 | 부분 일치 규칙을 이용한 코드 탈취 |
| 갱신 토큰 회전 필수 | 탈취된 갱신 토큰의 장기 사용 |
| implicit 그랜트 제거 | 토큰이 URL 프래그먼트로 노출 |
| 비밀번호 그랜트 제거 | 서드파티 앱에 비밀번호를 직접 넘기는 구조 |
| 쿼리스트링 베어러 토큰 금지 | 로그·리퍼러·브라우저 히스토리에 남음 |

별도로 [RFC 9700](https://datatracker.ietf.org/doc/rfc9700/)이 OAuth 2.0의 보안 모범 사례를 문서로 정리하고 있다. 여기서 읽을 것은 개별 항목이 아니라 구조다. **규격이 "권장한다"고 적어 둔 항목은 배포 현장에서 지켜지지 않는다.** 그래서 개정판은 같은 내용을 "반드시"로 다시 적는다. 1편에서 본 "강제할 중앙 권력이 없는" 웹의 성질이 여기서도 같은 방식으로 작동한다.

## 5. 이 계층에서 취약점이 사는 자리

- **BOLA / IDOR** — 요청된 객체가 정말 이 사용자의 것인지 확인하지 않는 결함이다. API 보안에서 가장 흔한 1순위 항목이고, 이유는 인증(로그인 여부)은 미들웨어로 한 번에 처리되지만 **인가(이 객체에 대한 권한)는 핸들러마다 따로 써야 하기 때문**이다. 한 곳만 빠뜨려도 뚫린다.
- **Mass assignment** — 요청 본문을 객체에 통째로 바인딩하면 `role` 같은 필드까지 들어온다. 입력 필드를 허용 목록으로 고정하는 것이 방어다.
- **레이스 조건** — 잔액 확인과 차감 사이에 다른 요청이 끼어드는 형태다. 3편의 single-packet attack이 이 창을 마이크로초 단위로 좁힌다. 데이터베이스 수준의 잠금이나 원자적 연산이 필요하고, 이는 13편의 트랜잭션 격리 수준과 직결된다.
- **SSRF** — 서버가 사용자 입력의 URL로 요청을 보낼 때 발생한다. 2편에서 본 사설 주소 대역과 4편의 DNS 해석이 결합되는 지점이다.
- **역직렬화** — 신뢰할 수 없는 직렬화 데이터를 객체로 복원하는 과정에서 임의 코드가 실행된다. 직렬화 포맷이 객체 생성과 메서드 호출을 표현할 수 있는 언어일수록 위험하다.
