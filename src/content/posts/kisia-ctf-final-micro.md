# [KISIA-CTF final] micro: ADC 지문과 RTC 게이트를 넘어 eFuse에 닿기

KISIA CTF 본선에서 나온 2000점짜리 하드웨어 문제다. 배포물이 파일이 아니라 실물 장비라는 점이 특이했다. 팀마다 ESP32-C3 개발보드 한 장, 빵판 한 장, 빨간 점퍼선 아홉 가닥, USB-C 케이블 하나가 들어 있는 봉투를 받았다. 문제 설명은 짧았다. "팀별로 분배된 장비를 이용하여 해결하는 문제입니다. 참가자 실수로 장치 손상 시 복구 불가능합니다. 제공된 장치에서 플래그 획득 후 서버에서 최종 플래그 획득하세요."

결론부터 적어 둔다. 장치의 모든 관문을 통과해 임의 메모리 읽기 권한까지 확보했고, eFuse 전 블록을 덤프해 DEVICE PROOF로 판단되는 32바이트를 회수했다. 다만 그 값을 검증할 챌린지 인스턴스가 만료되어 최종 플래그 문자열은 받지 못했다. 이 글은 거기까지 가는 동안 무엇이 맞았고 무엇이 틀렸는지의 기록이다.

![최종 배선 상태 — 모드 D, 임의 메모리 읽기가 열린 상태](/images/kisia-micro/board_wired.png)

## 1. 손에 쥔 것부터 확인하기

가장 먼저 한 일은 이 검은 기판이 정확히 무엇인지 확정하는 것이었다. 보드 뒷면 실크스크린에 `ESP32-C3`, `SuperMini`, `V1601`이 찍혀 있었고, 앞면 중앙의 QFN 패키지에도 `ESP32-C3`가 각인돼 있었다.

![보드 뒷면 — ESP32-C3 SuperMini V1601](/images/kisia-micro/board_back.png)

ESP32-C3는 RISC-V 32비트 싱글코어 SoC다. CPU, 400KB SRAM, 4MB 플래시, WiFi 802.11 b/g/n, BLE 5, ADC, 그리고 eFuse가 전부 이 한 칩 안에 들어 있다. 플래시가 칩 패키지 내장이라는 점은 나중에 중요해진다. 칩을 떼어내 별도 리더로 읽는 고전적 경로가 원천 봉쇄되기 때문이다.

![보드 앞면 — USB-C, BOOT/RST 버튼, ESP32-C3 QFN 패키지](/images/kisia-micro/board_front.png)

USB-C 커넥터가 칩의 네이티브 USB 핀에 직결돼 있어서, 케이블을 꽂자 별도 어댑터 없이 `/dev/cu.usbmodem1101`로 잡혔다. 이게 첫 번째 통로다.

핀 배치는 실크스크린을 읽어 확정했다. 앞면 기준으로 오른쪽 열이 위에서부터 `5V`, `G`, `3.3`, `GPIO4`, `GPIO3`, `GPIO2`, `GPIO1`, `GPIO0`이고, 왼쪽 열이 `GPIO5`부터 `GPIO21`까지다. 이 배치는 보드 모델에 종속된 것이지 칩이 정한 것이 아니다. 반면 "GPIO0\~4가 ADC1 채널 0\~4"라는 사실은 데이터시트에 있는 칩 고정 사양이다. 이 두 층을 구분하지 않으면 나중에 헷갈린다.

`5V`와 `3.3`이 두 칸밖에 안 떨어져 있다는 점은 미리 적어 둘 만하다. 이 문제에서 보드가 죽을 뻔한 사고는 전부 이 인접 핀을 잘못 물려서 생겼다.

## 2. 펌웨어를 열기 — 문자열 한 블록이 설계의 8할

handout으로 받은 `firmware.bin`은 593,920바이트였다. `esptool image-info`로 구조를 먼저 파싱했다.

```
Project name: micro
ESP-IDF: v4.4.4
Chip ID: 5 (ESP32-C3)
Checksum: valid / Validation hash: valid

Segment  Length   Load addr   Memory types
   0     0x058d0  0x3c070020  DROM
   1     0x02088  0x3fc8ce00  DRAM
   2     0x08690  0x40380000  IRAM
   3     0x6d2ec  0x42000020  IROM
   4     0x04648  0x40388690  IRAM
```

체크섬과 해시가 모두 유효하다는 것은 이미지가 평문이라는 뜻이다. 암호화된 이미지였다면 여기서부터 막혔을 것이다.

다음으로 DROM 세그먼트만 잘라내 통째로 헥스덤프했다. 앱의 읽기 전용 데이터가 모여 있는 곳이고, 여기서 얻을 것이 가장 많다. 실제로 오프셋 `0x744`부터 `0x8c8`까지 200바이트 남짓한 구간에 이 문제의 설계가 거의 다 들어 있었다.

```
0x744  IDLE  LOCKED  C  AUTH  NO  SSID  KEY  OK  OFF  S
0x781  192.168.4.1
0x7a4  23456789ABCDEFGHJKLMNPQRSTUVWXYZ
0x7c8  712dc48a36b905ee  9b4317d06ca2f528
0x7d8  D  AUTH  DENIED  FAULT  READY
0x7f8  %08lx:   0123456789abcdef
0x878  address=  &value=  stored  blocked  bad request
```

한 줄씩 읽으면 이렇게 해석된다. `C`, `S`, `D`는 세 가지 모드의 이름이다. `IDLE`, `LOCKED`, `AUTH`, `READY`, `DENIED`, `FAULT`는 상태머신의 응답이다. `192.168.4.1`은 ESP-IDF SoftAP의 기본 게이트웨이 주소이므로 이 장치가 WiFi AP를 연다는 뜻이다. `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`는 0·1·I·O를 뺀 32글자 알파벳으로, 사람이 눈으로 읽고 손으로 입력하는 코드에 쓰는 전형적인 인코딩이다. `%08lx:`와 `0123456789abcdef`가 나란히 있는 것은 헥스덤프 출력 루틴이 있다는 신호다. `address=`와 `&value=`는 HTTP 폼 파라미터이고, 응답으로 `stored`와 `blocked`가 준비돼 있다는 건 임의 주소에 쓰는 기능과 그것을 막는 범위 검사가 함께 있다는 뜻이다.

그리고 알파벳 바로 뒤에 붙은 16바이트, `712dc48a36b905ee 9b4317d06ca2f528`. 위치상 인증에 쓰이는 키 두 개일 가능성이 높았다. 이 추정은 나중에 실기에서 그대로 통과하면서 확정됐다.

코드를 한 줄도 디스어셈블하지 않고 여기까지 왔다. 임베디드 역분석에서 문자열 덤프가 가장 가성비 높은 첫 수인 이유다.

팀에서는 병행해서 Ghidra로 RISC-V 코드를 복원했다. 함수 이름은 전부 `FUN_ram_42004384` 같은 주소 기반 임시 명칭이었다. 컴파일된 바이너리에는 변수명도 주석도 남지 않기 때문이다. 남는 것은 명령어 흐름과 상수와 문자열뿐이고, 그 셋만으로도 동작은 충분히 복원된다. 디컴파일에서 확정된 것은 세 가지였다. 모드가 GPIO6과 GPIO7 두 비트로 정해진다는 것, 인증 코드가 `ALPHABET[SHA256(key ‖ device_id)[i] & 0x1f]`로 12글자 만들어진다는 것, 그리고 `device_id` 6바이트가 ADC 측정값에서 나온다는 것이다.

## 3. 세 개의 모드, 그리고 권한의 분리

같은 칩에 같은 펌웨어가 올라가 있지만, 부팅하는 순간 GPIO 두 개의 전압이 무엇이냐에 따라 완전히 다른 장치가 된다.

| GPIO6 | GPIO7 | 모드 | 통로 | 인증 | 능력 |
|---|---|---|---|---|---|
| 0 | 0 | LOCKED | — | — | 없음 |
| 1 | 0 | **C** 프로비저닝 | USB 시리얼 | 필요 | WiFi 자격을 NVS에 저장 |
| 0 | 1 | **S** SoftAP | WiFi HTTP | **없음** | 임의 주소 1바이트 **쓰기** |
| 1 | 1 | **D** 콘솔 | USB 시리얼 | 필요 | 임의 주소 **읽기** |

이 표가 문제의 전부다. 쓰기 능력과 읽기 능력이 서로 다른 모드에 갈라져 있고, 모드는 부팅할 때 한 번만 정해진다. 즉 둘을 동시에 가질 수 없다.

더 얄궂은 것은 인증의 비대칭이다. 강력해 보이는 쓰기 프리미티브는 인증이 아예 없다. AP에 붙기만 하면 누구나 메모리를 쓸 수 있다. 반대로 읽기는 12자리 코드를 요구한다. 개발자가 실수로 인증을 빼먹은 것이 아니다. 쓰기 쪽에는 eFuse 영역(`0x60008800`\~`0x60009000`)과 인접 페리페럴 영역을 명시적으로 차단하는 범위 검사가 구현돼 있다. 어디를 보호해야 하는지 정확히 알고 짠 코드다. 만약 S 모드에 읽기가 하나라도 있었다면 인증도 지문도 게이트도 전부 무의미해지고 문제가 즉시 붕괴한다. 이 비대칭이 곧 문제 그 자체였다.

## 4. ADC 지문 — 펌웨어만으로는 인증 코드를 계산할 수 없다

인증 코드는 `SHA256(고정키 ‖ device_id)`에서 나온다. 고정키는 펌웨어에 박혀 있어 누구나 추출할 수 있다. 실제로 우리도 문자열 덤프로 30분 만에 얻었다. 문제는 `device_id`다.

이 6바이트는 장치 어디에도 저장되어 있지 않다. 부팅할 때마다 GPIO0\~4의 전압을 ADC로 측정해 만들어 낸다. 채널마다 10회 샘플링해서 정렬한 뒤 가운데 6개를 합산하고, 그 합을 1536으로 나눠 0\~15로 양자화한다. 6번째 바이트는 채널 0을 다시 보정 측정한 값이다.

설계 의도는 명확하다. 핀을 아무것도 건드리지 않으면 각 보드가 고유한 부유 전압 패턴을 갖고, 그것이 팀별 고유 ID가 된다. 펌웨어만 뜯어서는 절대 계산할 수 없고 실물 보드를 손에 쥐어야만 알 수 있다. "팀별로 분배된 장비를 이용하여 해결하는 문제"라는 한 줄이 여기서 나온다.

정직하게 접근하면 이 값을 측정해야 한다. 멀티미터로 다섯 핀의 전압을 재고 공식에 넣으면 된다. 하지만 우리는 반대로 갔다. **값을 재는 대신 값을 강제했다.**

GPIO0\~4를 전부 3.3V에 묶으면 ADC가 포화한다. 12비트 ADC의 최대값 4095가 6번 더해지면 24570이고, 이를 1536으로 나누면 15.99, 상한 15로 잘린다. 즉 앞 다섯 바이트가 전부 `0x0f`로 고정된다. 개체차가 사라지고 미지수가 6바이트에서 1바이트로 줄어든다.

```
16^6 = 16,777,216 가지  →  16 가지
```

여기서 빵판과 점퍼선 아홉 가닥의 정체가 드러난다. 3.3V를 레일로 빼는 데 한 가닥, GPIO0\~4에 다섯 가닥, 모드 핀 두 개에 두 가닥. 정확히 여덟이고 한 가닥이 남는다. 봉투에 들어 있던 구성이 우연이 아니었다.

실제로 브루트포싱은 몇 초 만에 끝났다.

```
0f0f0f0f0f00 -> NO
0f0f0f0f0f01 -> DENIED
```

`NO`는 코드가 틀렸다는 뜻이고 `DENIED`는 다른 응답이다. 256개 조합 중 단 하나만 `DENIED`를 냈다는 사실이 이 값이 정답임을 강하게 시사했다. 즉 인증은 뚫렸는데 다른 무언가가 막고 있었다.

한 가지 부작용은 감수해야 했다. 포화 상태에서도 6번째 보정 바이트는 여전히 아날로그라서, 점퍼를 만질 때마다 값이 흔들렸다. `01`이었다가 `02`가 되고 `03`이 되기도 했다. 그래서 배선을 건드릴 때마다 16조합을 다시 돌려야 했다. device_id는 MAC 주소처럼 고정된 값이 아니라 매번 재는 체온에 가깝다.

## 5. RTC 게이트 — 부팅을 건너뛰는 다리

`DENIED`의 정체는 2차 관문이었다. 인증 코드가 맞아도 RTC 메모리의 두 워드가 모두 0이 아니어야 `READY`가 나온다.

```
0x50000024
0x50000028
```

RTC 도메인은 칩 안의 저전력 별도 구역이다. 원래는 딥슬립 중에도 시간을 세고 소량의 상태를 보관하려고 만든 곳인데, 중요한 성질이 하나 있다. **CPU가 리셋돼도 내용이 유지되고, 전원이 끊기면 사라진다.**

주최측은 이 성질을 부팅과 부팅 사이에 상태를 전달하는 다리로 썼다. 그리고 그 다리를 놓을 수 있는 유일한 도구가 S 모드의 임의 쓰기다.

```bash
curl -d "address=0x50000024&value=1" http://192.168.4.1/
```

이게 전부다. 특별한 API가 아니라 임의 주소 쓰기 프리미티브로 마침 그 변수를 1로 바꾸는 것뿐이다.

문제는 장치가 **한 부팅에 POST를 한 번만** 받는다는 점이다. 성공하면 HTTP 서버와 AP를 함께 내려버린다. 실제로 두 번째 curl은 이렇게 돌아온다.

```
1번째 → stored
2번째 → This URI does not exist
```

자물쇠가 두 개인데 한 부팅에 하나만 열 수 있으니, 사이에 반드시 재부팅이 필요하다. 그런데 재부팅하면 RTC가 지워질 수 있다. 여기서 이 문제의 진짜 관문이 드러난다.

## 6. 리셋의 종류를 아는 것이 문제의 일부였다

ESP32에는 재부팅 방법이 여럿 있고, RTC에 미치는 영향이 전부 다르다.

| 방법 | 리셋 코드 | 전원 | RTC 메모리 |
|---|---|---|---|
| USB 리셋 (RTS 신호 토글) | `0x15` | 유지 | **보존** |
| RST 버튼 (EN 핀) | `0x1` | 유지 | 소거 |
| 케이블 뽑기 | — | 차단 | 소거 |

USB 리셋은 케이블의 제어선 하나를 토글하는 것으로 끝난다.

```python
s.setRTS(True)
time.sleep(0.25)
s.setRTS(False)
```

부팅 로그에 `rst:0x15 (USB_UART_CHIP_RESET)`이 찍히면 성공이다. 칩 내부의 USB Serial/JTAG 컨트롤러가 CPU만 리셋하고 RTC 도메인은 건드리지 않는다.

반면 보드에 달린 `RST` 버튼은 EN 핀을 직접 당겨 칩 전체를 리셋한다. 눌리는 순간 RTC의 자물쇠가 도로 0이 된다.

이 구분을 몰라서 오래 헤맸다. 1발을 성공시킨 뒤 "재부팅해야 하니까"라며 RST를 눌렀고, 그때마다 성과가 사라졌다. 같은 자리를 몇 번이나 돌았다. 되짚어 보면 이건 실수가 아니라 문제가 의도한 함정이었다. 어떤 리셋이 무엇을 지우는지 아는 것 자체가 풀이의 일부다.

정리하면 최적 절차는 이렇다. 점퍼는 마지막에 한 번만 바꾸면 된다.

```
모드 S 상태에서
  micro-ap 접속 → POST 0x50000024=1 → stored
  USB 리셋 (점퍼 그대로)
  micro-ap 재접속 → POST 0x50000028=1 → stored
여기서 점퍼 하나 추가 → 모드 D → 인증 → READY
```

## 7. 실패의 기록

여기까지가 깔끔한 설명이고, 실제로는 훨씬 지저분했다.

**보드가 덜 꽂혀 있었다.** 초반에 device_id 브루트포싱이 계속 실패했다. 3.3V로 묶었으니 `0f0f0f0f0f0X`가 나와야 하는데 16개도, 256개 균일 조합도 전부 `NO`였다. 원인은 보드가 빵판에 비스듬히 꽂혀서 아래쪽 핀들이 떠 있었던 것이다. 사진을 자세히 보고서야 검은 핀헤더가 표면 위로 드러나 있는 것을 발견했다. 균등하게 눌러 넣자 두 번째 시도에서 바로 걸렸다. 위쪽 모드 핀은 접촉되고 아래쪽 ADC 핀은 안 되는 상태여서, "모드는 정상인데 값만 이상한" 헷갈리는 증상이 나왔던 것이다.

**단락으로 포트가 두 번 죽었다.** 빨간 레일에 3.3V를 흘리는 배선이라 `5V`나 `G`가 그 레일에 닿으면 즉시 전원이 끊긴다. 실제로 두 번 그랬고, 그때마다 `/dev/cu.usbmodem*`이 통째로 사라졌다. 다행히 단락을 제거하면 복구됐다. 배선을 여러 가닥 한꺼번에 바꾸면 원인을 특정할 수 없으니, 한 가닥씩 바꾸고 매번 확인하는 규율이 필요했다.

**내가 만든 증상도 있었다.** AP 탐지를 자동화하려고 1\~2초마다 WiFi 스캔을 돌렸는데, macOS가 스캔할 때 무선칩이 현재 채널을 떠나면서 붙어 있던 연결이 끊겼다. "붙었다가 1\~2초 뒤 끊기는" 무한 반복이 한동안 이어졌고, 원인이 내 스크립트라는 걸 뒤늦게 알았다. 스캔을 멈추자 이번엔 macOS WiFi 메뉴에서 AP가 사라졌다. 메뉴 목록이 스캔 캐시를 읽기 때문이다. 결국 접속될 때까지만 스캔하고 IP를 받는 순간 스캔을 끊는 구조로 정리했다.

**macOS는 CLI로 WiFi에 붙는 것을 막는다.** `networksetup -setairportnetwork`도, CoreWLAN의 `associate`도 전부 실패했다. 후자는 에러 원문이 `Code=-3912` 안에 `-3905 "tmpErr"`를 품고 있었는데, 신호가 rssi -45로 충분한 상황이었으니 무선 문제가 아니라 정책적 거부였다. 스캔은 되는데 결합만 막힌다. 결국 AP 접속만은 사람이 메뉴에서 클릭하는 수밖에 없었다. 이걸 인정하는 데 시간이 꽤 걸렸다.

**대회 중간에 펌웨어가 교체됐다.** "MICRO 문제 하드웨어와 펌웨어간 호환성 이슈가 발견되어 조치중"이라는 공지가 올라왔다. 우리가 겪던 증상 — USB 리셋으로는 AP가 안 뜨고 물리 RST로만 뜨는 것, AP가 44초 만에 꺼지는 것 — 과 정확히 맞아떨어졌다. 이후 `release2`가 배포됐고, 앱 파티션을 직접 플래싱하라는 안내가 따라왔다.

플래싱에서도 한 번 걸렸다. esptool이 이렇게 거부한다.

```
A fatal error occurred: Detected flash encryption and secure download mode enabled.
Flashing plaintext binary may brick your device! Use the force argument to override.
```

플래시 암호화가 켜진 장치에 평문 이미지를 쓰면 벽돌이 된다는 경고인데, 우리가 쓰는 건 이미 암호화된 `application.encrypted.bin`이라 해당되지 않는다. esptool은 파일 내용만 보고 그걸 구분할 수 없어 일괄 경고한다. `--force`를 붙이면 통과한다.

```bash
esptool --port /dev/cu.usbmodem1101 --no-stub write-flash --force 0x10000 application.encrypted.bin
```

쓰는 위치가 앱 파티션(`0x10000`) 하나이고 부트로더(`0x0`)와 파티션 테이블(`0x8000`)은 건드리지 않으니, 잘못돼도 부팅만 안 될 뿐 재플래싱으로 복구된다. 이미지 끝에 Secure Boot v2 서명 블록(`e7 02 00 00`)이 붙어 있는 것도 미리 확인했다.

v1과 v2를 바이트 단위로 비교해 보니 DROM은 완전히 동일했고 IROM만 160바이트 늘어나 있었다. 상수와 인증 체계는 그대로라는 뜻이고, 실제로 기존에 알아낸 키와 토큰 계산식이 그대로 통했다. 플래싱 후에는 USB 리셋만으로 AP가 4초 만에 올라왔다.

## 8. READY, 그리고 eFuse

두 발의 POST가 모두 `stored`를 받은 뒤 점퍼를 다시 꽂아 모드 D로 돌아갔다. 이번에는 응답이 달랐다.

```
D
AUTH
0f0f0f0f0f02 -> READY
```

임의 메모리 읽기가 열렸다. 명령 형식은 `R <주소> <길이>`이고 길이는 최대 256바이트다.

가장 먼저 한 일은 이 프리미티브가 믿을 만한지 검증하는 것이었다. 이미 정답을 아는 영역을 읽어 대조하면 된다. DROM 24KB를 덤프해 배포된 v2 펌웨어와 비교했다.

```
DROM 덤프 vs v2 펌웨어 : 22760/22760 = 100.0% 일치
DROM 덤프 vs v1 펌웨어 : 21305/22760 =  93.6%
```

한 바이트도 틀리지 않았다. 덤으로 v2가 실제로 플래싱됐다는 것도 확인됐다. 상수 위치도 실측으로 잡혔고, 팀이 디컴파일로 복원한 주소와 정확히 일치했다.

```
ALPHABET  0x3c0707bc
KEY8      0x3c0707e0   712dc48a36b905ee
CONST8    0x3c0707e8   9b4317d06ca2f528
```

RTC도 직접 읽어 우리가 쓴 값이 실제로 들어갔는지 확인했다.

```
0x50000020 = 6d43a91e   (RTC 초기화 매직)
0x50000024 = 00000001
0x50000028 = 00000001
```

그리고 eFuse 컨트롤러 전 영역을 덤프했다. 팀 분석이 지목한 USER_DATA(`0x6000887c`)는 32바이트 전부 0이었다. 주소는 맞다. ESP32-C3의 `EFUSE_RD_USR_DATA0_REG`가 정확히 그 위치다. 그냥 비어 있었다.

블록 단위로 정리하면 이렇다.

| 블록 | 주소 | 비영 바이트 | 내용 |
|---|---|---|---|
| BLK0 설정 | `+0x030` | 8/20 | 보안 플래그 |
| BLK1 MAC | `+0x044` | 15/24 | MAC 주소, SPI 설정 |
| BLK2 SYS_PART1 | `+0x05C` | 29/32 | ADC 캘리브레이션 추정 |
| BLK3 USER_DATA | `+0x07C` | **0/32** | 비어 있음 |
| BLK4 KEY0 | `+0x09C` | **0/32** | 비어 있음 |
| **BLK5 KEY1** | `+0x0BC` | **32/32** | 고엔트로피 32바이트 |
| BLK6 KEY2 | `+0x0DC` | 0/32 | 비어 있음 |

KEY1 하나만 꽉 차 있었다. 이게 DEVICE PROOF인지 아니면 플래시 암호화 키인지가 갈림길이었는데, BLOCK0의 `RD_DIS` 비트가 답을 줬다.

```
RD_DIS = 0x01
  bit0  BLOCK4/KEY0  읽기금지   →  그래서 0으로 읽힘
  bit1  BLOCK5/KEY1  읽기가능   →  32바이트가 그대로 노출
```

읽기 보호된 eFuse 블록은 0으로 읽힌다. KEY0이 전부 0인 것은 비어서가 아니라 잠겨 있어서다. 플래시 암호화가 켜져 있으니 그 키가 KEY0에 있고 당연히 잠겨 있다. 반대로 KEY1은 잠그지 않았다. 진짜 비밀키였다면 KEY0처럼 `RD_DIS`를 걸었을 것이다. 열어둔 유일한 비영 블록이고 크기도 32바이트로 딱 떨어진다.

```
585b25dd82df0ebd641cba5e686f7e5b10119eb603eef027ccbfa455f21bccd4
```

## 9. 남은 것

여기서 멈췄다. 이 값을 제출할 `micro device proof verifier` 인스턴스가 만료되어 `nc`가 타임아웃을 냈고, 최종 플래그 문자열은 받지 못했다. 검증되지 않은 값을 플래그라고 적을 수는 없으니 사실만 적어 둔다.

다만 확보한 것들은 여전히 살아 있다. RTC 게이트는 USB 케이블을 꽂아 두는 한 유지되고, 인증 코드는 16조합이면 다시 찾을 수 있고, 읽기 프리미티브의 무결성은 DROM 100% 일치로 증명됐다. 인스턴스만 다시 뜨면 제출은 몇 초다.

## 10. 돌아보며

이 문제가 잘 만들어졌다고 생각하는 이유는 방어가 여러 겹인데 그 겹들이 서로 다른 종류라는 점이다. Secure Boot와 Flash Encryption과 Secure Download Mode는 플래시를 통째로 뜨는 경로를 막고, ADC 지문은 펌웨어만으로 인증 코드를 계산하는 경로를 막고, 읽기와 쓰기의 모드 분리는 하나의 프리미티브로 끝내는 경로를 막는다. 그리고 그 셋을 잇는 마지막 장치가 "어떤 리셋이 RTC를 보존하는가"라는, 문서를 읽지 않으면 알 수 없지만 알고 나면 당연한 지식이었다.

개인적으로 가장 값진 교훈은 두 가지다.

하나는 문자열 덤프가 여전히 가장 싼 첫 수라는 것이다. 디컴파일러를 켜기 전에 DROM 200바이트를 읽은 것이 이 문제의 8할을 열었다.

다른 하나는 아날로그를 상대할 때는 측정하지 말고 강제하라는 것이다. ADC 지문을 정직하게 재려 했다면 멀티미터가 필요했고 오차와 싸워야 했다. 다섯 핀을 전부 3.3V에 묶어 포화시키자 개체차가 사라지고 탐색 공간이 1670만에서 16으로 줄었다. 문제가 아날로그의 불확실성을 방어로 삼았다면, 그 불확실성을 제거하는 것이 곧 공격이 된다.

마지막으로 적어 둘 것은, 이 문제에서 가장 오래 막힌 지점이 취약점이 아니라 배선이었다는 사실이다. 보드가 1mm 덜 꽂혀 있어서 몇 시간을 날렸다. 하드웨어 문제에서는 "코드가 틀렸나"보다 "선이 제대로 닿았나"를 먼저 의심하는 편이 낫다.
