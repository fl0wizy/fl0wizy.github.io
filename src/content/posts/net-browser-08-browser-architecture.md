이 글에서는 바이트열이 브라우저에 도착한 다음을 정리한다. 브라우저가 프로세스를 여러 개 쓰는 이유는 안정성보다 보안 쪽에 무게가 있고, 그 설계는 "렌더러는 결국 장악된다"는 전제에서 역산된 결과다.

![브라우저 프로세스 모델](/images/net-browser/08-browser-process.svg)

---

## 1. 단일 프로세스가 감당하지 못한 것

초기 브라우저는 모든 탭을 한 프로세스에서 돌렸다. 이 구조의 문제는 세 층위로 나뉜다.

- **안정성** — 탭 하나의 크래시가 브라우저 전체를 죽인다.
- **성능** — 한 탭의 무거운 스크립트가 다른 탭의 UI까지 멈춘다.
- **보안** — 렌더링 엔진에 메모리 취약점이 하나 있으면, 공격자는 그 프로세스가 가진 모든 것을 얻는다. 열려 있는 모든 탭의 내용, 쿠키 저장소, 파일 시스템 접근 권한 전부다.

앞의 둘은 불편이고 세 번째는 다른 종류의 문제다. HTML·CSS·JS·이미지·폰트 파서는 **임의의 적대적 입력을 받는 대형 C++ 코드베이스**다. 이런 코드에서 메모리 버그를 0으로 만드는 것은 현실적 목표가 아니다.

Chromium 문서는 이 판단을 전제로 못박는다. 공격자가 렌더러를 장악하는 방법을 찾아낼 것이라고 가정하며, 실제로 Chrome 버전당 렌더러 쪽 high/critical 등급 버그가 5-15개 수준으로 보고돼 왔다고 적는다. **버그를 없애는 대신, 버그가 터졌을 때 얻을 수 있는 것을 줄이는 쪽으로** 설계를 옮긴 것이다.

---

## 2. 무엇을 어디에 두는가

프로세스 분리의 실질은 권한 배치다.

| 프로세스 | 권한 | 다루는 것 |
|---|---|---|
| 브라우저 (브로커) | 사용자 권한 그대로 | UI, 권한 결정, 쿠키 저장소, 프로세스 관리 |
| 네트워크 | 제한적 | 소켓, TLS, 쿠키 부착, 캐시 |
| GPU | 제한적 | 래스터, 합성, 그래픽 드라이버 접촉 |
| 유틸리티 | 강하게 제한 | 이미지·오디오 등 포맷 디코딩 |
| **렌더러** | **샌드박스, 사실상 무권한** | HTML 파싱, DOM, CSS, 자바스크립트, 레이아웃, 페인트 |

렌더러는 파일을 열 수 없고, 소켓을 열 수 없고, 쿠키를 직접 읽을 수 없다. 필요한 모든 것을 IPC(Chromium에서는 Mojo)로 브로커에 요청하고, 브로커가 승인 여부를 판단한다. **적대적 입력을 파싱하는 코드와 권한을 가진 코드를 물리적으로 분리한 것**이 이 배치의 요지다.

유틸리티 프로세스의 존재 이유도 같다. 이미지 디코더 역시 적대적 입력을 파싱하는 대형 코드이므로, 렌더러보다도 더 제한된 별도 프로세스로 떼어 낸다.

## 3. Site Isolation — 격리의 단위

프로세스를 나누기로 했다면 경계를 어디에 그을지 정해야 한다. Chromium의 선택은 **사이트(site)** 다. 문서의 정의는 이렇다.

> "the scheme and registered domain name, including the public suffix, but ignoring subdomains, port, or path"

```
https://foo.example.com:8080  →  site = https://example.com
https://bar.example.com       →  site = https://example.com   (같은 프로세스 가능)
https://other.com             →  site = https://other.com     (반드시 다른 프로세스)
```

브라우저 보안 모델의 기본 단위인 **출처(origin)** 보다 거칠다. 출처는 스킴·호스트·포트가 전부 같아야 하지만, 사이트는 서브도메인과 포트를 무시한다. 더 촘촘한 출처 단위로 나누는 편이 보안상 낫다는 것은 명백한데도 그러지 않은 이유는 호환성이다. `document.domain`을 수정해 서브도메인 간 접근을 허용하는 오래된 페이지들이 남아 있고, 이들을 별도 프로세스에 두면 동작이 깨진다. 1편에서 본 "관대한 파싱"과 같은 종류의 부채가 여기서도 설계를 제약한다.

격리 범위는 탭 단위가 아니다. 한 페이지 안의 **cross-site iframe도 별도 프로세스**로 간다. 광고 iframe이 들어 있는 페이지는 프로세스가 최소 둘이다.

동시에 데이터가 프로세스에 **들어오는 것 자체**를 막는 장치가 붙는다. CORB(이후 ORB)는 cross-site 데이터가 서버의 허가(CORS) 없이는 요청한 페이지의 프로세스에 전달되지 않게 한다. 프로세스 안에 없는 데이터는 그 프로세스가 아무리 장악돼도 읽히지 않는다는 논리다.

## 4. Spectre가 바꾼 전제

Site Isolation의 동기 목록에서 가장 근본적인 것은 세 번째다. Chromium 문서는 Spectre류 사이드채널이 "Chrome에 버그가 없어도" 렌더러 프로세스의 임의 메모리를 읽게 한다고 적는다.

이 사실이 보안 모델의 층위를 하나 끌어내린다.

```
이전 전제 : 같은 프로세스 안이라도 소프트웨어가 출처를 구분해 준다
                (동일 출처 정책은 렌더러 내부의 검사로 강제된다)

Spectre 이후 : 같은 프로세스 안의 메모리는 소프트웨어 검사와 무관하게
                읽힐 수 있다
                → 소프트웨어 경계는 더 이상 보안 경계가 아니다
                → 프로세스 경계를 보안 경계로 승격시켜야 한다
```

같은 이유로 브라우저들은 고해상도 타이머의 정밀도를 낮추고 `SharedArrayBuffer`를 격리 헤더(`COOP`/`COEP`)가 있는 문서에서만 허용하게 됐다. 사이드채널 공격에는 정밀한 시계가 필요하기 때문이다. **하드웨어 계층의 결함이 웹 API 설계를 바꾼 사례**이고, 이 시리즈에서 "아래층이 안 주는 것을 위층이 떠맡는다"는 구조가 가장 극단적으로 드러나는 지점이다.

비용도 명시돼 있다. 데스크톱에서 탭이 많을 때 메모리 오버헤드가 10-13% 수준이고, 메모리가 2GB 미만인 기기와 Android WebView에서는 적용되지 않는다. 보안을 메모리로 사는 거래이며, 살 여력이 없는 환경에서는 적용되지 않는다는 뜻이기도 하다.

## 5. 이 구조에서 익스플로잇의 형태

프로세스 모델이 공격의 모양을 규정한다. 브라우저 익스플로잇은 거의 언제나 **체인**이다.

**1단계 — 렌더러 내부 코드 실행.** 자바스크립트 엔진, HTML/CSS 파서, DOM 구현의 메모리 버그를 쓴다. 성공하면 그 렌더러가 담당하는 사이트의 데이터에 접근할 수 있다.

**2단계 — 샌드박스 탈출.** 브로커와 주고받는 IPC 경계에서 검증이 빠진 지점을 찾거나, 커널·그래픽 드라이버의 취약점을 쓴다. 성공해야 기기 전체에 닿는다.

IPC 경계가 2단계의 주요 표적인 이유는 명확하다. 브로커는 권한을 가진 쪽이고, 렌더러는 적대적이라고 가정된 쪽이다. 브로커가 렌더러에서 온 메시지의 인자를 하나라도 검증 없이 믿으면 그 지점이 권한 경계를 관통하는 통로가 된다. "이 값은 우리 렌더러가 보낸 것이니 정상 범위일 것"이라는 가정이 전형적인 실패 지점이다.

1단계에서 쓰이는 자바스크립트 엔진 내부의 취약점 유형 — 타입 혼동, JIT 최적화의 가정 위반 같은 것 — 은 이 시리즈의 범위를 넘는다. 다음 편에서는 엔진이 파이프라인의 **어디에** 있고 **왜** 그런 형태가 됐는지까지만 다룬다.
