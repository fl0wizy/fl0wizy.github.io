12편이 넘긴 결손은 **읽기와 쓰기 사이에 열리는 창**이고, 그 창을 닫을 권한은 앱이 아니라 데이터가 실제로 놓인 층에 있다. 이 편은 그 층을 열어, 저장과 조회를 맡은 장치들이 왜 지금의 모양으로 굳었는지를 역산한다. **디스크는 느리고, 요청은 동시에 온다.**

## 1. 인덱스의 물리적 형태

인덱스 없이 조건에 맞는 행을 찾으려면 테이블 전체를 읽어야 한다. 행이 백만 개면 백만 번 비교한다. 인덱스는 이를 정렬된 구조로 바꿔 탐색 횟수를 로그 규모로 줄인다.

여기서 자연스러운 의문이 하나 생긴다. 정렬된 탐색 구조라면 이진 탐색 트리로 충분한데 왜 데이터베이스는 **B+트리**를 쓰는가.

답은 최적화 대상이 다르기 때문이다. 메모리 자료구조는 **비교 횟수**를 줄이는 것이 목표지만, 디스크에서는 **블록 접근 횟수**가 비용의 거의 전부다. 디스크는 바이트 단위로 읽지 않고 블록 단위로 읽는다. 한 블록을 읽는 데 드는 시간이 그 블록 안에서 키 수백 개를 비교하는 시간보다 압도적으로 크다.

그래서 노드를 블록 크기만큼 넓게 만든다. 한 노드에 키를 수백 개 담으면 팬아웃이 커지고 트리 높이가 3-4 수준으로 낮아진다. **디스크 접근 서너 번으로 수억 건에서 원하는 행에 도달한다.**

B+트리의 또 다른 성질은 실제 데이터를 리프에만 두고 **리프끼리 연결 리스트로 이어 둔다**는 점이다. 이 때문에 범위 조회가 트리를 다시 타지 않고 순차 읽기가 된다. `BETWEEN`, `ORDER BY`, 페이지네이션이 인덱스로 빨라지는 이유다.

### 인덱스가 공짜가 아닌 이유

- **쓰기 비용** – 행을 하나 넣으면 그 테이블의 모든 인덱스를 갱신해야 한다. 인덱스를 많이 걸수록 쓰기가 느려진다.
- **선택도** – 값의 종류가 적은 컬럼(예: 참/거짓)에 건 인덱스는 대부분의 행을 걸러 내지 못해 쓸모가 없다. 옵티마이저가 무시하고 풀스캔을 택한다.
- **복합 인덱스의 순서** – `(a, b)` 인덱스는 `a` 조건에는 쓰이지만 `b`만으로 조회할 때는 쓰이지 않는다. 사전에서 성으로 정렬된 목록을 이름만으로 찾을 수 없는 것과 같다.
- **커버링** – 조회에 필요한 컬럼이 전부 인덱스 안에 있으면 테이블 본체를 읽지 않아도 된다. 인덱스를 넓게 잡는 최적화의 근거다.

어떤 인덱스를 쓸지는 옵티마이저가 통계를 보고 정한다. 통계가 실제 분포와 어긋나면 계획이 어긋난다. "어제까지 빠르던 쿼리가 오늘 느려지는" 현상 상당수가 여기서 나온다.

## 2. 격리 수준이 허용하기로 한 것

트랜잭션이 동시에 돌면 서로의 중간 상태가 보일 수 있다. 이상 현상은 종류가 정해져 있다.

- **dirty read** – 아직 커밋되지 않은 값을 읽는다.
- **non-repeatable read** – 같은 행을 두 번 읽었는데 값이 다르다.
- **phantom** – 같은 조건으로 두 번 조회했는데 행의 개수가 다르다.

격리 수준은 이 중 무엇을 막을지의 단계다.

| 수준 | dirty | non-repeatable | phantom |
|---|---|---|---|
| READ UNCOMMITTED | 허용 | 허용 | 허용 |
| READ COMMITTED | 차단 | 허용 | 허용 |
| REPEATABLE READ | 차단 | 차단 | 구현마다 다름 |
| SERIALIZABLE | 차단 | 차단 | 차단 |

기본값이 최고 수준이 아닌 이유는 비용 때문이다. 격리를 높이면 잠금 범위가 넓어지거나 스냅샷 유지 부담이 커지고, 충돌로 인한 재시도가 늘어난다. 현대 데이터베이스 대부분은 MVCC를 써서 읽기가 쓰기를 막지 않게 하지만, 그 대신 **같은 시점의 스냅샷을 유지하는 비용**을 낸다.

### 격리 수준으로는 막히지 않는 것

여기가 12편의 레이스 조건과 만나는 지점이다. 다음 패턴은 격리 수준을 올려도 애플리케이션 로직 차원에서 그대로 깨진다.

```sql
-- T1                          -- T2
SELECT balance FROM acct ...   SELECT balance FROM acct ...   -- 둘 다 1000을 읽음
-- 애플리케이션에서 1000-100 계산
UPDATE acct SET balance = 900  UPDATE acct SET balance = 900  -- 결과: 100만 빠짐
```

**lost update**다. 각 트랜잭션은 자기 관점에서 완전히 정상이다. 해법은 읽기와 쓰기 사이의 창을 데이터베이스 쪽에서 닫는 것이다.

```sql
-- ① 읽고-고치고-쓰기를 한 문장으로 합친다 (원자적 갱신)
UPDATE acct SET balance = balance - 100 WHERE id = ? AND balance >= 100;

-- ② 읽을 때 잠근다
SELECT balance FROM acct WHERE id = ? FOR UPDATE;
```

또는 버전 컬럼을 두고 `WHERE version = ?`로 갱신해 실패하면 재시도하는 낙관적 잠금을 쓴다. 3편의 single-packet attack이 노리는 것이 정확히 이 창이다.

## 3. 캐시 계층이 따로 지는 비용

**Redis**는 키-값 저장소라기보다 자료구조 서버에 가깝다. 리스트, 집합, 정렬된 집합, 해시를 원자적으로 조작할 수 있어서 레이트 리밋, 큐, 세션 저장소, 분산 잠금에 쓰인다. 명령이 단일 스레드로 처리되므로 각 명령이 원자적이라는 성질이 이런 용도의 근거다. 같은 이유로 오래 걸리는 명령 하나가 전체를 멈춘다. 큰 키에 대한 `KEYS` 같은 명령을 운영 환경에서 금기시하는 이유다.

캐시를 도입하면 정합성 문제가 따라온다. 원본이 바뀌었는데 캐시가 남아 있으면 오래된 값이 나가고, 특히 **인가 결과를 캐시**하면 권한이 취소된 사용자가 계속 접근하는 상황이 생긴다. 캐시 키에 사용자 식별자가 빠지면 다른 사용자의 응답이 배달된다. 6편에서 본 웹 캐시 문제와 정확히 같은 형태가 애플리케이션 계층에서 반복된다.

## 4. 구문과 데이터의 분리가 막는 범위

SQL 인젝션의 원인은 문자열 결합 자체가 아니라, **구문(코드)과 데이터가 같은 문자열로 섞여 파서에 도달하는 것**이다. 준비된 구문은 구문을 먼저 파서에 보내 실행 계획을 확정한 뒤, 값을 별도 채널로 전달한다. 값이 무엇이든 이미 확정된 구문 구조를 바꿀 수 없다.

이 원리에서 한계도 따라 나온다. 파라미터로 바인딩할 수 있는 것은 **값**뿐이다.

```sql
-- 안전: 값은 파라미터로 간다
SELECT * FROM posts WHERE author = ?

-- 파라미터로 표현할 수 없는 자리
SELECT * FROM posts ORDER BY <컬럼명> <방향>
SELECT * FROM <테이블명> ...
```

정렬 컬럼, 정렬 방향, 테이블·컬럼 이름은 구문의 일부라 파라미터가 될 수 없다. 이 자리에 사용자 입력이 들어가면 준비된 구문을 써도 인젝션이 성립한다. 유일한 방어는 **허용 목록**이다. 입력값을 미리 정의된 컬럼 이름 집합에 매핑하고, 목록에 없으면 거부한다.

### 문서형 NoSQL의 연산자 주입

**문서형 NoSQL**에서는 인젝션의 모양이 달라진다. 쿼리가 문자열이 아니라 구조화된 객체이므로 구문을 깨는 방식이 아니라 **연산자를 주입**한다.

```js
// 의도: { username: "admin", password: "입력값" }
// 입력이 객체로 파싱되면: { username: "admin", password: { "$ne": null } }
```

값이 올 자리에 연산자 객체가 들어가 조건의 의미가 바뀐다. 방어는 타입 검증이다. 문자열이어야 하는 자리에 객체가 오면 거부한다.

### ORM이 가리는 쿼리

ORM은 테이블을 객체로 매핑하고, 객체 조작을 SQL로 번역하고, 같은 행에 대한 객체를 한 번만 만들도록 관리한다. 얻는 것은 반복 코드의 제거다. 대가는 **생성되는 쿼리가 보이지 않는 것**이다.

- **N+1** – 목록 100건을 가져온 뒤 각 항목의 연관 객체를 접근하면 쿼리가 101번 나간다. 코드에는 반복문 하나로 보인다. 로그를 켜 보기 전에는 드러나지 않는다.
- **의도치 않은 전체 로드** – 지연 로딩 설정 하나로 거대한 연관 테이블이 통째로 메모리에 올라온다.
- **필터 조건이 사용자 입력으로 조립되는 경우** – ORM의 필터 API에 키와 연산자를 사용자 입력으로 넘기면, SQL 문자열을 안 만들었는데도 조회 조건이 조작된다. 값은 파라미터로 안전하게 바인딩되지만 **어떤 컬럼을 어떤 연산자로 비교할지**가 조작되는 형태다.

## 5. 이 계층에서 취약점이 사는 자리

```
구문과 데이터의 분리 실패        → SQL 인젝션
파라미터화할 수 없는 자리        → 정렬·식별자 인젝션 (허용 목록만이 방어)
값 자리에 연산자가 들어감        → NoSQL 인젝션
읽기와 쓰기 사이의 시간          → lost update, 레이스 조건
인가 결과와 캐시 키의 불일치     → 다른 사용자 데이터 노출
응답 시간·에러 메시지의 차이     → blind / time-based 추출
```

마지막 줄이 이 계층의 특징이다. 데이터를 직접 읽지 못해도 **인덱스를 쓰는 쿼리와 풀스캔하는 쿼리의 시간 차이**가 관측되면 그것만으로 값을 한 비트씩 복원할 수 있다. 성능 특성이 그대로 정보 채널이 된다는 점에서, 5편의 패딩 오라클이나 7편의 HPACK 이야기와 같은 계열이다.

이 형태가 15편에서 원형 D – 부수 효과 관측으로 정리된다.
