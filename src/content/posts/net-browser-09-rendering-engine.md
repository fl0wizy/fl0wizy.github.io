8편이 이름 붙여 넘긴 **렌더러 안쪽**을 이 편은 단계의 구분으로 연다. 바이트열이 화면이 되기까지를 몇 개의 단계로 쪼개고, 그 사이에 자바스크립트와 엔진을 앉힌 구조가 이 계층의 장치다. **이 계층을 빠르게 만든 장치는 전부 무언가를 건너뛰거나 가정한다.**

엔진 내부의 중간 표현이나 최적화 로직, 거기서 나오는 취약점 유형은 이 편의 범위가 아니다. 여기서는 **엔진이 어디에 있고, 왜 그런 것이 필요했고, 지금 어디에 쓰이는지**까지만 본다.

## 1. 바이트에서 픽셀까지

Chromium의 렌더링 구조(RenderingNG)는 파이프라인을 여러 단계로 나눈다. 실무에서 의미 있는 단위로 묶으면 이렇다.

1. **파싱** – HTML 바이트열을 토큰화하고 DOM 트리를 만든다.
2. **스타일** – CSS를 파싱해 CSSOM을 만들고, 캐스케이드 알고리즘으로 각 DOM 노드의 최종 스타일 값을 계산한다.
3. **레이아웃** – 계산된 스타일로 각 박스의 위치와 크기를 정한다. 문서 전체의 기하 구조가 여기서 결정된다.
4. **페인트** – 무엇을 어떤 순서로 그릴지의 **명령 목록**을 만든다. 실제로 픽셀을 칠하지는 않는다.
5. **합성 · 래스터 · 출력** – 명령 목록을 레이어와 타일로 나누고, GPU 쪽에서 픽셀로 만들고, 프레임을 화면에 제출한다.

단계를 이렇게 잘게 나눈 이유는 순서를 명확히 하려는 것만이 아니다. **필요 없는 단계를 건너뛰기 위해서**다. Chromium 문서는 시각 효과 애니메이션과 스크롤이 레이아웃·프리페인트·페인트를 건너뛸 수 있다고 명시한다.

이것이 프런트엔드 성능 조언의 근거다. `transform`과 `opacity`로 만든 애니메이션은 이미 만들어진 레이어를 다시 배치하기만 하므로 합성 단계만 다시 돈다. 같은 움직임을 `top`/`left`로 만들면 박스의 기하가 바뀌므로 매 프레임 레이아웃부터 전부 다시 계산된다. "이 속성이 빠르다"는 경험칙이 아니라 파이프라인의 어느 지점부터 다시 도는지의 차이다.

## 2. 자바스크립트가 끼어드는 지점

### 파싱 중단

HTML 파서가 `<script>`를 만나면 파싱을 멈춘다. 스크립트가 `document.write`로 문서를 바꿀 수 있기 때문에, 스크립트 실행이 끝나기 전에는 다음 바이트를 어떻게 해석해야 할지 확정할 수 없다.

```html
<script src="a.js"></script>   <!-- 파싱 중단 → 내려받기 → 실행 → 재개 -->
<script src="a.js" defer></script>  <!-- 파싱 계속 → 문서 완성 후 순서대로 실행 -->
<script src="a.js" async></script>  <!-- 파싱 계속 → 도착하는 대로 즉시 실행 -->
```

브라우저는 이 중단 비용을 줄이려고 **프리로드 스캐너**를 함께 돌린다. 파싱이 멈춰 있는 동안에도 앞쪽 바이트를 미리 훑어 필요한 자원의 다운로드를 시작한다. 파서는 멈췄지만 네트워크는 멈추지 않게 하는 장치다.

### 이벤트 루프의 순서

한 프레임 안에서 코드가 실행되는 순서는 정해져 있다.

```
태스크 하나 실행 (이벤트 핸들러, setTimeout 콜백 …)
  → 마이크로태스크 큐를 전부 비움 (Promise 콜백, queueMicrotask)
  → 렌더링 기회 (필요하면 requestAnimationFrame 콜백 → 스타일 → 레이아웃 → …)
  → 다음 태스크
```

`setTimeout(fn, 0)`과 `Promise.resolve().then(fn)`의 차이가 여기서 나온다. 전자는 **다음 태스크**로 밀리므로 그 사이에 렌더링이 일어날 수 있다. 후자는 현재 태스크가 끝난 직후 렌더링 전에 반드시 실행된다. 마이크로태스크에서 다시 마이크로태스크를 큐에 넣는 코드를 쓰면 큐가 비지 않아 렌더링 기회가 영원히 오지 않는다.

### 강제 동기 레이아웃

레이아웃은 보통 프레임 끝에 한 번 돈다. 그런데 자바스크립트가 `offsetHeight`, `getBoundingClientRect()` 같은 기하 값을 읽으면, 브라우저는 정확한 값을 주기 위해 **그 자리에서 레이아웃을 실행**해야 한다.

```js
for (const el of items) {
  el.style.width = el.offsetWidth + 10 + 'px';  // 쓰기 → 읽기 → 쓰기 → 읽기 …
}
```

쓰기는 앞 절에서 본 무효화를 일으키고, 읽기가 그 재계산을 즉시 강제한다. 반복문 안에서 이 둘이 교대하면 레이아웃이 항목 수만큼 돈다. 읽기를 전부 먼저 하고 쓰기를 몰아서 하면 한 번으로 끝난다. 프레임워크들이 DOM 업데이트를 일괄 처리하는 이유가 이것이다.

## 3. 엔진의 담당 범위

파이프라인 그림에서 자바스크립트 엔진의 위치를 정확히 잡으려면, 엔진이 제공하는 것과 제공하지 않는 것을 나눠야 한다.

| 엔진(V8, SpiderMonkey, JavaScriptCore)이 제공 | 호스트(브라우저)가 제공 |
|---|---|
| 언어 자체 – 문법, 객체 모델, 프로토타입 | `document`, DOM API |
| 가비지 컬렉션 | `fetch`, `XMLHttpRequest` |
| Promise, 이터레이터 같은 내장 객체 | `setTimeout`, `requestAnimationFrame` |
| 실제 코드 실행 | 쿠키, 스토리지, 권한 |

`document`는 자바스크립트 언어의 일부가 아니다. 브라우저가 엔진에 꽂아 주는 호스트 객체다. 이 분리가 엔진을 브라우저 밖으로 꺼낼 수 있게 만든다. 호스트만 갈아 끼우면 DOM이 없는 환경에서도 같은 언어가 돈다.

## 4. 인터프리터만으로 부족해진 이유

1편에서 본 흐름이 여기로 이어진다. XMLHttpRequest가 1999년에 들어왔고, 2005년에 Ajax라는 이름이 붙었고, 그 뒤 웹페이지가 애플리케이션이 됐다. 문서를 장식하던 스크립트가 애플리케이션 로직 전체를 담게 되자 **자바스크립트 실행 시간 자체가 병목**이 됐다.

### AOT가 불가능한 이유

자바스크립트는 동적 타입이다. 함수 `f(a, b)`의 `a`가 정수인지 문자열인지 객체인지 실행 전에는 알 수 없고, 같은 함수가 호출마다 다른 타입을 받을 수도 있다. C처럼 미리 기계어로 번역해 두려면 모든 경우를 처리하는 코드를 생성해야 하고, 그러면 빨라지지 않는다.

엔진이 택한 구조는 **관찰 후 특화**다.

```
① 인터프리터로 실행하면서 "이 자리에는 어떤 타입이 오는가"를 관찰한다
② 자주 실행되는 함수만 골라, 관찰된 타입을 가정으로 박아 넣고 기계어로 컴파일한다
③ 실행 중 그 가정이 깨지면 컴파일된 코드를 버리고 인터프리터로 되돌린다
```

컴파일에는 시간이 든다. 한 번만 실행될 코드를 컴파일하면 손해다. 그래서 **실행 빈도로 컴파일 비용을 정당화**하는 구조가 된다. 이름이 "Just-In-Time"인 이유이기도 하다.

②에서 박아 넣는 가정이 무엇이고, ③의 되돌리기가 어떤 절차로 일어나며, 그 사이에 어떤 종류의 불일치가 생길 수 있는지는 별도의 주제다. **JIT은 최적화인 동시에 "가정에 기대는 코드"** 라는 사실만 붙잡아 두면, 왜 이 영역이 별도의 취약점 계열을 만들어 내는지 감이 잡힌다. 상세는 엔진을 다루는 다음 시리즈에서 코드 단위로 본다.

### 2008년 세 엔진의 동시 전환

2008년에 세 진영이 거의 동시에 움직인다.

| 시점 | 엔진 | 진영 |
|---|---|---|
| 2008년 9월 2일 | **V8** – Chrome 출시와 같은 날 오픈소스 | Google |
| 2008년 | **TraceMonkey** – 자바스크립트 최초의 JIT 컴파일러 | Mozilla |
| 2008년 | **SquirrelFish Extreme** – JavaScriptCore 계열 | Apple |

V8은 2006년 가을 라스 바크가 합류하면서 시작됐다. 덴마크의 한 농가 별채에서 개발이 진행됐고, 처음부터 기계어 생성을 전제로 설계됐다. Mozilla는 2009년 JaegerMonkey를 추가하며 방식을 보완했다. 이 시기를 흔히 자바스크립트 속도 경쟁이라고 부른다.

## 5. 엔진이 브라우저 밖에서 도는 자리

호스트만 갈아 끼우면 된다는 성질이 실제로 쓰인 자리는 브라우저 밖이다.

- **Node.js** (2009) – V8에 파일 시스템과 소켓을 호스트 객체로 붙였다. 서버에서 자바스크립트를 쓰게 된 출발점이다.
- **Electron** – Chromium과 Node를 함께 묶어 데스크톱 앱을 만든다.
- **Deno · Bun** – 각각 V8과 JavaScriptCore 위에 다른 호스트 API를 얹었다.
- **엣지 런타임** – 요청마다 격리된 실행 환경을 빠르게 만들어야 하는 곳에서, 프로세스 대신 엔진의 격리 단위를 쓴다.
- **확장 스크립트** – 프록시·데이터베이스·에디터가 사용자 스크립트를 돌리는 데 엔진을 임베드한다.

**자바스크립트 엔진은 브라우저의 부품에서 범용 실행 런타임이 됐다.** 이것이 엔진을 공부할 가치가 브라우저 하나에 한정되지 않는 이유다.

## 6. 이 계층에서 취약점이 사는 자리

렌더링 파이프라인 자체에서 나오는 결함들은 엔진 메모리 버그와는 다른 계열이다. 전부 **같은 문서를 두 번 해석하거나, 렌더링의 부수 효과가 관측 가능하다는 성질**에서 나온다.

- **mXSS (mutation XSS)** – 살균기가 안전하다고 판정한 마크업이, 브라우저가 DOM에 넣고 다시 직렬화·재파싱하는 과정에서 다른 구조로 변한다. 살균기의 파서와 브라우저의 파서가 같은 문자열을 다르게 읽는 문제이므로, 6편의 파서 불일치와 정확히 같은 형태다.
- **DOM clobbering** – HTML 요소의 `id`·`name`이 전역 객체의 속성이 되는 오래된 동작을 이용해, 스크립트 없이 마크업만으로 자바스크립트 변수를 덮어쓴다.
- **CSS injection** – 스크립트를 넣지 못해도 스타일만 넣을 수 있으면, 속성 선택자와 배경 이미지 요청을 조합해 페이지 안의 값을 한 글자씩 외부로 흘릴 수 있다.
- **XS-Leaks** – 렌더링에 걸리는 시간, 프레임 개수, 스크롤 위치 같은 관측 가능한 부수 효과로 다른 출처의 상태를 추정한다. 데이터를 직접 읽지 않고 **반응의 차이**만으로 정보를 얻는 형태다.

이 계층에서 취약점이 사는 자리는 파이프라인이 남기는 관측 가능한 차이다. 읽지 못하게 막아도 반응의 차이는 남는다는 이 형태가 15편의 원형 D(부수 효과 관측)다.
