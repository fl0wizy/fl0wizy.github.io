이 글에서는 프런트엔드의 변화를 하나의 축으로 정리한다. 프레임워크 이름을 나열하는 대신 **HTML을 누가 언제 어디서 만드는가**라는 질문 하나로 보면, 각 단계가 앞 단계의 어떤 문제를 풀려는 시도였고 그 대가로 무엇을 새로 떠안았는지가 드러난다.

## 1. 네 단계

### ① 서버 템플릿

요청이 오면 서버가 데이터를 조회해 완성된 HTML을 만들어 내려보낸다. 사용자가 무언가를 클릭하면 새 요청이 가고 페이지 전체가 다시 그려진다.

단순하고, 검색엔진이 잘 읽고, 첫 화면이 빠르다. 한계는 명확하다. 화면 일부만 바꾸는 것이 불가능하므로 데스크톱 애플리케이션 같은 조작감을 만들 수 없다.

### ② Ajax 부분 갱신

1편에서 본 XMLHttpRequest가 이 단계를 연다. 페이지 전체가 아니라 데이터만 받아 DOM의 일부를 고친다. jQuery 시대의 코드는 대개 명령형이다. "이 요소를 찾아서, 이 속성을 바꾸고, 저기에 붙인다."

새로고침 없는 상호작용을 얻었고, 상태를 잃었다. 정확히는 **상태가 DOM 여기저기에 흩어진다.** 어떤 버튼이 활성화돼 있는지, 목록이 어떤 필터로 정렬돼 있는지가 화면 요소의 클래스와 속성에 분산된다. 화면이 복잡해질수록 "지금 상태가 무엇인지"를 코드에서 확인할 수 없게 되고, 두 이벤트 핸들러가 같은 요소를 서로 다르게 고치는 버그가 늘어난다.

### ③ SPA

해법은 방향을 뒤집는 것이었다. DOM을 직접 고치는 대신 **상태를 선언하고, 상태에서 UI를 유도한다.** 서버는 거의 빈 HTML과 JSON API만 제공하고, 브라우저가 화면 전체를 만든다.

상태가 한 곳에 모이면서 복잡한 UI를 다룰 수 있게 됐다. 대가는 여러 개다.

- 첫 화면을 그리려면 자바스크립트 번들을 전부 받아 실행해야 한다.
- 서버가 내려주는 HTML이 비어 있으므로 검색엔진과 링크 미리보기가 내용을 보지 못한다.
- 라우팅, 스크롤 복원, 뒤로 가기, 접근성 포커스 관리를 전부 직접 구현해야 한다. 브라우저가 공짜로 해 주던 것들이다.

### ④ SSR 복귀와 서버 컴포넌트

세 번째 대가가 커지자 다시 서버에서 그리기 시작한다. 다만 ①로 돌아가는 것이 아니라, **서버에서 먼저 그린 뒤 브라우저에서 이어받는** 구조다. React가 서버 컴포넌트를 도입하고 Next.js가 이를 기본 모델로 삼으면서, 상호작용이 필요한 조각만 클라이언트로 보내는 방식이 주류가 됐다.

## 2. 하이드레이션이라는 비용

서버가 만든 HTML은 **보이기만 하고 아직 눌리지 않는다.** 이벤트 핸들러가 붙어 있지 않기 때문이다. 브라우저는 같은 컴포넌트 트리를 한 번 더 만들어 기존 DOM과 맞춰 보고 핸들러를 연결한다. 이 과정이 하이드레이션이다.

```
서버   : 컴포넌트 트리 → HTML 문자열 → 전송
브라우저: HTML 표시 (사용자는 화면을 본다)
         → 번들 다운로드 → 같은 트리를 다시 구성 → 이벤트 연결
         → 이제 눌린다
```

**보이는 시점과 쓸 수 있는 시점이 갈라진다.** 페이지가 그려졌는데 버튼이 반응하지 않는 구간이 생기고, 지표를 하나만 보면 이 간격이 보이지 않는다. 같은 작업을 두 번 한다는 낭비도 있다.

대응은 다시 그릴 범위를 줄이는 방향으로 갔다. HTML을 조각내어 준비되는 대로 흘려보내는 스트리밍, 화면에 보이는 부분부터 처리하는 부분 하이드레이션, 상호작용이 필요한 컴포넌트만 섬처럼 따로 활성화하는 아일랜드 구조가 그것이다. 서버 컴포넌트는 여기서 한 걸음 더 나가 **애초에 클라이언트로 보내지 않는다**는 선택을 한다. 렌더링에만 쓰이고 상호작용이 없는 컴포넌트의 코드는 브라우저에 도달하지 않는다.

## 3. 번들러가 존재하는 이유

프런트엔드 도구 체인이 복잡해 보이는 이유는 그것이 세 가지 다른 문제를 동시에 풀고 있기 때문이다.

- **모듈 시스템의 파편화** — 자바스크립트에는 오랫동안 표준 모듈 시스템이 없었다. 서버 쪽은 CommonJS, 브라우저 쪽은 AMD, 나중에 표준 ESM이 들어왔다. 서로 다른 형식으로 배포된 라이브러리들을 한 페이지에서 쓰려면 누군가 번역해야 한다.
- **요청 수 제한** — 6편에서 본 대로 HTTP/1.1에서는 연결당 응답이 순서대로만 나오고 브라우저는 도메인당 여섯 개쯤만 연결을 연다. 파일이 수백 개면 로딩이 치명적으로 느려진다. 그래서 하나로 합쳤다.
- **전송량 줄이기** — 사용하지 않는 코드 제거, 압축, 코드 분할.

두 번째 이유는 HTTP/2 이후 상당히 약해졌다. 그런데도 번들링이 사라지지 않은 것은 첫 번째와 세 번째가 남아 있기 때문이다. **문제 하나가 해결돼도 같은 도구가 다른 문제 때문에 계속 필요한** 전형적인 경우다.

## 4. 신뢰 경계가 함께 움직인다

렌더링 위치가 바뀌면 **어느 코드가 사용자의 통제 아래 있는가**도 바뀐다. 보안 관점에서 이 편의 핵심은 이 한 줄이다.

### 클라이언트로 옮겨 갈 때

폼 검증, 권한에 따른 메뉴 숨김, 할인 계산이 브라우저에서 돌면 그것은 검증이 아니라 **UI**다. 공격자는 화면을 거치지 않고 API를 직접 호출한다. 개발자 도구를 열면 코드와 상태가 전부 보이고, 조건문 하나를 바꿔 다시 실행할 수도 있다.

이 사실 자체는 오래된 상식인데, SPA 구조에서 실수가 늘어나는 이유는 **화면 로직과 검증 로직이 같은 코드베이스에 있기 때문**이다. 같은 함수를 서버와 클라이언트가 공유하는 구조에서는 어느 쪽이 권위 있는 판정인지가 흐려진다. 서버는 클라이언트가 보낸 모든 것을 처음부터 다시 검증해야 한다는 원칙이 변하지 않는다.

### 서버로 되돌아올 때

서버 컴포넌트에는 반대 방향의 새 실수가 있다. 서버 컴포넌트 안의 값은 서버에만 있을 것 같지만, **클라이언트 컴포넌트에 props로 넘기는 순간 직렬화되어 전송된다.** 데이터베이스 레코드를 통째로 넘기면 내부 식별자와 미공개 필드가 함께 나가고, 설정 객체를 넘기면 그 안의 키가 나간다. 코드상으로는 같은 파일 안의 함수 호출처럼 보이는데 실제로는 네트워크 경계를 넘는다는 점이 이 실수의 원인이다.

### XSS의 자리 이동

프레임워크는 기본적으로 문자열을 이스케이프한다. 그래서 고전적인 템플릿 XSS는 크게 줄었다. 대신 이스케이프를 **명시적으로 끄는 API**가 남는다.

```jsx
<div dangerouslySetInnerHTML={{ __html: userContent }} />
```

이름에 경고가 들어 있는 것이 설계 의도다. 문제는 서버에서 살균해서 보내니 괜찮다고 판단하는 경우인데, 9편에서 본 mXSS가 정확히 그 가정을 깬다. 살균기의 파서와 브라우저의 파서가 같은 문자열을 다르게 읽는다.

클라이언트 상태 객체를 병합하고 복사하는 코드가 늘면서 **프로토타입 오염**이 실제 공격 경로가 된 것도 이 시기의 변화다. 설정 객체를 깊게 병합하는 유틸리티에 `__proto__` 키가 섞여 들어가면 전역적으로 객체의 기본 속성이 오염되고, 그 값을 읽는 다른 코드가 가젯이 된다.

## 5. 정리

```
① 서버 템플릿   상태 없음, 상호작용 없음
② Ajax          상호작용 얻고 상태 잃음
③ SPA           상태 얻고 첫 화면·SEO·브라우저 기본기 잃음
④ SSR/RSC       첫 화면 회복, 대신 서버/클라 경계가 코드 안으로 들어옴

관통하는 것: 렌더링 위치가 이동할 때마다 신뢰 경계도 같이 이동한다
```

이 시리즈에서 만드는 대상인 hack-tree는 ④에 해당한다. Next.js의 App Router 위에서 대부분의 화면을 서버에서 그리고, 검색 팔레트와 그래프 뷰처럼 상호작용이 필요한 부분만 클라이언트 컴포넌트로 둔다. 16편에서 그 선택의 실제 결과를 다룬다.
