9편이 이름 붙여 넘긴 결손은 출처 사이의 경계다. 이 편은 그 경계를 출처(origin)라는 단위로 세우고, 그 위에 얹힌 헤더와 쿠키 속성으로 경계를 지킨다. 이 계층은 하나의 일관된 원칙에서 연역된 설계가 아니라 **사고가 터질 때마다 하나씩 덧붙은 지층**이다.

## 1. 출처 – 셋으로 갈라진 보안 단위

출처는 **스킴 + 호스트 + 포트**의 조합이다. 셋 중 하나라도 다르면 다른 출처다.

```
기준: https://example.com/app

https://example.com/other      같은 출처
http://example.com             다름 – 스킴
https://api.example.com        다름 – 호스트
https://example.com:8443       다름 – 포트
```

문제는 **쿠키가 이 기준을 쓰지 않는다**는 것이다. 쿠키는 6편에서 본 대로 HTTP에 나중에 덧붙은 장치이고, 도메인과 경로로 전송 여부를 판정하며 포트를 무시한다. `https://example.com`과 `http://example.com`은 다른 출처지만 기본적으로 같은 쿠키를 공유한다. 브라우저 보안 모델의 기본 단위가 둘로 갈라져 있고, 이 어긋남이 이 편에 등장하는 문제 다수의 출발점이다.

8편에서 본 Site Isolation의 "사이트"까지 더하면 기준이 셋이다. 출처(스킴+호스트+포트), 사이트(스킴+등록가능도메인), 쿠키의 도메인+경로가 각각 다른 범위를 가리킨다. 어떤 방어가 어느 기준으로 동작하는지를 확인하지 않으면 실제 경계를 잘못 잡게 된다.

## 2. 동일 출처 정책 – 읽기 금지와 보내기 허용

동일 출처 정책(SOP)의 핵심은 비대칭이다.

**막는 것 – 읽기**
- 다른 출처 문서의 DOM 접근
- 다른 출처로 보낸 요청의 응답 본문 읽기
- 다른 출처의 쿠키를 스크립트로 읽기

**막지 않는 것 – 보내기와 임베딩**
- `<img src>`, `<script src>`, `<link>`, `<form>`으로 다른 출처에 요청 보내기
- 그 요청에 **해당 사이트의 쿠키가 붙는 것**
- 다른 출처 페이지를 `iframe`으로 넣기

응답을 읽지 못해도 **요청은 이미 서버에 도착해 처리된 뒤**다. 계좌 이체가 폼 전송 하나로 끝나는 서버라면, 공격자 페이지에 숨긴 폼이 피해자의 쿠키와 함께 그 요청을 보낼 수 있다. 이것이 CSRF이고, **구현 실수가 아니라 SOP 설계의 직접적 귀결**이다. 웹이 처음부터 "다른 사이트의 이미지를 가져다 쓸 수 있는" 매체로 설계됐기 때문에 보내기를 막을 수 없었다.

읽지 않고 알아내는 경로도 같은 틈에 있다. 이미지 로드 성공 여부, 프레임 개수, 응답 시간 차이로 다른 출처의 상태를 추정하는 XS-Leaks 계열이 그것이다.

## 3. 사고마다 덧붙은 방어들

### CORS – 읽기 금지를 풀어 주는 장치

SOP가 응답 읽기를 막으면 정당한 교차 출처 API 호출도 막힌다. CORS는 이를 **서버가 허가를 표명하는 방식**으로 푼다. 브라우저가 `Origin` 헤더로 요청 출처를 알리고, 서버가 `Access-Control-Allow-Origin`으로 허용 여부를 답한다. 부작용이 있을 수 있는 요청(커스텀 헤더, `PUT`/`DELETE` 등)은 먼저 `OPTIONS` 프리플라이트로 허가를 묻는다.

판단 주체가 서버라는 점이 실패 지점을 만든다. 전형적인 실수는 두 가지다.

```http
# 요청의 Origin 을 그대로 반사 + 자격증명 허용
Access-Control-Allow-Origin: https://attacker.example
Access-Control-Allow-Credentials: true
```

이 조합은 사실상 모든 사이트에 인증된 응답을 읽을 권한을 주는 것과 같다. `null` 출처를 신뢰하는 설정도 마찬가지다. 샌드박스된 iframe이나 일부 리다이렉트 상황에서 출처가 `null`이 되므로, 공격자가 그 상태를 만들 수 있다.

### CSP – XSS가 없어지지 않는다는 전제

CSP는 발상이 다르다. XSS를 막는 것이 아니라 **XSS가 성공했을 때 할 수 있는 일을 줄인다.** 실행 가능한 스크립트의 출처를 제한하고, 인라인 스크립트를 기본 차단하며, nonce나 해시가 붙은 것만 허용한다.

우회는 대개 CSP 자체를 깨지 않고 **허용 목록 안에서** 이뤄진다.

- 허용된 도메인에 JSONP 엔드포인트가 있으면, 콜백 파라미터로 임의 코드를 실행할 수 있다.
- 허용된 CDN의 인기 라이브러리에 가젯(문자열을 코드로 평가하는 경로)이 있으면 그것을 쓴다.
- `base-uri`를 지정하지 않으면 공격자가 `<base>` 태그로 상대 경로 스크립트의 출처를 바꿀 수 있다.

`strict-dynamic`과 nonce 기반 정책이 권장되는 이유가 이것이다. 도메인 목록으로 신뢰를 표현하면 그 도메인 전체를 신뢰하게 되지만, nonce는 개별 스크립트 단위로 신뢰를 표현한다.

### frame-ancestors – 클릭재킹

투명하게 만든 iframe을 사용자의 클릭 위치에 겹쳐 두면, 사용자는 자기가 누른다고 믿는 것과 다른 것을 누른다. `X-Frame-Options`가 먼저 나왔고, 지금은 CSP의 `frame-ancestors`가 같은 일을 더 정밀하게 한다.

### 쿠키 속성 – 뒤늦은 보정

쿠키가 출처 기준이 아니라는 사실을 하나씩 메워 온 흔적이 속성 목록이다.

| 속성 | 대응하는 문제 |
|---|---|
| `Secure` | 평문 HTTP로 쿠키가 새는 것 |
| `HttpOnly` | XSS로 스크립트가 쿠키를 읽는 것 |
| `SameSite` | 다른 사이트에서 출발한 요청에 쿠키가 붙는 것 (CSRF) |
| `__Host-` 접두사 | 서브도메인이 상위 도메인 쿠키를 덮어쓰는 것 |

`SameSite=Lax`가 대부분의 브라우저에서 기본값이 되면서 CSRF의 기본 난이도가 크게 올라갔다. 다만 `Lax`는 **최상위 내비게이션의 GET 요청에는 쿠키를 붙인다.** 상태를 변경하는 동작이 GET으로 열려 있으면 여전히 성립한다. 기본값이 생겼다고 CSRF 토큰을 걷어 내는 것이 위험한 이유다.

### COOP · COEP · CORP – Spectre 이후

프로세스 안에서 메모리 경계가 무너진다는 전제는 8편 §3이 세웠다. 이 편에서 새로 생기는 것은 그 전제를 문서 쪽에서 떠안게 하는 헤더들이고, 그것들은 **다른 출처의 자원을 같은 프로세스·같은 브라우징 컨텍스트 그룹에 두지 않겠다는 선언**이다.

이 선언에는 보상이 따른다. 고정밀 타이머와 `SharedArrayBuffer` 같은 기능은 격리를 선언한 문서에서만 열린다. 강력한 기능을 쓰려면 먼저 격리를 증명하라는 구조이고, 기능 제공과 보안 요구를 묶은 설계 사례다.

## 4. 캐시와 스토리지의 상태 분할

같은 브라우저를 쓰는 한 캐시와 스토리지는 사이트 사이에서 공유될 수 있고, 그 공유가 정보 유출 경로가 된다. 어떤 자원이 캐시에 있는지를 로딩 시간으로 알아내면 사용자가 어디를 방문했는지 추정할 수 있다. 대응으로 브라우저들은 캐시와 스토리지의 키에 **"어느 사이트 안에서 쓰이는가"** 를 포함시켰다. 같은 이미지라도 최상위 사이트가 다르면 다른 캐시 항목이 된다.

## 5. 서드파티 쿠키 폐지의 철회 연표

쿠키 쪽에서는 계획이 한 번 뒤집혔다. 타임라인은 이렇다.

| 시점 | 내용 |
|---|---|
| 2020년 1월 | Chrome, 서드파티 쿠키 단계적 폐지 계획 발표 |
| 2024년 7월 22일 | 폐지하지 않기로 방향 전환 |
| 2025년 4월 22일 | 별도의 사용자 선택 프롬프트도 추가하지 않기로 결정 |
| 2025년 10월 17일 | Privacy Sandbox 기술 상당수 은퇴, 채택률 저조가 이유로 제시됨 |

남은 것 중 하나가 **CHIPS**, 즉 서드파티 쿠키를 최상위 사이트별로 분할해 저장하는 방식이다. 쿠키를 없애는 대신 파티션을 나누는 쪽으로 정리된 셈이다. Safari·Firefox·Brave는 여전히 서드파티 쿠키를 차단하므로, **브라우저마다 기본 상태가 다른 구간**이 당분간 지속된다.

기술적 타당성만으로 웹 플랫폼의 변화가 결정되지 않는다는 사례로 읽어 둘 만하다. 광고 생태계의 의존도와 규제 당국의 검토가 함께 작용한 결과이고, 표준 기구가 강제력을 갖지 않는다는 1편의 구조가 여기서도 작동한다.

## 6. 이 계층에서 취약점이 사는 자리

**이 계층의 방어는 하나의 원칙에서 연역된 것이 아니라 사고 하나에 하나씩 대응해 쌓인 지층이고, 취약점은 그 지층 사이의 틈에 산다.**

```
읽기만 막고 보내기는 열어 둔 비대칭    → CSRF, 그리고 SameSite라는 뒤늦은 보정
출처·사이트·쿠키로 갈라진 세 기준      → 방어가 잡는 경계와 실제 경계의 어긋남
허가 판정을 서버에 맡긴 CORS           → Origin 반사 설정, null 출처 신뢰
도메인 단위로 표현한 CSP의 신뢰        → 허용 목록 안의 JSONP·가젯 우회
사이트를 가로질러 공유된 상태와 화면   → 로딩 시간으로 새는 방문 이력, 겹쳐 둔 iframe으로 가로채는 클릭
```

CORS 오설정처럼 허가를 잘못 표명한 자리는 15편의 원형 C(권한 확인 누락)에, 기준이 셋으로 갈라진 자리와 그 위에 서는 CSRF는 원형 B(정체성 불일치)에 앉는다.

### Part II 요약

브라우저 편 세 개를 하나로 묶으면 이렇다.

```
08편  소프트웨어 검사로는 부족하다 → 프로세스 경계를 보안 경계로
09편  문서를 여러 번 해석하고, 그 부수 효과가 관측된다
10편  읽기는 막혔지만 보내기는 열려 있고, 기준이 셋으로 갈라져 있다
```

이 세 문장이 클라이언트 사이드 취약점 목록 대부분의 좌표다. 개별 항목 – 프로토타입 오염, DOM clobbering, postMessage 출처 미검증, 서비스 워커 남용 – 을 만날 때 어느 문장에 속하는지를 먼저 잡으면 정리가 빠르다.

브라우저가 긋는 경계는 문서가 도착한 뒤에야 그어진다. 그 HTML을 누가 어디서 만들었는지를 출처 기준은 묻지 않고, 이 파트가 풀지 못한 채 남긴 결손이 그것이다.
