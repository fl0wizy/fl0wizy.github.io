## 1. 계층이 남긴 빚

먼저 Part I부터 III까지의 결론을 한 줄씩 다시 세운다.

```
IP        순서·도착·중복없음·일정한 지연을 포기한다           (02편)
TCP       앞의 셋을 복구하지만 메시지 경계는 주지 않는다       (03편)
DNS       이름을 주소로 바꾸되, 답은 시간에 따라 달라진다      (04편)
TLS       상대를 확인하지만 경로 중간에서 끝난다              (05편)
HTTP/1.1  경계를 스스로 만들되 방법이 셋이다                  (06편)
HTTP/2,3  경계를 명확히 하고 막힘을 아래로 내린다             (07편)
브라우저   프로세스를 경계로 삼고, 읽기만 막는다               (08·10편)
프런트엔드 렌더링 위치를 옮기며 신뢰 경계도 함께 옮긴다        (11편)
백엔드     상태를 어디 두느냐로 버그의 종류가 정해진다         (12편)
DB        구문과 데이터를 분리하고, 동시성은 합의로 다룬다      (13편)
인프라     헤더를 사실로 받아들이는 지점을 만든다              (14편)
```

각 줄의 뒷부분이 빚이다. **어떤 계층이 주지 않는 것을 위 계층이 스스로 만들어야 하고, 그 자리에서 취약점이 나온다.** 이 사슬을 형태별로 접으면 다섯 개가 남는다.

## 2. 다섯 개의 원형

### A. 경계 불일치

같은 바이트열을 두 해석기가 다르게 읽는다. 어디까지가 하나의 메시지인지, 하나의 값인지에 대해 답이 갈린다.

- 요청 스머글링 (`Content-Length` vs `Transfer-Encoding`)
- 웹 캐시 포이즈닝·디셉션 (캐시 키와 실제 응답 결정 입력의 불일치)
- 리버스 프록시 경로 정규화 우회 (`..%2f`를 프록시와 앱이 다르게 푼다)
- mXSS (살균기의 파서와 브라우저의 파서)
- 유니코드 정규화 차이, 이메일·URL 파서 차이

1편에서 본 구조가 이 원형의 뿌리다. 중앙 통제가 없으므로 구현체가 조직마다 따로 있고, 해석 차이를 강제로 조정할 주체가 없다.

**방어의 형태는 해석기를 줄이거나 모호함을 거부하는 것이다.** 2025년 연구가 "업스트림을 HTTP/2로 바꾸라"고 말한 것이 전자이고, RFC 9112가 "두 헤더가 함께 오면 오류로 다루고 연결을 닫으라"고 한 것이 후자다.

### B. 정체성 불일치

접근을 결정하는 기준과 실제로 동작하는 기준이 다르다.

| 결정하는 기준 | 실제로 동작하는 기준 | 결과 |
|---|---|---|
| 쿠키의 도메인+경로 | SOP의 출처 | CSRF |
| 이름(origin 문자열) | 주소(소켓 연결) | DNS rebinding |
| 소켓의 출발지 IP | 헤더에 적힌 IP | XFF 위조, IP 기반 통제 우회 |
| 서버가 고정한 검증 키 | 토큰이 지시하는 키(`kid`, `jku`) | JWT 위조 |
| 허용 목록의 이름 | 그 이름의 현재 소유자 | 서브도메인 탈취 |

10편에서 본 대로 브라우저 안에만도 기준이 셋(출처·사이트·쿠키 도메인)이다. 어떤 방어가 어느 기준으로 동작하는지 확인하지 않으면 실제 경계를 잘못 잡는다.

**방어의 형태는 판정 기준을 하나로 고정하고, 그 기준을 입력이 바꾸지 못하게 하는 것이다.**

### C. 권한 확인 누락

가장 단순하고 가장 흔하다. 구조적 이유가 있다. **인증은 한 번, 인가는 매번**이기 때문이다.

로그인 여부 확인은 미들웨어 한 곳에서 끝나지만, "이 객체가 이 사용자의 것인가"는 핸들러마다 따로 써야 한다. 엔드포인트가 200개면 200번 써야 하고, 한 곳만 빠뜨리면 뚫린다. 잊을 수 있는 자리가 많은 구조에서는 결국 잊는다.

**방어의 형태는 잊을 수 있는 자리 자체를 없애는 것이다.** 인가를 데이터 접근 계층으로 내려 기본값을 거부로 만들고, 소유자 조건이 붙지 않은 조회는 애초에 불가능하게 한다. 각 핸들러가 기억해야 하는 구조에서 벗어나야 한다.

### D. 부수 효과 관측

데이터 자체는 차단돼 있지만 반응의 차이가 남는다. 이 시리즈에서 반복해 등장한 형태다.

- 5편 – 패딩 오라클: 복호화 실패의 **사유** 차이
- 7편 – CRIME: 압축된 **길이** 차이
- 9편 – XS-Leaks: 렌더 시간과 프레임 수
- 8편 – Spectre: 캐시 상태를 통한 메모리 내용
- 13편 – blind SQLi: 응답 시간 차이

2020년대 연구의 중심축이 이쪽으로 옮겨 왔다는 점이 중요하다. 사이드채널이 보조 수단이 아니라 **1차 공격 프리미티브**로 쓰인다. 리다이렉트 동작의 차이만으로 blind SSRF를 증폭하는 기법이 그 예다.

**방어의 형태는 응답을 같게 만들거나 관측 자체를 막는 것이다.** 상수 시간 비교와 통일된 오류 메시지가 전자, 프로세스 격리와 타이머 정밀도 하향이 후자다.

### E. 자원 비대칭

취약한 코드가 없어도 성립한다. 규격이 허용하는 정상 동작의 조합이 **보내는 비용과 처리하는 비용의 기울기**를 만든다.

7편의 Rapid Reset이 전형이다. 프레임 두 개를 보내는 비용으로 서버의 요청 처리 한 사이클을 소비시켰고, 동시 스트림 상한은 우회됐다. 정규식의 파국적 백트래킹(ReDoS), GraphQL의 중첩과 별칭 남용, XML 폭탄, 압축 폭탄이 같은 계열이다.

**방어의 형태는 처리 비용에 상한을 두고, 비용이 큰 동작에 대해 요청자에게도 비용을 청구하는 것이다.**

## 3. 웹해킹 트리를 이 좌표에 얹기

분류 트리의 각 섹션이 어느 원형에 속하는지를 붙이면, 항목이 백 개가 넘어도 지형이 다섯 칸으로 정리된다.

| 트리 섹션 | 주 원형 | 관련 편 |
|---|---|---|
| Injection (SQL, 명령, SSTI, XXE) | C + A | 13, 12 |
| SSRF | B (+ 2편의 주소 구조) | 02, 04, 12 |
| XSS · CSRF · 클릭재킹 | B (+ A: mXSS) | 10, 09 |
| 인증 / 세션 | B | 12 |
| 접근 제어 (IDOR·BOLA) | C | 12 |
| 파일 처리 · 경로 탈출 | A (경로 해석 차이) | 13, 14 |
| 역직렬화 | C (구문과 데이터의 미분리) | 12 |
| HTTP 프로토콜 계층 (desync·캐시) | A | 06, 07 |
| 비즈니스 로직 · 레이스 | C + E | 03, 13 |
| API 보안 (GraphQL 포함) | C + E | 12 |
| 클라이언트 사이드 (프로토타입 오염·DOM clobbering) | B + C | 09, 11 |
| 인프라 인접 (서브도메인 탈취·공급망) | B | 04, 14 |
| 암호 관련 결함 | D | 05 |
| 사이드채널 · XS-Leaks | D | 07, 08, 09 |

두 원형이 함께 적힌 칸이 있는 이유는 실제 공격이 대개 체인이기 때문이다. SSRF로 내부에 도달하고(B), 내부 서비스의 인가 누락을 쓴다(C). 이 결합 방식을 보는 것이 개별 항목을 외우는 것보다 오래 간다.

## 4. 새 기법을 만났을 때

매년 새 기법이 나온다. 이름과 세부는 계속 바뀌지만, 앞의 다섯 칸은 잘 바뀌지 않는다. 그래서 새 연구를 읽을 때 먼저 던지는 질문을 고정해 두면 소화가 빠르다.

1. **누가 무엇을 다르게 해석했는가** – 두 구성요소와, 갈린 대상이 무엇인지.
2. **어떤 두 기준이 갈라졌는가** – 결정하는 기준과 동작하는 기준.
3. **어느 확인이 빠졌는가** – 그리고 왜 빠지기 쉬운 자리인가.
4. **무엇이 관측됐는가** – 차단된 데이터 대신 새어 나온 신호.
5. **누가 비용을 냈는가** – 요청자와 처리자의 비용 비율.

이 다섯 질문에 답이 나오면 그 기법은 이미 아는 형태의 변주이고, 답이 안 나오면 그때가 정말 새로운 것이다. 후자는 드물다.

## 5. 학습 순서에 대해

이 시리즈는 아래에서 위로 올라왔다. 물리 계층에서 시작해 프로토콜, 브라우저, 애플리케이션, 인프라 순이다. 개념의 의존 관계를 따르는 순서이고, 3편의 "경계 없음"을 모르면 6편의 스머글링이 암기가 된다.

실제 학습에서는 여기에 반대 방향을 섞는 편이 낫다. 구체적인 취약점 하나를 재현해 보고, 왜 그것이 가능한지를 아래로 따라 내려가는 순서다. 두 방향이 만나는 지점에서 이해가 붙는다.

다음 편에서는 이 공부를 실제 플랫폼으로 만든 기록을 다룬다. 지금까지 본 계층들이 하나의 배포된 시스템 안에서 어떻게 겹쳐 있는지, 그리고 그 과정에서 내린 결정과 그 대가를 정리한다.
