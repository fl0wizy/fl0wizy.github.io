이 글에서는 앞의 열다섯 편을 실제 시스템으로 만든 기록을 정리한다. 지식 플랫폼 hack-tree는 원래 "보안·CS 개념을 내가 쓸 수 있게 정리해 두는 곳"으로 시작했는데, 만드는 과정 자체가 이 시리즈의 각 편을 한 번씩 다시 밟는 일이 됐다.

![hack-tree 아키텍처](/images/net-browser/16-hacktree.svg)

---

## 1. 무엇을 만들었나

웹해킹·포너블·커널·CS 네 축의 지식 노드를 마크다운으로 쓰고, 그것을 검색·그래프·진행도·퀴즈와 함께 제공하는 플랫폼이다. 현재 콘텐츠 규모는 이렇다.

| 축 | 노드 수 |
|---|---|
| 커널 | 175 |
| 포너블 | 156 |
| 웹 | 136 |
| CS | 66 |
| **합계** | **533** |

웹 축은 분류 트리와 별도로 **L0-L7의 멘탈 모델 사다리**를 갖고, 그것을 6단계 코스로 압축해 학습 순서를 정한다. 15편에서 정리한 다섯 원형이 이 사다리의 설계 근거이기도 하다.

기술 스택은 다음과 같다.

- **web** — Next.js 15 / React 19 / TypeScript / Tailwind, 패키지 매니저는 pnpm, 테스트는 vitest
- **api** — FastAPI / Uvicorn / SQLAlchemy 2 / Alembic / argon2, Python 3.12, 테스트는 pytest
- **데이터** — SQLite (도커 볼륨), 백업 전용 사이드카 컨테이너
- **엣지** — Caddy (자동 HTTPS, 리버스 프록시)
- **배포** — GitHub Actions → GHCR → GCP VM에 SSH, 인프라는 Terraform + cloud-init
- **셸 스크립트 테스트** — bats로 compose 구성과 배포 스크립트를 검증

## 2. 각 계층에서 실제로 내린 결정

### TLS가 끝나는 지점을 직접 정한다 (5편, 14편)

외부에 열린 포트는 Caddy의 `:80`과 `:443` 둘뿐이고, web과 api 컨테이너는 내부 도커 네트워크에만 노출된다. 인증서는 Let's Encrypt로 자동 발급·갱신된다.

5편에서 "TLS는 앱 서버가 아니라 프록시에서 끝난다"고 적었는데, 그 경계를 **설정 파일 한 줄이 옮긴다**는 것이 실제 감각이었다. Caddyfile에서 `/api/*`를 어디로 보내느냐에 따라 평문 구간의 범위가 달라진다. 문서에서 읽은 문장과 내 손으로 그 줄을 쓰는 것은 다른 종류의 이해다.

같은 파일에서 보안 헤더(HSTS, `X-Content-Type-Options`, `Referrer-Policy`)를 붙이고 `Server` 헤더를 제거한다. 10편의 방어들이 애플리케이션 코드가 아니라 엣지 설정에 사는 경우가 많다는 점도 여기서 체감했다.

### CORS를 설정하는 대신 필요 없게 만든다 (10편)

브라우저가 API를 `https://hack-tree.com/api/...`로 호출하고, Next.js가 그 경로를 내부 `api:8000`으로 다시 쓴다. 브라우저 입장에서는 **같은 출처로만 통신**하므로 CORS 설정 자체가 존재하지 않는다.

10편에서 본 CORS의 흔한 실패는 대부분 설정 실수에서 온다. 요청의 `Origin`을 반사하거나, `null`을 신뢰하거나, 자격증명 허용을 함께 켜는 경우다. 설정이 없으면 그 실수도 없다. **헤더를 잘 쓰는 것보다 필요 없게 만드는 쪽이 안전하다**는 것이 이 구조의 교훈이다.

### 서버에만 있어야 하는 파일은 서빙 경로 밖에 둔다 (11편)

퀴즈 채점에는 정답키가 필요하다. 이 파일을 프런트엔드의 정적 자원 디렉터리에 두면 URL만 알면 누구나 받을 수 있다. 그래서 정답키는 서빙되지 않는 별도 디렉터리에 두고, **api 이미지를 빌드할 때만 복사**한다. 채점은 전부 서버에서 하고 클라이언트는 결과만 받는다.

11편에서 "브라우저에서 도는 코드와 데이터는 전부 사용자가 읽을 수 있다"고 적은 것의 구체적 형태다. 클라이언트에서 채점하면서 정답을 숨기려는 시도는 전부 난독화이지 보안이 아니다.

### 기능을 빼서 공격면을 줄인다 (12편)

공개 회원가입이 없다. 관리자가 발급한 초대로만 계정이 생긴다. 원래는 소규모 사용을 전제한 편의상의 선택이었는데, 결과적으로 사라진 것이 많다.

```
없앤 기능 하나 = 사라진 공격면 여러 개
  회원가입 없음 → 계정 열거 없음
                → 이메일 인증 우회 없음
                → 비밀번호 재설정 포이즈닝 없음
                → 스팸·자동 가입 대응 불필요
```

12편의 인증 결함 목록 상당수가 "가입과 복구 흐름"에 몰려 있다. 그 흐름을 만들지 않으면 목록의 절반이 해당 사항 없음이 된다. 기능을 더해 방어하는 것보다 빼는 쪽이 확실한 경우가 있다는 사례로 남았다.

비밀번호는 argon2로 해싱하고, 세션은 서버가 상태를 가지는 쿠키 세션이다. 12편에서 정리한 대로 즉시 무효화가 필요한 상황에서 세션 쪽이 단순하다.

### 데이터는 백업이 검증돼야 백업이다 (13편)

SQLite 파일을 그냥 복사하면 쓰기 도중의 상태가 섞일 수 있다. 백업 컨테이너는 `sqlite3 .backup`으로 일관된 스냅샷을 만들고, `PRAGMA integrity_check`로 검증한 뒤, 정해진 개수만 남기고 회전시킨다. 데이터 볼륨은 **읽기 전용으로 마운트**한다. 백업 프로세스가 원본을 건드릴 수 있는 경로를 애초에 없애는 것이다.

## 3. 실제로 막혔던 자리

문서에 적힌 설계보다 이쪽이 더 많이 가르쳤다.

### alpine에서 네이티브 모듈이 로드되지 않음

이미지를 작게 만들려고 alpine 기반으로 시작했는데, 검색에 쓰는 ONNX 런타임과 이미지 처리 라이브러리가 로드에 실패했다. 원인은 C 표준 라이브러리였다. 두 패키지는 glibc용으로 미리 컴파일된 바이너리를 내려받는데 alpine은 musl을 쓴다. 빌드는 통과하고 **실행 시점에** 실패하는 형태라 원인을 찾는 데 시간이 걸렸다.

해결은 모든 빌드 스테이지를 glibc 기반 이미지로 통일하는 것이었다. 이미지 크기를 조금 내주고 예측 가능성을 샀다. 네이티브 의존성이 있는 스택에서 베이스 이미지는 취향 문제가 아니라 호환성 제약이라는 것을 배웠다.

### 135MB 모델 파일을 어디에 둘 것인가

의미 기반 검색에 다국어 임베딩 모델이 필요했다. 130MB가 넘는 파일이라 저장소에 그냥 넣을 수 없었고, Git LFS는 대역폭·용량 한도가 걸렸다.

택한 방법은 **고정된 리비전에서 내려받고 sha256을 검증하는 스크립트**다. 파일마다 해시를 확인하고 불일치하면 실패한다. 이미 받아 둔 파일이 해시까지 맞으면 건너뛰므로 재실행이 안전하다. CI에서는 스크립트 해시를 키로 캐시한다.

원래 목적은 용량 문제 해결이었는데, 부수 효과로 **공급망 무결성 검증**이 따라왔다. 14편에서 정리한 "움직이는 태그 대신 해시로 고정하라"는 원칙이 여기서도 그대로 적용된 셈이다. 모델은 web 이미지에 구워져 서버로 가므로, 서버는 모델을 받을 필요가 없다.

### 개발과 운영의 차이를 어디에 적을 것인가

로컬에서는 포트를 직접 열어야 편하고, 운영에서는 그러면 안 된다. 로컬은 HTTP라 `Secure` 쿠키가 동작하지 않지만 운영에서는 반드시 켜야 한다. 이 차이를 코드의 조건문으로 다루면 실수가 조용히 숨는다.

compose 파일을 셋으로 나눴다. 공통 정의, 개발에서 자동으로 얹히는 오버라이드, 운영에서 명시적으로 지정하는 파일이다. **차이가 파일 이름으로 드러나므로 어느 환경에서 무엇이 켜지는지가 눈에 보인다.** 셸 스크립트 테스트(bats)로 각 조합이 의도한 구성을 만드는지 검증한다.

### 배포를 되돌릴 수 있게 만들기

이미지에 `:latest`와 `:<커밋 해시>` 두 태그를 단다. 배포 스크립트는 특정 해시를 주입해 실행하므로 **어느 시점의 코드가 돌고 있는지가 항상 확정**된다. 배포 후 헬스체크가 실패하면 이전 해시로 되돌린다.

움직이는 태그만 쓰면 되돌릴 지점을 특정할 수 없다. 14편에서 서드파티 액션을 해시로 고정하라고 적은 것과 같은 이유이고, 이 경우는 보안보다 운영 쪽 동기가 먼저였다.

## 4. 읽어서 아는 것과 배포해서 아는 것

이 시리즈를 쓰면서 확인한 것은, 각 편에서 정리한 원칙 대부분이 **배포 구성 파일 몇 줄에 실제로 들어 있다**는 사실이었다.

- TLS가 어디서 끝나는가 → Caddyfile의 프록시 대상
- 신뢰 경계가 어디인가 → compose에서 무엇을 `expose`하고 무엇을 `ports`로 여는가
- 클라이언트에 무엇이 가는가 → Dockerfile의 `COPY` 대상
- 무엇을 되돌릴 수 있는가 → 이미지 태그 전략
- 공격면이 얼마나 넓은가 → 만들지 않기로 한 기능 목록

이 대응이 만들어지기 전까지는 각 원칙이 개별 지식이었다. 만들고 나니 서로 연결된 하나의 구조가 됐다. **읽어서 아는 것과 배포해서 아는 것의 차이가 대부분 여기에 있었다.**

동시에 이 프로젝트가 다루지 못한 것도 분명하다. 사용자 수가 적어서 성능·확장 문제를 거의 만나지 않았고, SQLite 단일 파일 구조라 13편에서 정리한 동시성 문제를 실제로 겪을 일이 없었다. 규모가 만드는 문제는 규모를 겪어야 배운다.

## 5. 다음 갱도

이 시리즈는 물리 계층에서 시작해 배포까지 올라왔다. 의도적으로 비워 둔 칸이 하나 있다. 9편에서 자바스크립트 엔진이 **어디에** 있고 **왜** 필요했는지까지만 다루고, 그 안에서 무슨 일이 일어나는지는 넘겼다.

다음 시리즈가 그 칸이다. 엔진이 코드를 실행 가능한 형태로 바꾸는 과정, 최적화가 기대는 가정, 그 가정이 깨질 때 생기는 일, 그리고 그 지점을 자동으로 찾기 위한 퍼저를 직접 만드는 것까지가 범위다. 8편에서 본 대로 렌더러 내부 코드 실행은 브라우저 익스플로잇 체인의 1단계이고, 그 1단계가 가장 자주 서는 자리가 엔진이다.

15편의 다섯 원형 중 어느 칸도 그곳에서 사라지지 않는다. 경계 불일치는 파서와 옵티마이저 사이에서, 정체성 불일치는 타입 추론에서, 부수 효과 관측은 캐시와 타이밍에서 다시 나타난다. 층을 내려갈 뿐 형태는 같다.
