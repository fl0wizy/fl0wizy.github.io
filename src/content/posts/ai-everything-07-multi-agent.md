> 이 편에서 정리할 것
> 1. **멀티에이전트의 판정 기준은 모델 다양성이 아니다** – 그럼 무엇인가
> 2. Subagent(심부름)와 Agent Teams(회의)의 결정적 차이
> 3. 역할 이름이 아니라 **문맥 경계**로 나누는 법
> 4. 멀티에이전트를 **쓰지 말아야 할 때**

## 1. 먼저 질문에 답한다

> "하나의 세션에서 10개 서브에이전트를 오케스트레이션하는데,
> 그 10개가 모두 Opus와만 통신한다면 이게 멀티에이전트가 맞는가?
> Gemini, Codex 이런 식으로 모델이 섞일 필요는 없나?"

**멀티에이전트가 맞다. 그리고 모델이 섞일 필요는 전혀 없다.**

멀티에이전트를 정의하는 것은 모델 다양성이 아니라 네 가지다.

| # | 조건 | 설명 |
|---|---|---|
| 1 | **독립된 컨텍스트 창** | 각 에이전트가 자기 책상을 가진다 |
| 2 | **고유한 시스템 프롬프트/역할** | "너는 숙소 조사 담당이다" |
| 3 | **분리된 도구 권한** | 조사 담당에게 배포 권한을 주지 않는다 |
| 4 | **조율 구조** | 누가 나누고 누가 합치는가 |

Anthropic의 멀티에이전트 리서치 시스템도 lead agent와 subagent들이 같은 모델 계열을 쓴다. Claude Code의 서브에이전트도 기본은 같은 모델이다.

### 반대로, 단일 에이전트란?

**Skill 50개, MCP 서버 10개, Hook 20개가 붙어 있어도 컨텍스트 창이 하나면 단일 에이전트다.** "확장된 단일 에이전트"일 뿐이다.

> 세는 단위는 "에이전트"라는 **말**이 아니라 **독립된 컨텍스트 창 + 자기 루프**다.

### 모델 계층화는 별개의 기법이다

강한 모델은 판단에, 싸고 빠른 모델은 단순 정리에 쓰는 **model tiering**은 **비용·지연 최적화 기법**이지 멀티에이전트의 조건이 아니다. 둘을 분리해서 기억하자.

```
멀티에이전트   ← 컨텍스트를 나누는 문제
모델 계층화    ← 비용을 최적화하는 문제
     이 둘은 함께 쓸 수 있지만, 서로의 조건은 아니다
```

## 2. Subagent와 Agent Teams – 결정적 차이

같은 "여러 에이전트"라도 두 종류로 갈린다. 이걸 구분하지 못하면 잘못된 구조를 고른다.

### 가족 여행 준비로 먼저 이해하기

토요일에 가족 여행을 간다. 해야 할 일이 많다. 그런데 **두 종류의 일이 섞여 있다.**

**첫 번째: 따로 조사해도 되는 일**

- "숙소 후보 세 곳만 찾아와"
- "기차 시간표만 비교해 와"
- "근처 맛집만 정리해 와"

한 사람이 따로 조사해서 결과만 가져오면 된다. 중간에 계속 회의할 필요가 없다. → **Subagent**

**두 번째: 계속 맞춰야 하는 일**

숙소가 바뀌면 교통편도 바뀌고, 교통비가 늘면 예산도 바뀌고, 부모님이 계단 많은 숙소를 힘들어하면 숙소 후보를 다시 봐야 한다. → **Agent Teams**

| 가족 여행 장면 | AI 구조 | 이유 |
|---|---|---|
| "숙소 후보 세 곳만 조사해 와" | Subagent | 독립적으로 조사하고 결과만 받으면 된다 |
| "기차 시간표만 비교해 와" | Subagent | 다른 담당자와 계속 대화하지 않아도 된다 |
| "숙소·교통·예산을 함께 맞추자" | Agent Teams | 한쪽 결정이 다른 쪽 결정을 계속 바꾼다 |
| "부모님 동선까지 고려해 전체 일정 재조정" | Agent Teams | 중간 발견을 모두가 바로 알아야 한다 |
| "간단한 당일치기 일정 하나만" | **단일 에이전트** | 나누는 비용이 더 클 수 있다 |

### 정면 비교표

| 구분 | **Subagent** | **Agent Teams** |
|---|---|---|
| 기본 성격 | **fire-and-forget** | **collaborative** |
| 작업 방식 | 맡긴 일을 끝내고 보고한다 | 서로 상태를 공유하며 조율한다 |
| 에이전트 간 대화 | **없다** | **있다** |
| 공유 메모리 | 없다 | 공유 작업 목록과 상태가 있다 |
| 지속 상태 | 거의 없다. 끝나면 사라진다 | 시간이 지나며 문맥이 쌓인다 |
| 부모의 역할 | 위임하고 요약을 받는다 | 팀 운영과 결과 종합 |
| 한 줄 요약 | **"조사해 오세요"** | **"같이 회의하면서 진행합시다"** |

## 3. Subagent – 격리를 통한 병렬성

Subagent 하나에는 보통 네 가지가 들어간다.

| 구성 요소 | 의미 | 일상 비유 |
|---|---|---|
| **고유한 시스템 프롬프트** | 이 에이전트가 어떤 전문가인지 | "너는 숙소 조사 담당이야" |
| **허용된 도구** | 사용할 수 있는 도구를 제한 | 숙소 담당에게 지도와 예약 사이트만 |
| **깨끗한 독립 문맥** | 부모 대화의 잡음 없이 필요한 정보만 | 자기 노트 한 권으로 조사 |
| **하나의 작업** | 한 번에 하나의 분명한 일 | "숙소 후보 3개 비교"처럼 범위를 좁힘 |

### 핵심 가치: 부모의 머릿속을 깨끗하게 유지한다

긴 조사 로그, 코드 검색 결과, 여러 후보 비교표를 **모두 부모 문맥에 넣지 않아도 된다.** 하위 에이전트가 조사하고, 부모에게는 압축된 결과만 돌아온다.

```
부모 에이전트 (여행 총괄)
 ├─ "숙소 후보 3곳 조사" → 숙소 담당 (독립 컨텍스트) ─┐
 ├─ "기차 시간표 비교"   → 교통 담당 (독립 컨텍스트) ─┼─→ 각자 "표 한 장"만 반환
 └─ "맛집 정리"          → 맛집 담당 (독립 컨텍스트) ─┘
                              ↓
                      부모의 최종 판단
```

**Subagent가 잘 맞는 일:**

- 서로 독립적인 자료 조사
- 코드베이스의 특정 영역 탐색
- 여러 문서의 초벌 요약
- 보안·성능·문체처럼 **관점이 뚜렷한 리뷰**
- 부모가 최종 요약만 받으면 되는 조회 작업

### Subagent의 약점

**중간에 발견한 내용이 다른 하위 에이전트의 판단을 즉시 바꿔야 하는 작업에는 약하다.**

숙소 담당이 "이 숙소는 싸지만 역에서 너무 멀다"를 발견했다고 하자. 이 정보가 교통 담당의 판단을 바로 바꿔야 한다면? 숙소 담당이 결과를 끝까지 들고 있다가 마지막에 보고하면, 교통 담당은 이미 잘못된 기준으로 시간을 계산했을 수 있다.

## 4. Agent Teams – 소통을 통한 조율

세 가지 움직이는 부분이 있다.

| 구성 요소 | 하는 일 | 일상 비유 |
|---|---|---|
| **팀 리드** | 일을 나누고, 순서를 잡고, 결과를 종합 | 여행 준비 총괄 |
| **팀원 에이전트** | 각자 자기 문맥 창을 가지고 병렬 작업 | 숙소·교통·예산 담당 |
| **공유 작업 목록** | 대기/진행중/완료 상태와 의존성 추적 | 냉장고에 붙인 공동 체크리스트 |

**핵심은 결과를 모으는 게 아니라 중간 상태를 함께 맞추는 것이다.**

프론트엔드 담당이 "API 응답 구조가 바뀌어야 합니다"라고 말하면, 백엔드 담당이 팀 리드를 기다리지 않고 바로 조정할 수 있다. 테스트 담당도 그 변경을 보고 대기 상태를 바꾼다.

> 가족 단체 채팅방과 비슷하다. 숙소 담당이 "예약 가능한 방이 하나뿐"이라고 올리면, 예산 담당은 바로 비용을 다시 계산하고, 교통 담당은 이동 시간을 다시 본다.

**Agent Teams가 잘 맞는 일:**

- 여러 역할의 결과가 계속 서로 영향을 주는 작업
- 중간 발견이 다른 작업 방향을 바꾸는 작업
- 작업 사이에 대기·차단·선행 조건이 많은 작업
- 한 번에 끝나는 조사가 아니라 오래 이어지는 프로젝트

## 5. 선택 기준표

| 질문 | Subagent | Agent Teams |
|---|---|---|
| 작업이 서로 독립적인가? | 각 작업이 따로 끝나고 요약만 합치면 된다 | 한쪽 결과가 다른 쪽 방향을 계속 바꾼다 |
| 중간 발견을 즉시 공유해야 하는가? | 최종 결과만 부모에게 주면 충분 | 중간 발견을 팀원이 바로 알아야 한다 |
| 작업 상태를 추적해야 하는가? | 굳이 공유할 필요 없다 | 의존성과 차단 상태를 계속 봐야 한다 |
| 비용과 복잡도는? | 병렬 처리 이득 > 조율 비용 | 조율 자체가 품질을 좌우 |
| 부모가 원하는 것은? | 압축된 요약 결과 | 조율된 공동 결과 |

**생활 언어로 바꾼 판정표:**

| 생활 질문 | 선택 |
|---|---|
| "각자 따로 알아보고 마지막에 표만 합치면 되는가?" | **Subagent** |
| "중간에 발견한 내용이 다른 사람의 일을 바로 바꾸는가?" | **Agent Teams** |
| "서로 계속 물어보느라 조사보다 회의가 더 길어질 것 같은가?" | **단일 에이전트** 또는 더 작은 범위 |
| "공동 체크리스트가 없으면 누가 뭘 하는지 헷갈리는가?" | **Agent Teams** |
| "한 사람이 차분히 하는 편이 더 빠른가?" | **단일 에이전트** |

## 6. 가장 중요한 원칙 – 역할이 아니라 **문맥 경계**로 나눈다

멀티에이전트 설계에서 **가장 흔한 실수**는 일을 역할 이름으로 나누는 것이다.

```
X 계획 담당 → 구현 담당 → 테스트 담당
   보기에는 깔끔하지만, 정보가 전달될 때마다 손실된다
```

**전달 게임(telephone game)과 같다.** 처음 문장은 분명했지만 여러 사람을 거치면 다른 문장이 된다.

> 좋은 기준은 역할이 아니라 **문맥 경계**다.

| 상황 | 판단 |
|---|---|
| 두 작업이 깊게 같은 정보를 필요로 한다 | **한 에이전트가 이어서 맡는다** |
| 두 작업이 서로 독립적인 정보만 필요로 한다 | **나눈다** |
| 중간 발견이 다른 작업을 바꿔야 한다 | Agent Teams처럼 **소통 구조** |
| 결과만 합치면 된다 | Subagent처럼 **격리 구조** |

**코딩에서 특히 중요하다.** 어떤 기능을 구현한 에이전트가 그 기능의 테스트까지 작성하는 편이 자연스러울 때가 많다. 이미 구현 의도와 예외 처리를 알고 있기 때문이다.

> 김치찌개를 끓이는 사람과 간을 보는 사람을 무조건 분리하면 이상하다. 끓인 사람이 어떤 재료를 넣었는지 아니까 기본 간은 그 사람이 먼저 본다. 대신 **손님상에 내기 전에는 다른 사람이 한 번 맛을 보면 좋다.**

이게 [08편의 Generator-Evaluator](/post/ai-everything-08-eval-harness) 구조로 이어진다. 모든 단계를 역할로 쪼개는 게 아니라, **최종 검증만 독립시키는** 것이다.

## 7. 5가지 오케스트레이션 패턴

Subagent든 Agent Teams든, 실제 흐름은 이 패턴들의 조합이다.

| 패턴 | 의미 | 언제 쓰는가 |
|---|---|---|
| **프롬프트 체이닝** | 앞 단계 결과를 다음 단계 입력으로 | 순서가 중요하고 단계가 서로 의존할 때 |
| **라우팅** | 요청을 보고 적절한 전문가·모델로 보낸다 | 쉬운 일과 어려운 일을 나눌 때 |
| **병렬화** | 독립 작업을 동시에 실행 | 여러 조사, 여러 후보 생성, 여러 문서 요약 |
| **오케스트레이터-워커** | 중앙 에이전트가 나누고 종합 | Subagent와 Agent Teams 모두에서 자주 |
| **평가자-개선자** | 하나가 만들고 다른 하나가 평가해 되돌린다 | 품질이 중요하고 한 번에 끝내기 어려울 때 |

**배타적이지 않다.** 부모가 요청을 라우팅하고, 세 개의 Subagent를 병렬 실행한 뒤, 평가자 에이전트가 결과를 검토하는 식으로 조합한다.

가족 여행으로 바꾸면: 여행지 → 숙소 → 세부 일정 순서로 정하면 **체이닝**, 숙소 질문은 숙소 담당에게 보내면 **라우팅**, 숙소·맛집·교통을 동시에 조사하면 **병렬화**, 한 사람이 전체를 나누어 맡기고 합치면 **오케스트레이터-워커**, 최종안을 다른 사람이 검토하면 **평가자-개선자**.

### 좋은 분업의 예

| 역할 | 하는 일 |
|---|---|
| **Planner** | 목표를 작은 단계로 나눈다 |
| **Researcher** | 자료를 찾고 요약한다 |
| **Builder** | 결과물을 만든다 |
| **Evaluator** | 결과를 **비판적으로** 검증한다 |
| **Reporter** | 사람에게 이해 가능한 보고서를 쓴다 |

## 8. 멀티에이전트를 **쓰지 말아야 할 때**

멀티에이전트는 멋져 보이지만 항상 정답은 아니다.

| 상황 | 왜 단일 에이전트가 나은가 |
|---|---|
| 작업이 단순해서 좋은 프롬프트 하나로 충분할 때 | 나누는 비용이 이득보다 크다 |
| 에이전트들이 계속 서로의 문맥을 물어봐야 할 때 | 조율 비용이 폭증한다 |
| 작업 의존성 관리 비용 > 실제 실행 이득 | 관리가 본업이 된다 |
| 여러 에이전트가 **같은 파일을 동시에** 고쳐야 할 때 | 충돌하거나, 더 위험하게는 **충돌 없이 합쳐졌지만 설계 가정이 어긋난다** |
| 결과가 느려지고 비용만 느는지 **측정할 방법이 없을 때** | 개선인지 악화인지 모른다 |

> **집수리 비유:** 전기 담당자와 배관 담당자가 동시에 같은 벽을 뜯는데 서로 말하지 않으면 위험하다. 한쪽은 콘센트 위치를 바꾸고, 다른 쪽은 그 자리에 배관을 지나가게 만들 수 있다. **각자 열심히 일했지만 합치면 문제가 된다.**

그래서 코딩에서 Subagent는 **동시에 코드를 쓰는 작업자**보다 **읽고 조사하고 위험을 알려주는 역할**로 쓰는 편이 안전하다.

### 실패 모드 3가지

**① 작업 설명이 흐리면 에이전트들이 서로 같은 일을 한다.**

```
X "조사해 줘"
O "공식 문서 기준으로 보안 위험 5개를 표로 정리하고, 코드 수정은 하지 마"
```

모든 에이전트에게 **목적 / 기대 출력 형식 / 사용할 도구와 자료 / 다루지 말아야 할 범위**가 분명해야 한다.

**② 검증 에이전트가 실제로 검증하지 않고 "괜찮다"고 말한다.**

```
X "잘 봐줘"
O "전체 테스트를 실행하고, 이 세 가지 케이스가 통과하기 전에는 완료라고 말하지 마"
```

**검증은 감상이 아니라 절차여야 한다.**

**③ 토큰 비용이 예상보다 빠르게 커진다.**

에이전트가 늘어나면 각자 문맥을 들고 움직인다.

> 세 명이 10분씩 따로 조사하면 **30분**이다.
> 그런데 다섯 명이 모여 한 시간 동안 계속 회의하면 **5시간**이 쓰인다.

**"사람이 많으니 빠르겠지"는 항상 맞지 않다.** 그래서 필요한 것:

- 모델 계층화 (중요한 판단은 강한 모델, 반복 조회는 빠르고 저렴한 모델)
- 예산 한도와 중단 조건을 하네스에 포함

---

## 9. 실전 판단 절차

```
1. 먼저 하나의 에이전트로 해결해 본다
2. 어디서 실패하는지 확인한다
3. 문맥이 너무 커지면 → Subagent로 격리한다
4. 독립 조사가 많으면 → Subagent를 병렬로 쓴다
5. 중간 상태를 계속 맞춰야 하면 → Agent Teams를 고려한다
6. 같은 파일을 동시에 수정해야 한다면 → 병렬 쓰기를 피한다
7. 비용·속도·품질이 실제로 좋아졌는지 측정한다
```

이 순서는 하네스 엔지니어링의 기본 태도와 같다. **복잡한 구조를 먼저 만들지 않는다. 작게 시작하고, 실제로 깨지는 지점을 보고, 그 지점에만 구조를 더한다.**

Anthropic의 「Building Effective Agents」도 같은 방향을 권한다. 먼저 단일 LLM 호출·검색·예시만으로 충분한지 확인하고, 필요할 때 workflow와 agent 구조를 붙인다.

## 10. 하나 더 – 하네스는 모델의 한계를 가정한다

Anthropic의 managed agents 글은 중요한 경고를 한다.

> **하네스는 "모델이 못한다고 가정한 것들"을 인코딩한다.**
> 그래서 모델이 발전하면 그 가정이 낡을 수 있다.

멀티에이전트도 마찬가지다. 오늘 "컨텍스트가 부족해서" 나눈 구조가, 컨텍스트가 늘어난 다음 모델에서는 불필요한 복잡성이 될 수 있다. 이게 [11편의 "비계(scaffolding)" 원칙](/post/ai-everything-11-patterns-decisions)이다.

---

## 11. 이 편의 요약

- **멀티에이전트의 조건은 모델 다양성이 아니다.** 독립 컨텍스트 창 + 역할 + 도구 권한 + 조율 구조
- 서브에이전트 10개가 전부 같은 모델을 써도 **멀티에이전트가 맞다**
- **모델 계층화는 비용 최적화 기법**이지 멀티에이전트의 조건이 아니다
- Skill·MCP·Hook이 아무리 많아도 **컨텍스트 창이 하나면 단일 에이전트**다
- **Subagent = fire-and-forget (심부름), Agent Teams = collaborative (회의)**
- **역할 이름이 아니라 문맥 경계로 나눈다.** 전달 게임에서 정보가 손실된다
- 오케스트레이션 5패턴: 체이닝 / 라우팅 / 병렬화 / 오케스트레이터-워커 / 평가자-개선자
- **같은 파일을 동시에 고치는 병렬 쓰기는 피한다.** 충돌보다 "충돌 없이 합쳐졌지만 가정이 어긋난 것"이 더 위험하다
- 멀티에이전트는 속도가 아니라 **품질과 문맥 관리**를 위한 도구다. 비용은 오히려 늘어난다
