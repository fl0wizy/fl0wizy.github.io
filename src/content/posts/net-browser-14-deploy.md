13편이 넘긴 결손은 **실행 환경의 경계**다. 이 편은 그 경계를 두 경로로 나눠 연다. 사용자 요청이 앱에 닿는 경로와, 코드가 서버에 닿는 경로다. **앞의 것은 대개 잘 검토되고 뒤의 것은 자주 잊히는데, 권한의 크기는 반대다.**

## 1. 요청 경로와 그 위의 신뢰 경계

| 구간 | 하는 일 | 이 구간이 만드는 문제 |
|---|---|---|
| 브라우저 → CDN | TLS 종료, 엣지 캐시 | 캐시 키에 없는 입력이 응답에 영향을 주면 오염된다 (6편) |
| CDN → 로드밸런서 | 분배, 헬스체크 | 백엔드 중 한 대만 설정이 다르면 간헐적 취약점이 된다 |
| LB → 리버스 프록시 | 경로 라우팅, 헤더 조작 | 경로 정규화 차이로 접근 제어가 우회된다 |
| 프록시 → 앱 | HTTP/1.1 재작성 | 여기가 요청 스머글링이 사는 칸이다 (6편) |
| 앱 → DB | 사설망 | 내부는 인증이 약하다는 전제가 SSRF의 가치를 만든다 (2편, 4편) |

이 표는 구간 전체의 개요다. 아래 두 소절은 그중 경계가 가장 자주 어긋나는 두 지점을 편다.

### 암호화가 끝나는 지점

5편에서 짚은 내용이 여기서 실체를 갖는다. 실제 배포에서 TLS는 앱 서버가 아니라 CDN이나 리버스 프록시에서 끝난다. 그 뒤 구간은 평문이거나 별도의 내부 TLS다. 즉 **평문을 읽고 고칠 수 있는 주체가 경로 중간에 존재한다.** "HTTPS를 쓰니 안전하다"는 진술은 정확히는 "브라우저와 엣지 사이가 안전하다"는 뜻이다.

### 클라이언트 IP가 헤더에 적힌 값이 되는 지점

앱 서버가 소켓에서 보는 출발지 주소는 마지막 프록시의 것이다(2편). 진짜 클라이언트 주소는 헤더로 전달된다.

```http
X-Forwarded-For: 1.2.3.4, 10.0.0.9, 10.0.0.3
```

각 프록시가 자기가 본 출발지를 뒤에 덧붙인 목록이다. 문제는 **클라이언트도 이 헤더를 보낼 수 있다**는 것이다. 프록시가 들어오는 `X-Forwarded-For`를 제거하지 않으면 공격자가 목록의 앞부분을 마음대로 채운다.

```
목록의 맨 앞을 읽는다        → 공격자가 위조한 값을 읽는다
목록의 맨 뒤를 읽는다        → 항상 마지막 프록시의 IP다
뒤에서 N번째를 읽는다        → N이 인프라 구성과 정확히 맞아야 한다
```

정답은 "신뢰하는 프록시 홉 수를 설정으로 명시하고, 그 개수만큼 뒤에서 세는 것"이다. 프록시 한 대를 추가하면 이 설정도 바꿔야 한다. IP 기반 레이트 리밋, 접근 제한, 감사 로그가 전부 이 값 위에 서 있으므로 틀리면 셋 다 틀린다. 이 값을 읽어 판단하는 쪽은 12편의 앱이다.

## 2. 컨테이너가 실제로 격리하는 것

컨테이너는 가상머신이 아니다. 세 가지 커널 기능의 조합이다.

- **네임스페이스** – 무엇을 보는가. 프로세스 목록, 네트워크 인터페이스, 마운트 지점, 호스트명을 분리된 뷰로 준다.
- **cgroups** – 얼마나 쓰는가. CPU와 메모리 사용량의 상한.
- **capabilities와 seccomp** – 무엇을 할 수 있는가. 특권 동작과 허용 시스템 콜의 제한.

**커널은 호스트와 공유한다.** 이 한 줄이 보안상 결정적이다. 가상머신은 게스트 커널이 따로 있어서 탈출하려면 하이퍼바이저를 깨야 하지만, 컨테이너는 같은 커널을 쓰므로 **커널 취약점 하나가 곧 탈출 경로**다. 컨테이너 탈출 연구가 사실상 커널 익스플로잇 연구와 겹치는 이유다.

실무에서 문턱을 낮추는 설정들은 정해져 있다. 특권 모드, 호스트의 도커 소켓 마운트, 컨테이너 안에서 root로 실행, 불필요한 capability 유지, 호스트 네트워크 네임스페이스 공유. 이 중 도커 소켓 마운트는 사실상 호스트 권한을 그대로 주는 것과 같다. 그 소켓에 접근할 수 있으면 특권 컨테이너를 새로 띄울 수 있기 때문이다.

## 3. 오케스트레이션이 늘리는 표면

컨테이너 한 대의 격리를 정하는 주체는 커널이지만, 수백 대의 배치와 연결을 정하는 주체는 그 위의 스케줄러다. 쿠버네티스 같은 오케스트레이터는 API 서버라는 단일 통제점을 만든다. 편의의 근원이자 표적의 집중점이다.

- **네트워크 정책이 없으면 파드 사이는 평면 네트워크다.** 기본값에서는 어떤 파드든 다른 파드에 접근할 수 있다. 웹 프런트엔드 하나가 뚫리면 내부 서비스 전체가 사정권에 들어온다. 2편·4편의 전제가 여기서 비용을 청구한다.
- **기본 시크릿은 암호화가 아니라 인코딩이다.** 별도로 저장소 암호화나 외부 비밀 관리자를 붙이지 않으면 etcd에 사실상 평문으로 있다.
- **서비스 계정 토큰이 파드 안에 마운트된다.** 애플리케이션을 장악한 공격자가 곧바로 API 서버에 질의할 수 있다는 뜻이다. RBAC이 느슨하면 그 자리에서 클러스터 전체로 확장된다.

## 4. 관측성 – 수집이 만드는 노출면

로그, 메트릭, 트레이스는 사고 조사에 반드시 필요하다. 동시에 그 자체가 유출 경로다. 인증 헤더, 세션 쿠키, 요청 본문의 개인정보가 로그에 그대로 남는 일이 흔하고, 로그 수집 시스템은 보통 애플리케이션 데이터베이스보다 **더 많은 사람이 접근**한다. 마스킹은 수집 지점에서 해야 하며, 저장된 뒤에 지우는 것은 늦다.

반대로 감사 로그가 없으면 사고가 나도 무엇이 일어났는지 재구성할 수 없다. 5편에서 본 Certificate Transparency의 발상이 여기서도 그대로 적용된다. **예방이 완전할 수 없으면, 일어난 일이 반드시 드러나게 만드는 데 예산을 쓴다.**

## 5. 코드가 서버에 닿는 경로

§3까지가 사용자 요청이 앱에 닿는 경로다. 나머지 하나는 코드가 서버에 닿는 경로다. 애플리케이션 취약점이 주는 것은 대개 **사용자 수준의 권한**이다. 파이프라인 취약점이 주는 것은 **배포 권한**이다. 후자는 임의의 코드를 프로덕션에 올릴 수 있다는 뜻이므로 항상 더 크다.

반복되는 실패 유형은 목록이 정해져 있다.

**외부 PR이 시크릿에 접근하는 워크플로를 트리거한다.** 포크에서 온 PR의 코드가 리뷰 전에 실행되고, 그 실행 환경에 배포 자격증명이 노출되는 구성이다. 빌드 스크립트 한 줄을 고쳐 시크릿을 외부로 보내면 끝난다. 신뢰 없는 코드를 실행하는 잡과 시크릿을 쓰는 잡을 분리하는 것이 기본 방어다.

**서드파티 액션과 베이스 이미지를 움직이는 태그로 참조한다.** `@v3`이나 `:latest`는 이름이고, 그 이름이 가리키는 내용은 언제든 바뀐다. 업스트림이 침해되면 다음 빌드부터 조용히 악성 코드가 들어온다. 커밋 해시나 이미지 다이제스트로 고정해야 실제로 같은 것을 쓴다.

**내부 패키지 이름이 공개 레지스트리에서 선점된다.** 패키지 관리자가 사설 레지스트리와 공개 레지스트리를 함께 보도록 설정돼 있고 공개 쪽 버전이 더 높으면, 내부 이름으로 공격자의 패키지를 받아 온다. 의존성 혼동이라고 부르는 형태다.

**IaC 상태 파일이 비밀을 담은 채 방치된다.** 상태 파일은 인프라 전체의 설계도이며, 자원 속성에 데이터베이스 비밀번호 같은 값이 평문으로 들어간다. 접근 통제 없는 스토리지에 두면 그 자체가 최상위 유출이다.

## 6. 이 계층에서 취약점이 사는 자리

**이 계층에서는 설정 한 줄이 신뢰 경계의 위치를 정한다.**

```
들어오는 XFF를 지우지 않음        → 클라이언트가 자기 IP를 정한다
신뢰 홉 수와 실제 구성의 어긋남   → 레이트 리밋·접근 제한·감사 로그가 함께 틀린다
호스트와 공유하는 커널            → 커널 취약점 하나가 곧 탈출 경로
파드 사이를 막지 않는 기본값      → 앱 하나의 장악이 클러스터 권한이 된다
파이프라인이 쥔 배포 자격증명     → 프로덕션에 임의의 코드가 올라간다
마스킹 없는 수집 지점             → 앱 데이터베이스보다 넓게 열린 로그
```

헤더가 사실이 되는 지점은 15편의 원형 B – 정체성 불일치로, 배포 경로가 쥔 권한은 원형 C – 권한 확인 누락으로 정리된다.
