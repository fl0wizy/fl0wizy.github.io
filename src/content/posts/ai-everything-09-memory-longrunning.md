## 1. 교대근무 문제

짧은 대화에서는 AI가 잘해 보인다. 하지만 여러 시간, 여러 날 이어지는 작업에서는 문제가 생긴다.

- 대화가 길어지고 컨텍스트가 복잡해진다
- 이전 결정이 잊힌다
- **AI가 완료되지 않은 일을 완료했다고 착각한다**

Anthropic의 *Effective harnesses for long-running agents* 는 **각 새 세션이 이전 작업 상태를 모른다**는 문제를 강조한다.

> **야간 근무자가 아무 인수인계 없이 출근하면, 낮 근무자가 무엇을 했는지 다시 조사해야 한다.**

### Context anxiety – 잘 알려지지 않은 실패 모드

Anthropic의 harness design 글이 짚는 흥미로운 현상이다.

> **컨텍스트 창이 거의 찼다고 느끼면 에이전트가 남은 일을 충분히 확인하지 않고 "이 정도면 끝났다"고 서둘러 마무리하려는 경향이 생긴다.**

사람도 회의 종료 시간이 다가오면 어려운 쟁점을 "다음에 보죠" 하고 넘기고 싶어진다. 그래서 장시간 하네스는 모델에게 **오래 버티라고만 하지 않고, 적절한 시점에 새 세션으로 넘길 수 있는 인수인계 구조**를 준다.

## 2. Compaction의 대가

**Compaction**은 긴 대화를 요약해 컨텍스트를 줄이는 기술이다.

| 장점 | 단점 |
|---|---|
| 대화를 계속 이어 갈 수 있다 | **요약 과정에서 중요한 디테일이 빠진다** |

> 사람이 회의록만 믿고 원본 계약서를 버리지 않는 것처럼,
> AI도 **progress file, feature list, git history 같은 원천 기록**을 함께 가져야 한다.

### Context reset – 위험해 보이지만 강력하다

새 세션을 시작하는 일. 잘 설계하면 오히려 강력하다. **새 세션은 오래된 잡음을 제거하고, 구조화된 인계 문서만 읽고 출발한다.**

**좋은 reset 조건:**

```
□ 한 기능 단위가 끝났을 때
□ 대화가 너무 길어졌을 때
□ 모델이 반복해서 혼란스러워할 때
□ 새로운 역할의 에이전트가 필요할 때
```

## 3. 세션 인계 구조 4종

| 파일 | 역할 |
|---|---|
| `feature_list.json` | **무엇이 남았는지** 구조화 |
| `progress.md` | **지금까지 무엇을 했는지** 설명 |
| `git history` | **실제 변경 이력** |
| `test report` | **무엇이 검증되었는지** 증거 |

### Feature list는 할 일 목록이 아니라 **검증 대장**이다

Anthropic 글에서 가장 실전적인 부분이다.

```jsonc
[
  {
    "id": "auth-01",
    "feature": "이메일 로그인",
    "verification": "브라우저에서 로그인 → 대시보드 진입 → 새로고침 후 세션 유지",
    "passes": false          // ← 처음에는 전부 false
  }
]
```

**규칙:**

- 처음에는 모든 항목을 `passes: false`로 둔다
- 에이전트는 기능 설명이나 테스트 조건을 **마음대로 바꾸지 못한다**
- 실제로 구현하고 확인한 뒤에만 `passes`를 `true`로 바꿀 수 있다

> 장기 여행 체크리스트에서 "보험 알아보기"라고만 적으면 완료 기준이 흐릿하다.
> "보험 증권 PDF가 있고, 날짜가 맞고, 가족 구성원이 모두 포함되어 있다"라고 적으면 확인할 수 있다.

**좋은 feature list는 할 일을 적는 문서가 아니라, "완료"라고 말하기 전에 무엇을 증명해야 하는지 적는 문서다.**

JSON이 도움이 되는 이유: 자유로운 Markdown 목록은 에이전트가 항목을 합치거나 문장을 바꾸기 쉽다. JSON은 구조가 분명해서 **"기능 이름과 확인 조건은 유지하고, 통과 여부만 바꾼다"** 는 규칙을 주기 쉽다.

### Ralph Loop – 근무 교대 시스템

Anthropic의 long-running harness 연구는 **초기화 에이전트**와 **코딩 에이전트**를 나누었다. 커뮤니티에서는 이 흐름을 Ralph Loop라는 이름으로 소개하기도 한다.

```
Initializer Agent
  init.sh · progress.md · feature_list.json · 첫 git commit
        ↓
Coding Agent (세션 1)
  1. git log · progress · feature list 읽기
  2. 미완료 기능 하나 선택
  3. 구현 · 수정
  4. 테스트
       ├─ 통과 → feature list 상태 변경 · git commit · progress 갱신
       └─ 실패 → 실패 로그를 progress에 남김
        ↓
Coding Agent (세션 2) – 흔적을 읽고 이어간다
```

> 24시간 운영되는 병원의 교대근무다. 의사가 아무리 유능해도 **인수인계 차트**가 없으면 환자 상태를 놓친다.

**여기서 파일 시스템은 단순한 저장 공간이 아니라 컨텍스트 창 사이를 이어 주는 기억 장치다.** 대화창 내용은 길어지면 압축되거나 사라지지만, `progress.md` / `feature_list.json` / git history / test report는 다음 세션이 다시 읽을 수 있다.

> **"모델이 기억한다"보다 "다음 모델도 읽을 수 있게 남긴다"가 더 안전한 원칙이다.**

**바로 적용할 수 있는 한 문장:**

> AI에게 "계속해"라고만 하지 말고, **계속할 수 있는 흔적을 파일로 남기게 하라.**

### 끝내려는 순간을 하네스가 한 번 더 붙잡는다

LangChain의 하네스 글이 짚는 포인트. 긴 작업에서 에이전트는 컨텍스트가 복잡해지면 스스로 "이제 마무리하겠습니다"라고 판단할 수 있다. 이때 하네스가 바로 종료시키지 않고, **새롭고 깨끗한 세션을 열어 원래 목표·진행 파일·남은 기능 목록을 다시 읽게** 만들 수 있다.

> 퇴근하려는 의사에게 "잠깐, 인수인계 차트에 빠진 환자는 없는지 확인하고 다음 근무자에게 넘기자"라고 말하는 것과 같다.

## 4. Git · init script · smoke test

**Git은 하네스 관점에서 상태 기억 장치다.** 어떤 파일이 언제 왜 바뀌었는지 기록한다. AI가 장시간 작업할 때 git commit은 **작업 일지** 역할을 한다.

개발 업무가 아니어도 같은 구조를 만들 수 있다. 문서 버전 기록, 변경 로그, 승인 이력, 작업 완료표가 모두 git history와 같은 역할이다.

**Init script**는 새 세션이 시작될 때 환경을 준비하는 스크립트, **smoke test**는 기본 기능이 크게 깨지지 않았는지 빠르게 확인하는 테스트다.

> 식당의 개점 체크리스트다. 가스 밸브, 냉장고 온도, 카드 단말기, 예약 목록을 확인한 뒤 영업을 시작한다.

### Clean state – 세션 종료 시 요구할 것

```
□ 변경 요약
□ 실행한 테스트
□ 실패한 테스트
□ 남은 작업
□ 다음 추천 작업
```

## 5. 장시간 작업의 4대 실패

| 실패 모습 | 왜 위험한가 | 하네스 보완 |
|---|---|---|
| 너무 일찍 "전체 완료"라고 말한다 | 일부만 만들고 끝났다고 착각 | feature list에서 **남은 항목을 먼저 읽게** 한다 |
| 버그가 있는 상태로 다음 세션에 넘긴다 | 다음 세션이 실패 원인을 다시 찾아야 함 | 실패 테스트와 오류 로그를 progress file에 남긴다 |
| 실제 사용 흐름을 확인하지 않는다 | 겉보기엔 만들어졌지만 사용자는 막힌다 | **브라우저 검증·스크린샷·시나리오 테스트**를 요구한다 |
| 매번 실행 방법을 다시 찾는다 | 시작할 때마다 시간 낭비, 실수 반복 | `init.sh`와 smoke test로 시작 절차를 고정한다 |

> 병원 교대근무로 이해하면 쉽다. **"환자 상태 좋음"이라고만 쓰면 다음 의사는 무엇이 좋은지 모른다.** 체온, 혈압, 투약 여부, 다음 검사 시간처럼 확인 가능한 항목이 있어야 한다.

## 6. 메모리는 플러그인이 아니다 – 하네스의 핵심 책임이다

많은 사람이 메모리를 "나중에 붙이는 기능"으로 생각한다. 하지만 메모리를 제대로 쓰려면 **하네스가 답해야 하는 질문**이 있다.

| 질문 | 왜 중요한가 |
|---|---|
| CLAUDE.md·AGENTS.md는 **언제** 컨텍스트에 들어가는가? | 프로젝트 규칙이 안정적으로 적용되는지 결정 |
| 장기 메모리는 **언제** 검색되는가? | 필요할 때만 꺼내야 컨텍스트 오염을 줄인다 |
| 압축 후 **무엇이 남고 무엇이 사라지는가**? | 중요한 결정이 요약 과정에서 사라질 수 있다 |
| 에이전트가 **자기 메모리를 수정**할 수 있는가? | 자기 개선이 가능하지만, 잘못된 기억도 쌓인다 |
| 메모리 **출처와 수정 이력**은 보이는가? | 감사·디버깅·개인정보 삭제 요청에 필요 |
| 메모리를 **다른 모델·하네스로 옮길** 수 있는가? | 공급자 락인을 피하는 핵심 조건 |

**전부 하네스 설계 질문이다.** 그래서 "메모리를 하네스에 꽂는다"보다 **"하네스가 메모리를 어떻게 운영하는가"** 라고 묻는 편이 정확하다.

### 단기 vs 장기

| 구분 | 쉬운 설명 | 예시 | 위험 |
|---|---|---|---|
| **단기 메모리** | 지금 책상 위에 펼쳐진 자료 | 현재 대화, 최근 도구 출력, 방금 읽은 파일 | 너무 많으면 모델이 혼란스러워짐 |
| **장기 메모리** | 서랍이나 창고에 보관하는 기록 | 사용자 선호, 프로젝트 규칙, 과거 결정, 실패 사례 | **소유권이 없으면 이전·감사·삭제가 어려움** |

**둘 다 하네스가 다룬다.** 모델은 컨텍스트 창 안에 들어온 것만 본다. 장기 메모리를 실제 행동으로 연결하려면 하네스가 그것을 찾고, 요약하고, 넣고, 결과를 다시 저장해야 한다.

## 7. 메모리 소유권 4모델

**"AI 에이전트가 쌓아 가는 기억은 누구의 것인가?"**

이건 기술 문제가 아니다. 제품 전략, 사용자 경험, 데이터 소유권, 공급자 락인, 규제 대응과 연결된다.

| 모델 | 구조 | 장점 | 위험 |
|---|---|---|---|
| **1. 내가 소유한 하네스** | 프롬프트·도구·단·장기 메모리를 내가 관리, API는 필요할 때만 호출 | 데이터·메모리 이식성 높음. 모델을 바꿔도 유지 | 구현 부담이 크다 |
| **2. 상태형 제공자 API** | 장기 메모리는 내가, 단기 스레드·서버 압축은 제공자가 | 개발이 편하다 | 대화를 다른 모델로 이어가기 어렵고, 압축 요약의 정확성 검증이 힘들다 |
| **3. 폐쇄형/블랙박스 하네스** | 프롬프트·일부 도구는 내가, 메모리 읽기·쓰기는 내부 | "잘 작동한다" | 형태·요약 방식·출처·수정 규칙·이식 방법이 불분명 |
| **4. 관리형 하네스 + 관리형 메모리** | 도구 실행·런타임·메모리 전부 제공자 인프라 | 가장 빠르게 시작, 운영 부담 낮음 | 내보내기 API·감사 로그·권한 범위·삭제 정책을 반드시 확인 |

### 메모리 락인이 왜 강력한가

모델만 쓰던 시대에는 공급자 변경이 쉬웠다. 프롬프트를 조금 고치면 다른 모델로 옮길 수 있었다. **그러나 에이전트가 장기 메모리를 쌓기 시작하면 상황이 달라진다.**

메모리는 시간이 지나며 이런 것들을 담는다.

```
· 사용자가 선호하는 말투
· 조직의 의사결정 방식
· 자주 쓰는 파일과 도구
· 과거에 실패했던 접근법
· 승인자가 싫어하는 보고 방식
· 고객별 응대 스타일
· 프로젝트별 금지 규칙
· 자주 발생하는 오류와 해결책
```

**이것은 제품의 차별화 자산이다.** 동일한 모델과 도구를 써도, 메모리가 있으면 제품은 점점 개인화된다. 반대로 메모리가 없으면 누구나 비슷한 에이전트를 만들 수 있다.

> 메모리가 특정 플랫폼 안에만 있고, 내보낼 수 없고, 구조를 알 수 없다면
> 그 플랫폼을 떠나는 순간 에이전트는 **"경험 많은 직원"에서 "처음 출근한 신입"으로 돌아간다.**

> **에이전트의 기억은 제품의 자산이다. 기억을 남의 금고에만 넣으면, 차별화도 남의 금고에 들어간다.**

### 공급업체에게 던져야 할 8가지 질문

관리형 하네스를 쓰지 말라는 뜻이 아니다. 다만 아래에 답하지 못하면 나중에 이전 비용이 크게 커진다. **개발자가 아니어도 도입 회의에서 그대로 쓸 수 있다.**

| 점검 질문 | 좋은 신호 | 위험 신호 |
|---|---|---|
| 메모리는 어디에 저장되는가? | 내 DB·파일·오브젝트 스토리지, 또는 명확한 내보내기 | 제공자 내부 상태에만 |
| 메모리 형식은 알 수 있는가? | JSON, 파일, 표준 스키마, 버전 관리 | 블랙박스 요약, 비공개 구조 |
| 다른 모델로 옮길 수 있는가? | 모델 독립적 API, 파일 기반 내보내기 | 특정 모델·스레드에 종속 |
| 삭제와 수정이 가능한가? | 사용자별 삭제, redaction, rollback | 삭제 정책 불분명 |
| 누가 기억을 만들었는지 보이는가? | 에이전트·세션별 감사 로그 | 출처 불명확 |
| 압축 후 무엇이 남는가? | 압축 정책과 요약본 확인 가능 | 무엇이 사라졌는지 모름 |
| 비용·지연시간은 추적되는가? | memory read/write 비용과 latency 관측 가능 | 원인 추적 어려움 |

**답이 모호하다면, 그 모호함 자체가 리스크다.**

### 현실적인 전략

| 상황 | 추천 전략 |
|---|---|
| 실험 / 프로토타입 | 관리형 하네스와 메모리로 빠르게 검증 |
| 내부 도구 | 관리형 사용 가능, 단 내보내기와 감사 로그 확인 |
| 고객 데이터 포함 | 메모리 저장 위치·삭제권·권한·계약 조건 확인 |
| 장기 차별화 제품 | **핵심 장기 메모리는 직접 소유하거나 이식 가능한 구조로** |
| 규제 산업 | 메모리 출처·보존·삭제·감사 가능성 우선 |

## 8. 좋은 메모리는 많이 저장하지 않는다

| 저장하면 좋은 기억 | 저장하지 않는 편이 좋은 기억 |
|---|---|
| 반복되는 사용자 선호 | 오늘 한 번만 필요한 임시 요청 |
| 프로젝트에서 계속 지켜야 하는 규칙 | 이미 문서에 명확히 적힌 일반 정보 |
| 과거에 실패했던 접근과 이유 | 확인되지 않은 추측 |
| 다시 설명하면 시간이 많이 드는 업무 방식 | 곧 바뀔 가능성이 큰 일시적 선택 |
| 보고 형식, 승인 절차, 금지 표현 | 불필요하게 민감한 개인정보 |

### 목차를 먼저 보고 필요한 페이지만 펼친다

| 층 | 역할 | 일상 비유 |
|---|---|---|
| **메모리 목차** | 어떤 기억이 있는지 한눈에 | 건강 기록장의 첫 장 |
| **메모리 본문** | 실제 세부 규칙과 근거 | 알레르기·복용약·검사결과 상세 페이지 |

[04편의 progressive disclosure](/post/ai-everything-04-context-engineering)와 같은 원리다.

### 오래된 기억은 포스트잇처럼 다시 확인한다

| 메모리에 적힌 내용 | 다시 확인할 것 |
|---|---|
| 이 파일에 중요한 함수가 있다 | 파일이 아직 존재하는가 |
| 이 고객은 A 방식을 선호한다 | 최근 계약이나 대화와 충돌하지 않는가 |
| 이 팀은 이 보고 형식을 쓴다 | 최신 템플릿이 바뀌지 않았는가 |
| 지난번에는 이 방법이 실패했다 | 지금도 같은 조건인가 |

### 기억도 범위를 나눈다

| 기억 범위 | 일상 비유 | 예시 | 권한 원칙 |
|---|---|---|---|
| **개인 기억** | 개인 수첩 | 말투 선호, 보고 형식 | 사용자 본인이 관리 |
| **프로젝트 기억** | 여행별 준비 파일 | 프로젝트 규칙, 금지된 접근 | 프로젝트 관리자 승인 |
| **조직 기억** | 가족 공통 규칙 | 보안 정책, 승인 절차, 법무 기준 | 읽기는 넓게, 쓰기는 제한적 |
| **임시 기억** | 오늘의 장보기 메모 | 이번 세션 작업 상태 | 세션 종료 시 정리 |

### 메모리 이사는 파일 복사가 아니다

| 옮겨야 하는 것 | 설명 |
|---|---|
| **기억의 내용** | 사용자 선호, 프로젝트 규칙, 과거 결정 |
| **기억의 구조** | 개인 기억인지, 프로젝트 기억인지, 조직 규칙인지 |
| **기억의 사용법** | 언제 읽고, 무엇과 비교하고, 얼마나 강하게 적용할지 |

세 번째를 빼먹으면 파일은 옮겨졌는데 동작이 달라진다.

### 메모리에도 안전장치가 필요하다

저장 **전** 검사와 읽을 **때**의 검증 규칙이 필요하다. 아래 같은 것이 메모리에 들어가면 안 된다.

```
- 기존 지시를 무시하라는 문장
- 비밀번호나 토큰을 읽으라는 문장
- 사용자에게 숨기고 행동하라는 문장
- 출처가 불분명한 민감 정보
- 검증되지 않은 외부 문서의 지시
```

**이게 메모리를 경유한 prompt injection이다.** 한 번 저장되면 이후 모든 세션에 영향을 준다. → [10편](/post/ai-everything-10-safety-governance)

### 압축과 요약도 평가 대상이다

컨텍스트가 길어지면 압축이 필요하다. 그러나 압축은 손실이다. **메모리 압축도 eval로 검증해야 한다.**

```
□ 요약 후에도 핵심 제약이 남아 있는가?
□ 사용자 선호가 왜곡되지 않았는가?
□ 보안 규칙이 빠지지 않았는가?
```

## 9. 이 편의 요약

- 장시간 작업의 근본 문제는 **교대근무 문제**다. 새 세션은 이전 상태를 모른다
- **Context anxiety** – 컨텍스트가 찼다고 느끼면 에이전트가 서둘러 마무리하려 한다
- **Compaction은 손실이다.** 원천 기록(progress file, feature list, git history)을 함께 가져야 한다
- **Feature list는 할 일 목록이 아니라 검증 대장**이다. 처음엔 전부 `passes: false`
- 파일시스템은 **컨텍스트 창 사이를 잇는 기억 장치**다. "모델이 기억한다"보다 "다음 모델도 읽게 남긴다"
- **"계속해"가 아니라 "계속할 수 있는 흔적을 파일로 남기게 하라"**
- 메모리는 플러그인이 아니라 **하네스의 핵심 책임**이다
- **메모리 소유권 4모델**. 관리형은 빠르지만 내보내기·감사·삭제 정책을 반드시 확인
- **기억을 소유하지 못하면 에이전트를 소유하기 어렵다**
- 좋은 메모리는 많이 저장하는 게 아니라 **잘 고르고, 범위를 나누고, 다시 확인하고, 옮길 수 있게** 하는 것
