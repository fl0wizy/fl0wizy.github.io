# `[hack-tree]` 시리즈 설계

- 작성일: 2026-09-16
- 대상: `src/content/posts/` 신규 브래킷 시리즈 9~10편
- 대체 대상: `net-browser-*` 19편 (번호 시리즈)

---

## 1. 배경 — 기존 19편이 실패한 지점

「네트워크 및 브라우저 성장기」 19편을 측정한 결과 세 가지가 확인됐다.

**형태가 내용보다 먼저 정해졌다.** 19편 전부가 11,000자 ± 1,000, `h2` 6~7개, SVG 정확히 1장이다. 예외가 없다. 주제가 요구한 분량이 아니라 틀을 먼저 만들고 채운 결과다.

**축이 교과서 목차였다.** 시리즈의 축이 "OSI 계층을 아래에서 위로"여서, 각 편의 "왜 지금 이 얘기냐"에 대한 답이 "다음 계층이니까"밖에 없다. 전환 문장이 연결을 주장하지만 독자의 질문에 답하지는 않는다. 읽는 쪽에서 "이어지는 것 같은데 왜 이어지는지 모르겠다"가 나오는 원인이다.

**표가 설명의 대체물로 쓰였다.** 표 칸에 한 번 등장하고 본문 어디에서도 설명되지 않는 용어가 **28개**다: `PKCE`, `SSTI`, `XXE`, `XFF`, `AES-GCM`, `ChaCha20-Poly1305`, `SERIALIZABLE`/`COMMITTED`/`UNCOMMITTED`, `GOAWAY`, `SpiderMonkey`/`SquirrelFish`/`TraceMonkey` 등.

대표 사례가 12편 §5의 OAuth 2.1 표다. 6줄 전부가 시리즈에서 한 번도 설명되지 않은 개념을 참조한다. §4가 OAuth와 OIDC의 차이는 설명하면서 **OAuth에 그랜트 타입이 있다는 사실 자체를 말하지 않아**, "implicit 그랜트 제거"가 독자가 존재를 모르는 것의 제거가 된다. 게다가 그 절의 실제 주장은 OAuth가 아니라 "권고는 지켜지지 않으니 필수로 올린다"는 표준화 과정에 대한 메타 관찰이고, 표는 그 주장의 증거물인데 가르치는 표처럼 생겼다.

**증거 가치가 없다.** 19편 중 대체 불가능한 것은 16편(hack-tree 제작기) 하나다. 나머지는 RFC와 MDN을 읽으면 누구나 쓴다. 그런데 16편은 다른 편을 **19번** 참조해서(5·6·8·9·10·11·12·13·14·15편) 혼자 서지 못하고, 가장 약한 18편 뒤에 놓여 있다.

## 2. 목표

네트워크와 풀스택을 공부해 **아키텍처를 설계하고 배포까지 굴렸다**는 것을 보이는 글. 지식 자체가 아니라 그 지식이 결정과 사고로 나타난 기록이 증거다.

## 3. 그릇 — 브래킷 시리즈

`[KISIA-CTF final]`, `[HACKSIUM 2026]`과 동일한 규약을 쓴다. 각 글이 **번호 없이 독립된 제목**을 가지므로 순서 의존을 구조적으로 만들 수 없다. 16편이 19번 참조에 묶였던 실패가 그릇 차원에서 차단된다.

부수 효과로 **나중에 편을 추가하는 비용이 0**이다. 지금 기억나지 않는 사건이 떠오르면 그때 한 편 더 쓰면 되고, 번호가 없으니 기존 편의 순서를 건드리지 않는다. 따라서 목차를 지금 완결시킬 필요가 없다.

### 프론트매터 규약

```yaml
id: "hack-tree-<topic-slug>"          # 파일명과 동일
title: "[hack-tree] <증상 또는 결정>: <부제>"
titleEn: "[hack-tree] ..."
description: "..."                     # 무슨 일이 있었는지 구체적으로. 1인칭 사건 서술
descriptionEn: "..."
date: "YYYY-MM-DD HH:MM"
category: "development"
tags: ["hack-tree", ...]               # 첫 태그가 시리즈 이름
published: true
```

`category`를 `development`로 통일한다. 제작기가 맞고, 해당 카테고리가 현재 비어 있으며, 전 편이 같은 카테고리여야 사이드바에서 한 덩어리로 보인다. 보안 성격이 있는 7·7b편도 예외를 두지 않는다.

## 4. 한 편의 골격

```
1. 증상        무엇이 어떻게 실패했나. 로그·에러 원문 그대로
2. 전제        왜 그게 될 거라고 생각했나
3. 어긋난 곳   전제가 틀린 지점. 개념은 여기서 처음 나오고, 나오는 자리에서 설명된다
4. 고친 것     실제 설정/커밋
5. 남은 것     이 경험이 바꾼 기본값
```

전경 편만 이 골격을 따르지 않는다(§5).

### 규칙 셋

1. **이름을 꺼내면 그 자리에서 설명한다.** 용어가 표 칸에서 처음 등장하는 것을 금지한다. PKCE 사고가 정확히 이 위반이었다.
2. **표는 비교에만 쓴다.** 나열이나 정의에는 쓰지 않는다. 표는 정리한 느낌만 주고 설명하지 않는다.
3. **다른 편 참조는 한 편당 링크 1개까지.** 앞 편을 읽지 않아도 완결되어야 한다.

분량은 정하지 않는다. 사건이 요구하는 만큼 쓴다. 3,000자짜리와 12,000자짜리가 같은 시리즈에 섞이는 것이 정상이다.

## 5. 전경 편

**`[hack-tree] 533개 노드를 굴리는 구조`**

유일하게 SVG가 주인공인 편이자, 나머지 편으로 가는 허브. 골격은 이렇다.

- 무엇인가 — 웹·포너블·커널·CS 4축 533노드(커널 175 / 포너블 156 / 웹 136 / CS 66), 웹 축의 L0–L7 사다리와 6단계 코스
- 어떻게 생겼나 — 아키텍처 SVG 1장. 엣지(Caddy) / web(Next.js 15·React 19) / api(FastAPI·Python 3.12) / SQLite + 백업 사이드카 / GitHub Actions → GHCR → GCP VM, Terraform + cloud-init
- 경계가 어디인가 — 외부에 열린 포트는 `:80`·`:443`뿐. TLS가 끝나는 지점, 같은 출처로 도는 `/api/*` rewrite
- 각 사건 편으로 나가는 링크

규칙 3(참조 1개)은 전경 편에 적용하지 않는다. 허브가 그 역할이다.

## 6. 사건 편 8~9개

각 편에 그 편에서 **반드시 처음 설명해야 할 개념**을 명시한다. 규칙 1의 체크리스트다.

### 1. 빌드는 통과하는데 실행이 안 됐다

- **증상** — `pnpm build`가 CI에서 `ERR_DLOPEN_FAILED`로 exit 1. 빌드 로그는 통과인데 실행 시점에 죽는다.
- **원인** — `build-embeddings.mts`가 로드하는 `onnxruntime-node` prebuilt가 glibc(`ld-linux-*.so`)를 요구하는데 `node:22-alpine`은 musl이다. build 스테이지만 slim으로 바꾸자 이번엔 `sharp`가 같은 mismatch를 냈다.
- **고침** — install/build/run 전 스테이지를 `node:22-slim`으로 통일. 이미지 크기를 내주고 예측 가능성을 샀다.
- **재료** — `6bacd6e`
- **처음 설명할 개념** — musl / glibc, prebuilt 네이티브 바이너리, 다단계 빌드에서 libc가 스테이지마다 다를 수 있다는 것
- **이어짐** — 이 결정이 3편의 wget 사고를 만든다

### 2. 130MB 모델을 어디에 둘 것인가

네 단계를 거쳤고, 각 단계가 앞 단계의 대가를 치렀다.

- **0단계** — `docker build` 중 HuggingFace에서 129MB를 직접 받았다. 비-hermetic 빌드. GHA 캐시가 무효화될 때마다 재다운로드하고 실패했다.
- **1단계** — Git LFS로 벤더링(`0f04057`). CI checkout에 `lfs:true`.
- **2단계** — 서버가 `git pull` 할 때 LFS smudge로 129MB를 또 받았다. 서버는 모델을 GHCR 이미지에서 쓰므로 불필요하다. `GIT_LFS_SKIP_SMUDGE=1`로 땜질(`9acbacc`).
- **3단계** — LFS 대역폭 월 10GB 한도가 소진돼 **CI checkout 자체가 차단**됐다. LFS를 버리고 `scripts/fetch-models.sh`가 HF 고정 revision(`761b726`)에서 받아 sha256을 검증한다. CI는 `actions/cache`로 재다운로드를 피한다(`f1a372c`).
- **남은 것** — 용량 문제를 풀려다 **공급망 무결성 검증이 부수 효과로 따라왔다**. 해시가 맞지 않으면 실패한다.
- **재료** — `0f04057` → `9acbacc` → `f1a372c`
- **처음 설명할 개념** — hermetic 빌드, Git LFS smudge, 고정 revision, sha256 검증

### 3. 헬스체크가 거짓으로 실패한다

이 편은 연쇄 사고 하나와 그것을 고치자 드러난 두 번째 사고를 다룬다.

- **사고 1 — 안전장치가 배포를 죽였다.** web만 폴링하고 api·caddy는 단발 체크였다. 신규 마이그레이션 배포에서 api가 `alembic upgrade` + APScheduler 기동에 수 초 걸리는 동안 web은 1초 만에 통과했고, 직후 단발로 친 api 체크가 거짓 실패를 냈다. 거짓 `api unhealthy`가 자동 롤백을 유발했는데, **롤백 대상 구이미지는 DB가 이미 새 revision이라** alembic 정합 실패로 크래시했다. `ROLLBACK ALSO FAILED`로 배포가 완전히 막혔다. → api·caddy도 폴링화(`275b2bb`).
- **사고 2 — 고치자 비로소 도달한 문제.** 도메인 모드에서 `curl -H "Host: $site" https://localhost`는 **TLS SNI가 `localhost`로 남고 Host 헤더는 도메인**이라 둘이 불일치했다. Caddy의 HTTP/2가 `421 Misdirected Request`를 반환해 거짓 `caddy edge unhealthy`가 났다. `--resolve "$site:443:127.0.0.1"`로 도메인을 로컬에 매핑해 SNI와 Host를 일치시켰다(`2a3d3e5`).
- **사고 3 — 1편의 여파.** web runner를 alpine에서 slim으로 바꾸며 busybox `wget`이 사라졌고, `python:3.12-slim`에도 원래 없었다. 컨테이너 내부 프로브가 전부 죽어 `web unhealthy`가 났다. 두 이미지에 `wget` 설치(`83b70f1`).
- **남은 것** — 롤백은 되돌릴 수 있는 것만 되돌린다. 마이그레이션은 단방향이라 롤백의 사각이다.
- **재료** — `275b2bb`, `2a3d3e5`, `83b70f1`
- **처음 설명할 개념** — SNI와 Host 헤더가 서로 다른 계층이라는 것, `421 Misdirected Request`, alembic revision의 단방향성, 단발 체크와 폴링의 차이

### 4. 되돌릴 수 있는 배포

- **문제** — 움직이는 태그(`:latest`)만 쓰면 되돌릴 지점을 특정할 수 없다. 어느 시점의 코드가 돌고 있는지도 확정되지 않는다.
- **고침** — compose 이미지 태그를 `IMAGE_TAG`로 변수화해 SHA 고정 배포(`7d0d013`). `deploy.sh`에 SHA핀 + 자동롤백 + 다층 헬스 + `flock` 가드(`f23b474`). CI에 `deploy-validate` 잡과 `DEPLOY_SHA` 전달(`6fa765f`).
- **재료** — `f23b474`, `7d0d013`, `6fa765f`
- **처음 설명할 개념** — 움직이는 태그 대 불변 태그, `flock`이 막는 것(동시 배포), 다층 헬스의 층 구성
- **주의** — 3편과 소재가 붙어 있다. 3편은 "헬스체크가 틀렸다", 4편은 "되돌릴 수 있게 만든다"로 축을 분리한다. 겹치면 4편을 3편에 흡수한다.

### 5. 남의 인프라에 기대는 지점들

- **사고 1** — `appleboy/ssh-action`이 실행 시점에 GitHub releases에서 `drone-ssh` 바이너리를 받는데, 그 다운로드가 504로 반복 실패해 배포가 막혔다. 러너 기본 openssh로 직접 접속해 런타임 다운로드 의존을 제거했다. 옮기면서 **host key 검증을 추가**했다 — appleboy 기본값은 검증이 없다(`cd2a867`).
- **사고 2** — GCP 서버가 `registry-1.docker.io`에 직접 닿지 못해 `caddy:2-alpine` pull이 i/o timeout으로 실패했다. cloud-init에서 `/etc/docker/daemon.json`에 `registry-mirrors`로 `mirror.gcr.io`를 심어 우회했다(`2c71c1d`).
- **남은 것** — 2편과 같은 형태다. 가용성 문제를 풀었더니 보안이 따라왔다.
- **재료** — `cd2a867`, `2c71c1d`
- **처음 설명할 개념** — 액션이 런타임에 무엇을 받는가, host key 검증, pull-through 캐시

### 6. 백업은 복구를 해봐야 백업이다

- **문제** — SQLite 파일을 그냥 복사하면 쓰기 도중 상태가 섞인다.
- **고침** — `sqlite3 .backup`으로 일관된 스냅샷, `PRAGMA integrity_check`로 검증, 원자적 발행(`490df9b`). 7일 회전(`7458802`). 데이터 볼륨은 읽기 전용 마운트 — 백업 프로세스가 원본을 건드릴 경로를 없앤다. prod compose에 backup 사이드카 + `backup_data` 볼륨(`9c5d270`).
- **본론** — `restore.sh`가 **손상된 백업을 거부**한다(`63e300f`). 복구 경로를 테스트하지 않은 백업은 백업이 아니다.
- **재료** — `490df9b`, `63e300f`, `7458802`, `9c5d270`, `8d969ce`
- **처음 설명할 개념** — `.backup` API가 `cp`와 다른 이유, `integrity_check`, 원자적 발행

### 7. 정답을 숨기려던 네 번의 시도

원래 결정형으로 잡았으나 커밋 이력이 사건형임을 보여줬다. **정답키는 처음에 `web/public`에 있었다** — 정적으로 서빙되는 디렉터리다. 16편은 이것을 처음부터 의도한 설계처럼 적었는데, 실제로는 노출된 상태에서 고친 것이다.

- **1단계** — 퀴즈 정답이 노드 frontmatter에 그대로 있었다. 클라이언트에서 정답을 제거하는 헬퍼를 붙였다(`aed7cc0`). 이 시점의 방어는 난독화다.
- **2단계** — 빌드 때 `quiz-answers.json`으로 분리(`dece26a`), api에 정답키 로더와 config 경로 추가(`c6e723a`). 채점이 서버로 갔다.
- **3단계** — 그런데 그 파일이 `web/public`에 있었다. URL만 알면 받을 수 있는 자리다. `web/private`로 이전(`21a9731`).
- **4단계** — 채점 자체가 먹통이었던 것을 정답키 포맷 마이그레이션과 함께 수정(`ee48e69`), 이후 292노드 MCQ + 주관식 accept 저작(`792b585`), 나머지 241노드(`2e1527c`)로 전 노드 자동 채점 완성.
- **남은 것** — 클라이언트에서 채점하며 정답을 숨기려는 시도는 전부 난독화다. 그리고 **서버로 옮기는 것과 서빙 경로 밖으로 옮기는 것은 별개의 단계**다. 2단계에서 멈췄으면 여전히 노출이었다.
- **재료** — `aed7cc0`, `dece26a`, `c6e723a`, `21a9731`, `ee48e69`
- **처음 설명할 개념** — 정적 서빙 디렉터리가 무엇인가, 난독화와 분리의 차이

### 7b. 기능을 지워서 줄인 공격면

7편에 붙일지 독립시킬지는 7편 초안 분량을 보고 정한다. 주장은 하나다 — **안 만들면 안 생긴다.**

- 공개 회원가입 없음. 관리자 초대만(`7285001` 1회용·만료·자동로그인, `72f536b` RBAC+CSRF, `5659b65` 초대 가입 페이지, `2dec1be` admin이 유저 1명 프로비저닝 CLI). → 계정 열거, 이메일 인증 우회, 비밀번호 재설정 포이즈닝, 스팸 가입이 전부 해당 없음이 된다
- CORS 설정이 존재하지 않는 구조 — 브라우저가 `https://hack-tree.com/api/...`를 호출하고 Next.js가 내부 `api:8000`으로 rewrite한다. 브라우저 입장에서 같은 출처라 설정할 것이 없다. Origin 반사, `null` 신뢰, 자격증명 동시 허용 같은 흔한 실패가 설정과 함께 사라진다
- argon2 + 서버 상태 세션(JWT 아님), CSRF 토큰(`99a9281`) — 즉시 무효화가 필요한 상황에서 단순하다
- IDOR을 구조로 막기 — `GET /api/activity`가 세션의 `user_id`만 읽는다(`9a5ef4f`). 클라이언트가 id를 보내지 않으면 바꿔치기할 것도 없다
- **처음 설명할 개념** — 계정 열거, Origin 반사, 자격증명 허용 플래그, IDOR

### 8. 한글이 ASCII 다이어그램을 깨뜨린다

- **증상** — 노드 본문의 ASCII 박스 다이어그램이 한글이 섞이면 우측 테두리가 어긋난다.
- **원인** — East Asian Width. 한글·한자·전각 문자는 터미널/모노스페이스에서 2칸을 차지하는데, 문자열 길이는 1로 센다.
- **고침** — 4차례 재정렬 웨이브: 단일박스 8노드 → 격자형 12노드 → 단일박스 우측 테두리 13노드 → 비트필드·표 헤더 3건.
- **재료** — `cce699c`, `99e75ea`, `e9e391e`, `79870ed`
- **처음 설명할 개념** — East Asian Width, 문자 수와 표시 폭의 차이

## 7. SVG 정책

**전경 편 1장만 SVG로 간다.** 나머지 편의 기본은 표와 코드블록이고, 그림은 **화살표로 관계를 그려야 할 때만** 넣는다.

기존 19장을 측정했을 때 7장(07·10·12·13·15·deep-01·deep-02)이 화살표 0개였다. 관계를 그리지 않는다는 뜻이고, 그렇다면 그것은 그림이 아니라 박스에 담아 이미지로 만든 글이다. 텍스트 노드가 장당 32~66개였다. 그 대가는 전부 실측됐다.

- 검색·복사가 안 된다
- 화면에서 축소되면 읽히지 않는다
- 스크린리더가 읽지 못한다
- 영어판을 위해 24장을 통째로 다시 만들어야 했다

판정 기준: **화살표가 없으면 표나 코드블록으로 쓴다.**

## 8. 기존 19편 처리

`published: false`로 내린다. 삭제하지 않는다.

- 재료로 계속 쓴다
- 되돌릴 수 있다
- 내부 상호 링크(`/post/net-browser-*`)가 다수 걸려 있으므로, 내릴 때 **다른 published 글에서 이 19편으로 가는 링크가 있는지 검사**하고 있으면 제거한다
- 16편의 내용은 전경 편과 7편으로 분해되어 흡수된다

## 9. 역할 분담

**본문은 작성자가 직접 쓴다.** 결정을 내린 사람만 쓸 수 있는 문장이 이 시리즈의 전부다.

## 10. 검증

기존 19편을 진단할 때 쓴 측정을 그대로 신규 글의 게이트로 돌린다.

| 검사 | 방법 | 기준 |
|---|---|---|
| 규칙 1 위반 | 용어의 첫 등장 위치가 표 안인지 | 0건 |

| 기존 lint | `npm run lint:posts` | 오류 0 |

규칙 1·3 검사는 스크립트로 만든다. `scripts/lint-posts.mjs`에 얹을지 별도 스크립트로 둘지는 구현 단계에서 정한다.

## 11. 범위 밖

- **`docs(spec)` → `docs(plan)` → TDD 워크플로.** 596 커밋 전부가 이 순서를 따르지만, hack-tree의 아키텍처가 아니라 **작업 방식**이다. 여기 들어오면 시리즈 축이 흐려진다. 별도 글 한 편으로 둔다.
- **네트워크/풀스택 지식의 독립 편.** 지식은 결정의 근거로만 등장한다. 기존 19편을 주제별로 재편해 흡수하는 안은 검토했고 기각했다 — 지식 편과 제작 편이 한 글에 합쳐지면 다시 11,000자 틀로 회귀할 위험이 크다.
- **기존 19편의 삭제.** `published: false`까지만 한다.
